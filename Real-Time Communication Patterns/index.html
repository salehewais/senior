Long Polling

الاتجاهشبه أحادي البروتوكولHTTP/1.1 التأخيرمتوسط–عالٍ

المفهوم والتعريف

بدل أن يستطلع العميل الخادم باستمرار (short polling)، يفتح طلباً ويُبقي الخادم الاتصال معلّقاً حتى تتوفر بيانات جديدة أو ينتهي المهلة — ثم يعيد العميل الطلب فوراً.

كيف يعمل

  1. العميل يرسل طلب HTTP وينتظر.
  2. الخادم يعلّق الاستجابة حتى يحدث حدث أو تنتهي المهلة.
  3. عند توفر بيانات، يُرسل الرد ويُغلق الاتصال.
  4. العميل يعيد فتح طلب جديد فوراً لمتابعة الاستماع.

المميزات والعيوب

المميزات

  • يعمل فوق HTTP العادي دون بروتوكولات خاصة
  • متوافق مع الجدران النارية والبروكسيات القديمة
  • أبسط من WebSockets للتحديثات أحادية الاتجاه

العيوب

  • حمل أعلى بسبب إعادة فتح الاتصالات باستمرار
  • تأخير إضافي بين إغلاق الرد وفتح الطلب التالي
  • استهلاك موارد على الخادم للاتصالات المعلّقة

حالات الاستخدام

  • إشعارات بسيطة
  • دردشة قديمة / legacy
  • عندما لا يتوفر SSE أو WebSocket
  • واجهات خلف جدران نارية صارمة

Server-Sent Events (SSE)

الاتجاهأحادي البروتوكولHTTP/1.1 · HTTP/2 التأخيرمنخفض

المفهوم والتعريف

قناة HTTP مفتوحة يبث عبرها الخادم أحداثاً نصية مستمرة إلى العميل. المتصفح يدعمها أصلاً عبر EventSource مع إعادة اتصال تلقائية.

كيف يعمل

  1. العميل يفتح اتصال EventSource إلى مسار الأحداث.
  2. الخادم يرد بـ Content-Type: text/event-stream ويبقي الاتصال مفتوحاً.
  3. كل حدث يُرسل ككتلة نصية (data: …) مفصولة بأسطر فارغة.
  4. عند انقطاع الاتصال يعيد العميل المحاولة تلقائياً.

المميزات والعيوب

المميزات

  • بسيط جداً للبث أحادي الاتجاه
  • إعادة اتصال ومعرّفات أحداث مدمجة في المعيار
  • يعمل جيداً مع HTTP/2 وتعدد الاتصالات

العيوب

  • اتجاه واحد فقط (من الخادم للعميل)
  • نصي فقط — ليس مثالياً للبيانات الثنائية الثقيلة
  • حدود اتصال على HTTP/1.1 لكل نطاق

حالات الاستخدام

  • Live feeds وأخبار لحظية
  • أسعار أسهم / مؤشرات
  • شريط تقدّم المهام
  • لوحات مراقبة وtelemetry

4إعادة اتصال تلقائية عند الانقطاع
ثنائي الاتجاه

WebSockets

الاتجاهثنائي البروتوكولTCP بعد HTTP handshake التأخيرمنخفض جداً

المفهوم والتعريف

بعد مصافحة HTTP للترقية (Upgrade)، يتحول الاتصال إلى قناة TCP ثنائية الاتجاه كاملة الإرسال — مثالية للدردشة، الألعاب، والتحرير التعاوني.

كيف يعمل

  1. العميل يطلب ترقية الاتصال عبر رؤوس HTTP الخاصة بـ WebSocket.
  2. الخادم يوافق (101 Switching Protocols).
  3. القناة تصبح ثنائية: إطارات نصية أو ثنائية في الاتجاهين.
  4. أي طرف يغلق الاتصال بإطار close عند الانتهاء.

المميزات والعيوب

المميزات

  • أقل تأخيراً للتفاعل ثنائي الاتجاه
  • دعم البيانات النصية والثنائية
  • كفاءة أعلى من فتح HTTP متكرر

العيوب

  • تعقيد أعلى (حالة الاتصال، إعادة الاتصال، التوسع)
  • بعض البروكسيات/الجدران النارية تعيق الترقية
  • يتطلب بنية تحتية تدير اتصالات طويلة الأمد

حالات الاستخدام

  • دردشة فورية
  • ألعاب متعددة اللاعبين
  • تحرير تعاوني (co-editing)
  • لوحات تداول تفاعلية

Webhooks

الاتجاهأحادي (خادم→خادم) البروتوكولHTTP التأخيريعتمد على الشبكة

المفهوم والتعريف

عندما يحدث حدث عند مزوّد (Source)، يستدعي عنوان URL لديك (Destination) بطلب HTTP — عادة POST — محملاً ببيانات الحدث. نمط دفع بين خوادم وليس متصفحاً.

كيف يعمل

  1. تسجّل عنوان endpoint لدى المزوّد وتشترك في أنواع الأحداث.
  2. عند وقوع الحدث يرسل المزوّد طلب HTTP إلى عنوانك.
  3. خادمك يتحقق من التوقيع/المصادقة ويعالج الحمولة.
  4. ترد بسرعة (2xx)؛ المعالجة الثقيلة تُؤجَّل لطابور.

المميزات والعيوب

المميزات

  • لا حاجة لاستطلاع — دفع عند الحدث فقط
  • تكامل بسيط بين أنظمة مستقلة
  • منخفض التعقيد إن أُحسنت الموثوقية

العيوب

  • يتطلب endpoint عاماً موثوقاً ومتاحاً
  • يجب التعامل مع إعادة المحاولة والترتيب المكرر
  • أمن التوقيعات وتجنب الطلبات المزيفة ضروري

حالات الاستخدام

  • بوابات دفع (Stripe وغيرها)
  • أحداث GitHub / CI
  • إشعارات Slack / Discord
  • مزامنة CRM وأنظمة خارجية

جدول المقارنة

ملخص سريع لاختيار النمط المناسب حسب الاتجاه، التأخير، والتعقيد.

النمط الاتجاه البروتوكول التأخير التعقيد أمثلة استخدام
