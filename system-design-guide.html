System Design — Introduction

تصميم الأنظمة (System Design) هو فن بناء أنظمة برمجية قابلة للتوسع، موثوقة، وآمنة — ليس مجرد رسم صناديق، بل فهم trade-offs بين الأداء والتكلفة والاتساق.

🏙️ تخيل مدينة: OOD يصمّم الشقة الواحدة وتفاصيل غرفها (Classes & Objects)، و Software Architecture يخطط الهيكل العام للمدينة ويحدد أين تقام الأحياء السكنية والصناعية (High-level Components)، بينما System Design يمدّ شبكات الطرق، الكهرباء، والمياه ليربط هذه الأحياء ويضمن استيعابها للنمو السكاني (Infrastructure & Scalability).

Software ArchitectureModules، layers، boundariesMonolith vs microservices split

💡
في المقابلة: System Design يختبر قدرتك على التفكير بصوت عالٍ، طرح أسئلة clarifying، وتبرير قراراتك — مش الحل المثالي الوحيد. ابدأ بـ 30 Core Concepts كمرجع سريع.

Back-of-the-Envelope
Estimation

التقديرات السريعة تثبت أنك تفهم scale — استخدم أرقاماً مدورة.

Capacity Estimation

Storage، bandwidth، memory — how much infra needed?

Load Estimation

QPS/TPS from DAU × actions/day. Peak = 2–5× average.

Formulas
# QPS from DAU
DAU = 100M, actions/user/day = 10
Total/day = 1B → QPS ≈ 1B / 86400 ≈ 12K (peak ~3x → 36K)

# Storage
100M records × 500 bytes = 50GB raw (+ indexes ~2x)

# Bandwidth
10K QPS × 10KB response = 100MB/s ≈ 800 Mbps

# Retention
1GB/day × 365 days × 5 years = ~1.8TB
📊 DAU/MAU

MAU ≈ 3–5× DAU for social apps. Peak QPS ≈ 2–5× average.

🔢 Powers of 2

2^10≈1K, 2^20≈1M, 2^30≈1B — للحساب الذهني

🧮التقدير مش دقة رياضية — الهدف orders of magnitude. لو قلت 10K QPS والصح 15K، ده acceptable. لو قلت 10 والصح 10K، ده red flag.
Interview Example — Twitter-like
Assumptions: 300M MAU, 100M DAU, 2 tweets/user/day
Writes: 200M/day → ~2.3K QPS (peak ~7K)
Reads: 10× writes → ~70K QPS peak
Storage: 200M × 300 bytes × 365 × 5yr ≈ 100TB+ (with media much more)
Bandwidth: 70K × 2KB ≈ 140MB/s read-heavy

CAP & PACELC
Distributed Trade-offs

نظرية CAP: في partition، تختار بين Consistency و Availability. PACELC يوسّع: Else — Latency vs Consistency.

CP

Consistent + Partition tolerant — ZooKeeper, etcd. تفضّل correctness.

AP

Available + Partition tolerant — Cassandra, Dynamo. eventual consistency.

💡
CAP يصف worst-case partition — معظم الوقت تحاول balance وليس binary choice.

نماذج الاتساق
Consistency Models
Strong

Linearizable — reads see latest write. Costly in distributed.

Eventual

Replicas converge over time. High availability.

Causal

Preserves cause-effect order. Middle ground.

Read-your-writes

User always sees own updates. Session stickiness.

Monotonic reads

No going backwards in time on reads.

📰Strong consistency = صحيفة واحدة للكل. Eventual = كل فرع يطبع نسخته ويتزامن لاحقاً — أسرع لكن قد ترى خبراً قديماً لثوانٍ.
⚠️
Latency triangle: Consistency + Availability + Low Latency — pick two under load.

Idempotency & Deduplication
Reliable Operations

نفس الطلب مرتين = نفس النتيجة. ضروري مع retries وat-least-once delivery.

Pattern
POST /pay
Header: Idempotency-Key: uuid-v4

Server:
  if key exists in store → return cached response
  else → process + store result with TTL
💬
استخدم idempotency keys في payments، webhooks، وأي POST mutating.
Ordering — Total

Global order across all events — single leader or total order broadcast.

Ordering — Partial

Order within partition/key only — Kafka partition model.

Deduplication

Store processed message IDs (inbox) with TTL — at-least-once safe.

Exactly-once illusion

Idempotent consumer + dedup = effectively once for business logic.

Networking Layer
DNS

Resolution hierarchy: browser cache → OS → resolver → root → TLD → authoritative. TTL controls cache.

TCP vs UDP

TCP: reliable, ordered, connection-oriented. UDP: fast, loss tolerant (video, DNS).

Connection Pool

Reuse TCP connections — avoid handshake overhead per request.

HTTP/2 & HTTP/3

Multiplexing, header compression. HTTP/3/QUIC over UDP — faster on lossy networks.

Long Polling

NAT

Network Address Translation — private IPs → public IP. Enables many devices behind one IP.

Rate Limiting vs Throttling

Rate limit = hard cap (429). Throttle = slow down gradually — smoother UX under load.

CQRS & Saga
Data & Distributed Transactions
CQRS

Separate read/write models. Optimize each side. Adds complexity.

Event Sourcing

Store events not state. Full audit trail. Replay capability.

Saga — Choreography

Services react to events. Decentralized, harder to trace.

Saga — Orchestration

Central coordinator drives steps. Clearer, single point.

Scaling & State
Horizontal vs Vertical
Vertical Scaling

Bigger machine — simple but ceiling.

Horizontal Scaling

More nodes + load balancer — preferred at scale.

Stateless Services

Stateful

Microservices
Service Discovery · Communication · Patterns

Microservices = خدمات صغيرة مستقلة، لكل واحدة DB خاص — التحدي في التنسيق والـ observability.

Service Discovery

Consul، etcd، Kubernetes DNS — services find each other dynamically without hardcoded IPs.

Inter-Service Communication

Sync: REST/gRPC. Async: Kafka/events. Prefer async for decoupling.

Data per Service

كل service يملك data store — no shared DB. Integration via APIs/events only.

Circuit Breaker

Stop calling failing service — fail fast، prevent cascade. (Hystrix/Resilience4j pattern)

Retry & Timeout

Exponential backoff + jitter. Timeout at every hop — total < user SLA.

Microservices Anti-Patterns

Distributed monolith، shared DB، chatty sync calls، no tracing — debug nightmare.

💡
Sidecar pattern: Envoy/Istio proxy بجانب كل pod — mTLS، retries، metrics بدون تغيير app code.

SQL vs NoSQL
Storage Fundamentals
FactorSQLNoSQL
SchemaFixed, enforcedFlexible, schema-on-read
ScaleVertical + read replicasHorizontal sharding native
TransactionsACID strongOften eventual, per-item
JoinsNativeDenormalize or app-side
ExamplesPostgreSQL, MySQLMongoDB, Cassandra, Redis
Indexing — B-Tree

Range queries, default in most SQL.

Hash Index

Equality only — O(1) lookup.

Composite Index

Multi-column — order matters.

Covering Index

Index includes all query columns — no table lookup.

⚠️
Indexes speed reads but slow writes and consume storage — index what you query.
Normalization

Reduce redundancy — 3NF typical. Joins at read time.

Denormalization

Duplicate data for read performance — feeds, analytics.

Backup — Full

Complete snapshot — slow, simple restore.

Backup — Incremental

Changes since last backup — faster, chain restore.

PITR

Point-in-time recovery via WAL replay — RPO in minutes.

Schema Design

Model entities، relationships، access patterns first — then pick SQL vs NoSQL.

Data Modeling

Design for queries you'll run — denormalize for read-heavy، normalize for write consistency.

Hot Partitions

Shard key skew — one partition gets all traffic. Fix: random suffix، re-shard، salting.

Data Migration

Dual-write → backfill → verify → cutover. Zero-downtime needs careful planning.

Caching Patterns
Cache Strategies
PatternFlowPros/Cons
Cache-AsideApp reads cache, on miss reads DB, writes cacheSimple; stale risk
Read-ThroughCache loads from DB on missCentralized logic
Write-ThroughWrite cache + DB syncConsistent but slower writes
Write-BackWrite cache, async flush DBFast writes; data loss risk
Write-AroundWrite DB directly, bypass cacheGood for write-heavy, cold reads
Cache Hit / Miss

Hit = data in cache (fast). Miss = fetch from DB then populate cache. Hit rate = key metric.

Cache vs DB

Cache = speed layer in-memory. DB = source of truth on disk. Never treat cache as primary store.

Eviction — LRU

Least Recently Used — evict oldest accessed. Default in many systems.

Eviction — LFU / FIFO

LFU = least frequent. FIFO = first in first out. Pick based on access pattern.

Redis vs Memcached

Redis: rich types, persistence, pub/sub. Memcached: simple KV, multithreaded, pure cache.

Cache Invalidation

أصعب جزء 😄 — TTL، event-driven invalidation، or version keys. Stale data vs complexity.

TTL

Time-to-live — balance freshness vs hit rate.

Cache Stampede

Many requests on expiry — lock/mutex or probabilistic early refresh.

Local vs Distributed

In-process fast but inconsistent. Redis shared across nodes.

Hot Keys

Replicate hot key across nodes. Local cache layer.

Cache Penetration

Query for non-existent keys — Bloom filter or cache null with short TTL.

CDN as Cache

Edge POPs serve static and cacheable API responses globally.

Architecture
Read:  Client → CDN? → App → Redis → DB
Write: Client → App → DB → Invalidate/Update cache
       (write-through or cache-aside invalidation)
