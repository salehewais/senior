2. Domain Layer

domain/entities/user.py

ده الـ Entity الأساسي بتاعنا.

مش هيعرف أي حاجة عن PostgreSQL أو SQLAlchemy.

from dataclasses import dataclass
from uuid import UUID, uuid4


@dataclass
class User:
    id: UUID
    name: str
    email: str

    @classmethod
    def create(cls, name: str, email: str):
        return cls(
            id=uuid4(),
            name=name,
            email=email
        )

3. Application Layer

أولًا: application/interfaces/user_repository.py

ده الـ Repository Interface.

الـ Application بتقول إنها محتاجة Repository يقدر يحفظ User، لكنها مش بتحدد إزاي.

from abc import ABC, abstractmethod
from domain.entities.user import User


class UserRepository(ABC):
    @abstractmethod
    def save(self, user: User) -> None:
        pass

ثانيًا: application/use_cases/create_user.py

ده الـ Use Case المسؤول عن إنشاء المستخدم.

from domain.entities.user import User
from application.interfaces.user_repository import UserRepository


class CreateUser:
    def __init__(self, user_repository: UserRepository):
        self.user_repository = user_repository

    def execute(self, name: str, email: str) -> User:
        user = User.create(name, email)
        self.user_repository.save(user)
        return user
لاحظ: CreateUser بيتعامل مع Interface، مش مع PostgreSQL Repository مباشرة.

4. Infrastructure Layer

هنا بقى هنقسم Infrastructure إلى Persistence و Data Access زي ما طلبت.

أولًا: Data Access

infrastructure/data_access/database.py

مسؤول عن إعداد الاتصال بقاعدة البيانات وإنشاء SQLAlchemy Session.

from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker, declarative_base

DATABASE_URL = (
    "postgresql+psycopg://postgres:password@localhost:5432/mydb"
)

engine = create_engine(DATABASE_URL)
SessionLocal = sessionmaker(
    bind=engine,
    autoflush=False,
    autocommit=False
)
Base = declarative_base()
  • engine: مسؤول عن الاتصال بقاعدة البيانات.
  • SessionLocal: مصنع لإنشاء Sessions.
  • Base: الأساس اللي هتورث منه SQLAlchemy Models.

infrastructure/data_access/models.py

هنا بنعرّف شكل الجدول باستخدام SQLAlchemy.

from sqlalchemy import Column, String
from sqlalchemy.dialects.postgresql import UUID
from infrastructure.data_access.database import Base


class UserModel(Base):
    __tablename__ = "users"

    id = Column(UUID(as_uuid=True), primary_key=True)
    name = Column(String(100), nullable=False)
    email = Column(String(255), unique=True, nullable=False)
خلي بالك: UserModel مش هو نفسه User الموجود في Domain. الأول بيمثل شكل البيانات في قاعدة البيانات، والتاني بيمثل الـ Business Entity.

ثانيًا: Persistence — Mapper

infrastructure/persistence/mappers/user_mapper.py

وظيفته تحويل البيانات بين الـ Domain والـ Database Model.

from domain.entities.user import User
from infrastructure.data_access.models import UserModel


class UserMapper:
    @staticmethod
    def to_model(user: User) -> UserModel:
        return UserModel(
            id=user.id,
            name=user.name,
            email=user.email
        )

    @staticmethod
    def to_entity(model: UserModel) -> User:
        return User(
            id=model.id,
            name=model.name,
            email=model.email
        )
User Entity  <---  User Mapper  <---  UserModel

الـ Mapper هو اللي بيمنع الـ Domain Entity من الارتباط بشكل جدول قاعدة البيانات.

ثالثًا: Persistence — Repository Implementation

infrastructure/persistence/repositories/postgres_user_repository.py

هنا هننفذ الـ Interface اللي عرفناها في Application.

from domain.entities.user import User
from application.interfaces.user_repository import UserRepository
from infrastructure.data_access.models import UserModel
from infrastructure.persistence.mappers.user_mapper import UserMapper


class PostgresUserRepository(UserRepository):
    def __init__(self, session):
        self.session = session

    def save(self, user: User) -> None:
        user_model = UserMapper.to_model(user)
        self.session.add(user_model)
        self.session.commit()

لاحظ المسؤوليات:

  1. استقبل Domain Entity.
  2. استخدم Mapper لتحويلها إلى SQLAlchemy Model.
  3. استخدم Session لحفظ البيانات.
  4. نفذ Commit.

إذن الـ Repository مش مسؤول عن تعريف الاتصال بقاعدة البيانات؛ هو بيستخدم Session جاهزة تم تمريرها إليه.

5. Presentation Layer — FastAPI

presentation/api/user_controller.py

ده الـ Controller اللي هيستقبل HTTP Request.

from fastapi import APIRouter, Depends
from pydantic import BaseModel
from sqlalchemy.orm import Session

from infrastructure.data_access.database import SessionLocal
from infrastructure.persistence.repositories.postgres_user_repository import (
    PostgresUserRepository
)
from application.use_cases.create_user import CreateUser

router = APIRouter()


class CreateUserRequest(BaseModel):
    name: str
    email: str


def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()


@router.post("/users")
def create_user(
    request: CreateUserRequest,
    db: Session = Depends(get_db)
):
    repository = PostgresUserRepository(db)
    use_case = CreateUser(repository)
    user = use_case.execute(request.name, request.email)
    return {
        "id": str(user.id),
        "name": user.name,
        "email": user.email,
    }

7. نفهم العلاقة بين الملفات

دي أهم نقطة في المثال كله.

وقت تنفيذ Request

user_controller.py → create_user.py → user.py → user_repository.py → postgres_user_repository.py → user_mapper.py → models.py + database.py → PostgreSQL
  • user_controller.py — استقبال HTTP Request
  • create_user.py — تنفيذ Use Case
  • user.py — إنشاء Domain Entity
  • user_repository.py — Repository Interface
  • postgres_user_repository.py — تنفيذ الحفظ
  • user_mapper.py — Domain Entity إلى ORM Model
  • models.py + database.py — SQLAlchemy Model و Session
  • PostgreSQL — التخزين النهائي

الفرق بين Persistence و Data Access في المثال

الملف المسؤولية
postgres_user_repository.py تنفيذ عمليات الـ Repository
user_mapper.py تحويل Entity إلى ORM Model والعكس
database.py إعداد الاتصال والـ Sessions
models.py تعريف شكل جداول قاعدة البيانات
ملحوظة معمارية مهمة: التقسيم ده اختيار تنظيمي مناسب للمثال، مش قاعدة إلزامية في Clean Architecture. كمان المثال مبسط؛ في مشروع حقيقي ممكن نفصل Transaction Management عن Repository، ونتعامل مع أخطاء الـ Database وعمليات الـ Commit/Rollback بشكل مركزي.

الخلاصة: الـ Application بتحدد هي محتاجة إيه، والـ Infrastructure بتحدد هتنفذ الاحتياج ده إزاي، والـ FastAPI Controller بيربط الـ HTTP Request بالـ Use Case.
