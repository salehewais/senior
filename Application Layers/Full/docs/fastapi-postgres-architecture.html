2. Domain Layer

هنا هنحط الـ Business Rules والسلوك الخاص بالـ User.

domain/entities/user.py

from dataclasses import dataclass
from uuid import UUID, uuid4


@dataclass
class User:
    id: UUID
    name: str
    email: str

    @staticmethod
    def normalize_email(email: str) -> str:
        return email.strip().lower()

    @classmethod
    def create(cls, name: str, email: str):
        name = name.strip()
        email = cls.normalize_email(email)

        if not name:
            raise ValueError("Name is required")

        if "@" not in email:
            raise ValueError("Invalid email")

        return cls(
            id=uuid4(),
            name=name,
            email=email,
        )

    def change_email(self, new_email: str):
        new_email = self.normalize_email(new_email)

        if not new_email or "@" not in new_email:
            raise ValueError("Invalid email")

        self.email = new_email
ليه ده Domain Model؟ لأن User مش مجرد Data Structure بتحتوي على id وname وemail. هي كمان مسؤولة عن سلوكها وقواعدها: إنشاء User صالح، تطبيع الإيميل، وتغيير الإيميل مع التحقق من صلاحيته. لاحظ إننا مش بنستخدم هنا FastAPI أو SQLAlchemy أو PostgreSQL.

3. Application Layer

أولًا: Repository Interface — user_repository.py

from abc import ABC, abstractmethod

from domain.entities.user import User


class DuplicateEmailError(Exception):
    pass


class UserRepository(ABC):
    @abstractmethod
    def find_by_email(self, email: str) -> User | None:
        pass

    @abstractmethod
    def save(self, user: User) -> None:
        pass

ليه أضفنا find_by_email؟ لأن الـ Use Case محتاج يعرف هل الإيميل مستخدم بالفعل أم لا.

وليه عرفنا DuplicateEmailError هنا؟ ده استثناء ضمن العقد اللي الـ Repository بيقدمه للـ Application، بحيث الـ Application متضطرش تعرف تفاصيل أخطاء PostgreSQL.

ثانيًا: Create User Use Case — create_user.py

from domain.entities.user import User
from application.interfaces.user_repository import (
    UserRepository,
    DuplicateEmailError,
)


class CreateUser:
    def __init__(self, user_repository: UserRepository):
        self.user_repository = user_repository

    def execute(self, name: str, email: str) -> User:
        normalized_email = User.normalize_email(email)

        existing_user = self.user_repository.find_by_email(
            normalized_email
        )

        if existing_user:
            raise DuplicateEmailError("Email already exists")

        user = User.create(
            name=name,
            email=normalized_email,
        )

        self.user_repository.save(user)
        return user

هنا بنلاحظ الفصل المهم:

  • User.create() مسؤول عن قواعد إنشاء المستخدم.
  • CreateUser.execute() مسؤول عن تنسيق عملية الإنشاء.
  • UserRepository مسؤول عن توفير عمليات الوصول للمستخدمين من خلال abstraction.
ليه فحصنا تكرار الإيميل في Application؟ لأن التحقق هنا محتاج Repository عشان نعرف هل فيه User آخر بنفس الإيميل. دي مش خاصية يقدر User واحد يقررها بمفرده.

4. Infrastructure Layer

هنبدأ بـ Data Access وبعدها Persistence.

أولًا: Data Access — database.py

import os

from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker, DeclarativeBase

DATABASE_URL = os.getenv(
    "DATABASE_URL",
    "postgresql+psycopg://postgres:password@localhost:5432/mydb",
)

engine = create_engine(DATABASE_URL)
SessionLocal = sessionmaker(
    bind=engine,
    autoflush=False,
    expire_on_commit=False,
)


class Base(DeclarativeBase):
    pass

المسؤوليات:

  • engine: إعداد الاتصال بقاعدة البيانات.
  • SessionLocal: إنشاء SQLAlchemy Sessions.
  • Base: الأساس الذي سترث منه الـ ORM Models.

models.py

from uuid import UUID

from sqlalchemy import String, UniqueConstraint, Uuid
from sqlalchemy.orm import Mapped, mapped_column

from infrastructure.data_access.database import Base


class UserModel(Base):
    __tablename__ = "users"
    __table_args__ = (
        UniqueConstraint(
            "email",
            name="uq_users_email",
        ),
    )

    id: Mapped[UUID] = mapped_column(
        Uuid,
        primary_key=True,
    )
    name: Mapped[str] = mapped_column(
        String(100),
        nullable=False,
    )
    email: Mapped[str] = mapped_column(
        String(255),
        nullable=False,
    )

ده تمثيل جدول users في PostgreSQL باستخدام SQLAlchemy.

خلي بالك من الفرق:

  • User: Domain Entity.
  • UserModel: Database ORM Model.

مش نفس الـ Class ومش نفس المسؤولية.

ثانيًا: Persistence — Mapper — user_mapper.py

from domain.entities.user import User
from infrastructure.data_access.models import UserModel


class UserMapper:
    @staticmethod
    def to_model(user: User) -> UserModel:
        return UserModel(
            id=user.id,
            name=user.name,
            email=user.email,
        )

    @staticmethod
    def to_entity(model: UserModel) -> User:
        return User(
            id=model.id,
            name=model.name,
            email=model.email,
        )

الـ Mapper مسؤول عن التحويل بين الشكلين:

Domain Entity <--- Mapper <--- ORM Model

ثالثًا: Persistence — Repository — postgres_user_repository.py

from sqlalchemy import select
from sqlalchemy.exc import IntegrityError
from sqlalchemy.orm import Session

from domain.entities.user import User
from application.interfaces.user_repository import (
    UserRepository,
    DuplicateEmailError,
)
from infrastructure.data_access.models import UserModel
from infrastructure.persistence.mappers.user_mapper import UserMapper


class PostgresUserRepository(UserRepository):
    def __init__(self, session: Session):
        self.session = session

    def find_by_email(self, email: str) -> User | None:
        statement = select(UserModel).where(
            UserModel.email == email
        )
        model = self.session.scalar(statement)

        if model is None:
            return None

        return UserMapper.to_entity(model)

    def save(self, user: User) -> None:
        try:
            user_model = UserMapper.to_model(user)
            self.session.add(user_model)
            self.session.commit()
        except IntegrityError:
            self.session.rollback()
            raise DuplicateEmailError("Email already exists")

لاحظ إن الـ Repository هنا بيجمع بين:

  1. تنفيذ الـ Repository Interface.
  2. استخدام Mapper.
  3. استخدام SQLAlchemy Session.
  4. التعامل مع عملية الحفظ.
كمان فيه حماية من حالة الـ Race Condition: ممكن طلبين يحاولوا إنشاء نفس الإيميل في نفس اللحظة، وبالتالي فحص الـ Application وحده مش كفاية. الـ Unique Constraint في قاعدة البيانات هو الحماية النهائية.

5. Presentation Layer — FastAPI

presentation/api/user_controller.py

from fastapi import APIRouter, Depends, HTTPException
from pydantic import BaseModel
from sqlalchemy.orm import Session

from infrastructure.data_access.database import SessionLocal
from infrastructure.persistence.repositories.postgres_user_repository import (
    PostgresUserRepository,
)
from application.use_cases.create_user import CreateUser
from application.interfaces.user_repository import DuplicateEmailError

router = APIRouter()


class CreateUserRequest(BaseModel):
    name: str
    email: str


class UserResponse(BaseModel):
    id: str
    name: str
    email: str


def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()


@router.post("/users", response_model=UserResponse)
def create_user(
    request: CreateUserRequest,
    db: Session = Depends(get_db),
):
    repository = PostgresUserRepository(db)
    use_case = CreateUser(repository)

    try:
        user = use_case.execute(request.name, request.email)
    except DuplicateEmailError as exc:
        raise HTTPException(status_code=409, detail=str(exc))
    except ValueError as exc:
        raise HTTPException(status_code=422, detail=str(exc))

    return UserResponse(
        id=str(user.id),
        name=user.name,
        email=user.email,
    )

6. Main — تشغيل التطبيق

src/main.py

from contextlib import asynccontextmanager

from fastapi import FastAPI

from presentation.api.user_controller import router
from infrastructure.data_access.database import Base, engine
# Import model so SQLAlchemy registers its table
from infrastructure.data_access.models import UserModel


@asynccontextmanager
async def lifespan(app: FastAPI):
    Base.metadata.create_all(bind=engine)
    yield


app = FastAPI(lifespan=lifespan)
app.include_router(router)
create_all هنا للتجربة التعليمية فقط. في مشروع حقيقي استخدم Alembic لإدارة Database Migrations.

10. اتجاه الاعتماد بين الطبقات

Infrastructure → Application → Domain
  • Infrastructure تعتمد على Application لتنفيذ الـ Repository Interface.
  • Application تعتمد على Domain لاستخدام الـ Entities وقواعدها.
  • Domain لا تعتمد على أي طبقة خارجية.

أما وقت تنفيذ الطلب، فالتدفق بيكون:

HTTP Request → Controller → CreateUser → User Domain → UserRepository → PostgreSQL

الأسهم هنا بتوضح تدفق التنفيذ، مش اتجاه الـ Dependency.

ملاحظة مهمة: المثال الحالي بيطبق Domain Model بشكل مبسط، وليس DDD كاملًا. وchange_email() موجودة في الـ Domain لتوضيح السلوك، لكننا لم ننشئ Use Case لتغيير الإيميل أو Repository method لتحديثه؛ لأن السيناريو الحالي مقتصر على إنشاء المستخدم.

كده الفصل بقى واضح: الـ Domain يملك قواعد الـ Business، والـ Application تنسق تنفيذها، والـ Infrastructure تنفذ التفاصيل التقنية.
