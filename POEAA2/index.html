المرجع المنظم لـ Enterprise Application Patterns

خريطة عملية للأنماط اللي بتحدد فين تحط قواعد البزنس، وإزاي توصل للبيانات، وتدير الجلسات والتزامن — بأمثلة كود قصيرة.

أولًا: نفهم الخريطة قبل ما نحفظ أسماء الأنماط

تخيل إن العميل ضغط على زرار «تأكيد الطلب». العملية دي ممكن تمر بالمراحل التالية:

  1. 1
    استقبال الطلبWeb Presentation — Controller
  2. 2
    تنسيق العمليةService Layer
  3. 3
    تطبيق قواعد البزنسTransaction Script أو Domain Model
  4. 4
    قراءة البيانات وكتابتهاRepository / Data Mapper / Active Record
  5. 5

دي خريطة توضيحية وليست معمارية إلزامية. مش كل تطبيق لازم يحتوي على كل المكونات دي، ومش كل Pattern عبارة عن Layer مستقلة.

والأهم: الأنماط المذكورة في كتاب Patterns of Enterprise Application Architecture بتعالج مشكلات على مستويات مختلفة. هنفصل بينها بدل ما نعتبرها كلها بدائل لبعضها.

1. Domain Logic Patterns — فين نحط قواعد البزنس؟

خلينا نفترض أن العميل بيشتري منتجًا، وعندنا قواعد مثل:

  • مينفعش نبيع كمية أكبر من المتاح.
  • فيه خصم للعملاء المميزين.
  • إجمالي الطلب يساوي مجموع العناصر بعد الخصم.

السؤال هنا: هنكتب القواعد دي فين؟

1.1 Transaction Script

الفكرة: كل عملية أعمال لها إجراء واضح ينفذ خطواتها.

def place_order(customer_id, product_id, quantity, repository):
    product = repository.get_product(product_id)
    if product.stock < quantity:
        raise ValueError("Insufficient stock")
    total = product.price * quantity
    order = {
        "customer_id": customer_id,
        "product_id": product_id,
        "quantity": quantity,
        "total": total,
    }
    repository.save_order(order)
    repository.decrease_stock(product_id, quantity)
    return order

إيه اللي بيميزه؟

المنطق موجود في الإجراء نفسه، والخطوات متسلسلة بوضوح.

مناسب إمتى؟ لما تكون العمليات محددة وقواعد البزنس بسيطة نسبيًا.

المشكلة المحتملة: لو عندك عشرات العمليات وقواعد متداخلة، ممكن تكرر نفس القواعد في أماكن مختلفة.

ملحوظةملحوظة مهمة: الكود توضيحي؛ التنفيذ الإنتاجي محتاج Transaction مناسبة، والتحقق من المخزون وتحديثه بشكل آمن ضد الطلبات المتزامنة.

1.2 Domain Model

الفكرة: الكائنات نفسها تحمل بيانات المجال وسلوكه وقواعده.

class Order:
    def __init__(self, items):
        self.items = items
        self.status = "draft"

    def calculate_total(self):
        return sum(
            item.quantity * item.unit_price
        for item in self.items
        )

    def confirm(self):
        if not self.items:
            raise ValueError("Cannot confirm an empty order")
        if self.status != "draft":
            raise ValueError("Order is not in draft state")
        self.status = "confirmed"

هنا Order مش مجرد مجموعة بيانات؛ هو كمان مسؤول عن قواعد تخص الطلب نفسه.

الفرقالفرق عن Transaction Script: في الأول الإجراء هو مركز المنطق، وفي الثاني سلوك المجال موزع على كائنات المجال المناسبة.

مش كل قاعدة لازم تتحط في Order؛ مثلًا التحقق من توفر المخزون قد يحتاج خدمة أو كائنًا آخر يتعامل مع مصدر المخزون.

1.3 Table Module

الفكرة: كائن واحد يحتوي على سلوك ومنطق أعمال مرتبط بصفوف جدول أو View كامل، بدل ما يكون عندك كائن مجال مستقل لكل سجل.

class OrdersTableModule:
    def __init__(self, rows):
        self.rows = rows

    def total_for_customer(self, customer_id):
        return sum(
            row["total"]
        for row in self.rows
        if row["customer_id"] == customer_id
        )

المثال بيوضح الفكرة بصورة مبسطة؛ تطبيق النمط الفعلي يكون فيه منطق مرتبط ببيانات الجدول، وليس مجرد استعلام واحد.

مناسب إمتى؟ لما يكون نموذج البيانات قريبًا من الجداول، ومش محتاج Domain Model غني بكائنات مستقلة.

دورها الأساسي تنسيق العملية والتعامل مع حدود التطبيق، بينما قواعد المجال تفضل في المكان المناسب لها.

2. Data Source Architectural Patterns — إزاي نتعامل مع قاعدة البيانات؟

القسم ده مش بيسأل: «فين أحط قواعد البزنس؟»؛ هو بيسأل: إزاي أنظم الكود المسؤول عن الوصول إلى البيانات؟

هنستخدم جدول customers كمثال.

2.1 Table Data Gateway

كائن يوفر عمليات التعامل مع جدول كامل، زي البحث والإضافة والتعديل والحذف.

class CustomerTableGateway:
    def __init__(self, db):
        self.db = db

    def find_by_email(self, email):
        return self.db.fetch_one(
            "SELECT * FROM customers WHERE email = %s",
            [email],
        )

    def insert(self, name, email):
        return self.db.execute(
            "INSERT INTO customers (name, email) VALUES (%s, %s)",
            [name, email],
        )

لاحظ إن الكلاس مسؤول عن عمليات الجدول، مش بالضرورة عن تمثيل عميل واحد.

2.2 Row Data Gateway

هنا كل Gateway يمثل سجلًا معينًا، ويوفر عمليات الوصول إليه.

class CustomerRowGateway:
    def __init__(self, customer_id, db):
        self.customer_id = customer_id
        self.db = db

    def get_name(self):
        row = self.db.fetch_one(
            "SELECT name FROM customers WHERE id = %s",
            [self.customer_id],
        )
        return row["name"] if row else None

    def update_name(self, name):
        self.db.execute(
            "UPDATE customers SET name = %s WHERE id = %s",
            [name, self.customer_id],
        )
الفرقالفرق الأساسي: Table Data Gateway يتعامل مع عمليات على مستوى الجدول، بينما Row Data Gateway يركز على سجل محدد.

2.3 Active Record

الكائن يمثل سجلًا من قاعدة البيانات، ويحتوي عادةً على عمليات حفظه وتعديله وحذفه.

class Customer:
    def __init__(self, customer_id, name):
        self.id = customer_id
        self.name = name

    def save(self, repository):
        repository.update_customer(self.id, self.name)

المثال ده يوضح وجود سلوك للحفظ بجوار بيانات العميل، لكنه يستخدم Repository لتنفيذ التخزين؛ لذلك هو توضيح للفكرة وليس تطبيقًا حرفيًا كاملًا لـ Active Record.

في Active Record الفعلي، الكائن نفسه يوفر عادةً واجهة مثل save() وdelete() ويتولى تفاصيل الاستمرار عبر ORM أو آلية تخزين.

مثال عملي: نمط Active Record معروف في Django ORM من خلال نماذج مثل Customer.objects.create(...)، مع ملاحظة أن Django Model لا يطابق النمط حرفيًا في كل تفاصيله.

2.4 Data Mapper

هنا بنفصل كائن المجال عن تفاصيل قاعدة البيانات، ونستخدم مكونًا يحول بينهما.

class Customer:
    def __init__(self, customer_id, name):
        self.id = customer_id
        self.name = name


class CustomerMapper:
    def __init__(self, db):
        self.db = db

    def get_by_id(self, customer_id):
        row = self.db.fetch_one(
            "SELECT id, name FROM customers WHERE id = %s",
            [customer_id],
        )
        if row is None:
            return None
        return Customer(row["id"], row["name"])

هنا Customer لا يعرف SQL ولا يعرف كيف يتصل بقاعدة البيانات.

الفرق اللي يهمك

النمطالسؤال اللي بيجاوب عنه
Table Data Gatewayإزاي أنفذ عمليات على الجدول؟
Row Data Gatewayإزاي أتعامل مع سجل محدد؟
Active Recordإزاي الكائن يمثل السجل ويتولى استمراره؟
Data Mapperإزاي أفصل كائن المجال عن تفاصيل التخزين؟

خد بالك: Table Module من القسم الأول مختلف عن Table Data Gateway. الأول يهتم بمنطق الأعمال المرتبط بصفوف الجدول، والثاني يهتم بعمليات الوصول للبيانات.

3. Object-Relational Behavioral Patterns — إدارة تحميل وحفظ الكائنات

هنا بنتكلم عن السلوك الناتج عن التعامل مع كائنات موجودة في الذاكرة ومربوطة بقاعدة بيانات علائقية.

3.1 Unit of Work

المشكلةالمشكلة: أثناء تنفيذ عملية واحدة، ممكن تعدل عميلًا، وتنشئ طلبًا، وتعدل بيانات المخزون.

بدل ما يكون كل كائن مسؤولًا عن الحفظ بشكل مستقل، يمكن استخدام Unit of Work لمتابعة التغييرات وتنسيق كتابتها.

class UnitOfWork:
    def __init__(self, db):
        self.db = db
        self.new_objects = []
        self.dirty_objects = []
        self.deleted_objects = []

    def register_new(self, obj):
        self.new_objects.append(obj)

    def register_dirty(self, obj):
        self.dirty_objects.append(obj)

    def register_deleted(self, obj):
        self.deleted_objects.append(obj)

    def commit(self):
        with self.db.transaction():
            for obj in self.new_objects:
                obj.insert(self.db)
            for obj in self.dirty_objects:
                obj.update(self.db)
            for obj in self.deleted_objects:
                obj.delete(self.db)

ده هيكل توضيحي، مش تنفيذ كامل؛ مثلًا محتاج معالجة لإعادة المحاولة بعد الفشل، ومنع التكرار، وإدارة حالة الكائنات.

النقطة الدقيقة: Unit of Work لا يعني بالضرورة أن كل التغييرات تُكتب باستعلام SQL واحد. ممكن ينفذ استعلامات كثيرة داخل Transaction واحدة.

3.2 Identity Map

المشكلةالمشكلة: لو جبت العميل رقم 5 مرتين داخل سياق العمل نفسه، ممكن ينتهي بك الأمر بنسختين من كائن العميل، كل نسخة فيها قيم مختلفة.

الحل: خريطة تربط هوية الكائن بنسخة واحدة داخل السياق.

class CustomerIdentityMap:
    def __init__(self):
        self._objects = {}

    def get(self, customer_id):
        return self._objects.get(customer_id)

    def add(self, customer):
        self._objects[customer.id] = customer
الاستخدامالاستخدام:
customer = identity_map.get(5)
if customer is None:
    customer = mapper.get_by_id(5)
    if customer is not None:
        identity_map.add(customer)
الهدفالهدف الأساسي هنا اتساق هوية الكائن داخل السياق، وليس مجرد تسريع الاستعلامات.

وده قريب من الفكرة التي يعتمد عليها ORM عند الاحتفاظ بكائنات محمّلة داخل جلسة أو سياق عمل، مع اختلاف تفاصيل التنفيذ بين الأطر.

3.3 Lazy Load

المشكلةالمشكلة: العميل عنده آلاف الطلبات، لكن الشاشة الحالية محتاجة اسمه فقط.

بدل تحميل كل الطلبات من البداية، نؤجل تحميلها حتى تحتاجها.

class Customer:
    def __init__(self, customer_id, order_loader):
        self.id = customer_id
        self._order_loader = order_loader
        self._orders = None

    @property
    def orders(self):
        if self._orders is None:
            self._orders = self._order_loader(self.id)
        return self._orders

عند أول وصول إلى customer.orders، يتم التحميل، وبعدها يحتفظ المثال بالنتيجة داخل الكائن.

لكن خلي بالك من حاجتين:

  • ده مثال يدوي، بينما ORM قد يستخدم Proxy أو آلية أخرى لتنفيذ Lazy Loading.
  • لو كررت الوصول لعلاقات كثيرة داخل Loop، ممكن تقع في مشكلة N+1 Queries.

الفرق بينهم

  • Unit of Work: يتابع التغييرات وينسق حفظها.
  • Identity Map: يحافظ على نسخة الكائن المرتبطة بهويته داخل السياق.
  • Lazy Load: يؤجل تحميل البيانات حتى الحاجة إليها.

التلاتة ممكن يعملوا مع بعض في ORM واحد، لأن كل واحد بيحل مشكلة مختلفة.

4. Object-Relational Structural Patterns — إزاي نمثل الكائنات في الجداول؟

هنا بنحدد طريقة الربط بين نموذج الكائنات ونموذج قاعدة البيانات.

4.1 Identity Field

كل كائن يحتاج هوية مستقرة يمكن ربطها بسجل قاعدة البيانات.

class Customer:
    def __init__(self, customer_id, name):
        self.id = customer_id
        self.name = name

الخاصية id هنا بتمثل هوية العميل في التخزين.

4.2 Foreign Key Mapping

علاقة كائن بكائن آخر من خلال Foreign Key.

CREATE TABLE customers (
    id INTEGER PRIMARY KEY,
    name TEXT NOT NULL
);

CREATE TABLE orders (
    id INTEGER PRIMARY KEY,
    customer_id INTEGER NOT NULL REFERENCES customers(id)
);

كل طلب مرتبط بعميل من خلال customer_id.

4.3 Association Table Mapping

لعلاقة Many-to-Many، نستخدم جدولًا وسيطًا.

CREATE TABLE student_courses (
    student_id INTEGER REFERENCES students(id),
    course_id INTEGER REFERENCES courses(id),
    PRIMARY KEY (student_id, course_id)
);

الطالب ممكن يشترك في كورسات كثيرة، والكورس ممكن يكون فيه طلاب كثيرون.

4.4 Dependent Mapping

ده نمط مهم ومعناه أدق من مجرد إن الكائن الابن تابع للأب.

الفكرة: مسؤولية حفظ الكائن التابع تُدار من خلال Mapping الكائن الأب.

مثلًا، لما تحفظ Order، يقوم الـ Mapper الخاص بالطلب بحفظ OrderItem المرتبط به، بدل ما يحتاج كل عنصر طلب إلى مسار حفظ مستقل.

ده مختلف عن مجرد وجود Foreign Key أو قاعدة ON DELETE CASCADE؛ فالأخيرة آلية في قاعدة البيانات، بينما Dependent Mapping يصف مسؤولية الـ Mapping.

4.5 Embedded Value

عندك قيمة مركبة مثل العنوان، وتريد تخزينها داخل صف العميل بدل جدول مستقل.

CREATE TABLE customers (
    id INTEGER PRIMARY KEY,
    name TEXT NOT NULL,
    address_street TEXT,
    address_city TEXT,
    address_country TEXT
);

ده مناسب لو العنوان جزء من بيانات العميل ولا تحتاج إلى إدارته ككيان مستقل. لكن لو العنوان يُشارك بين كيانات، أو يحتاج دورة حياة مستقلة، فقد يكون جدولًا منفصلًا أنسب.

4.6 Serialized LOB

بدل تحويل كل تفاصيل كائن معقد إلى أعمدة منفصلة، يمكن تسلسل بياناته في حقل واحد.

{
  "theme": "dark",
  "language": "ar",
  "notifications": true
}

ممكن تخزنها في عمود JSON أو حقل نصي كبير.

لكن التخزين بهذه الطريقة له ثمن: الاستعلام عن الحقول الداخلية وفرض القيود عليها قد يصبح أصعب، بحسب نوع قاعدة البيانات وتصميم التخزين.

4.7 أنماط Mapping للوراثة

تخيل عندك Product، وتحته Book وMovie.

Single Table Inheritance

جدول واحد لكل الأنواع

products(id, type, name, author, director)

مناسب لما تحب تبسط عمليات القراءة، لكن قد يحتوي الجدول على أعمدة غير مستخدمة لكل نوع.

Class Table Inheritance

جدول للأب وجداول للأنواع الفرعية

products(id, name)، وbooks(id, author)، وmovies(id, director).

يفصل بيانات كل نوع، لكن قراءة كائن فرعي قد تتطلب JOIN.

Concrete Table Inheritance

جدول مستقل لكل نوع نهائي

books(id, name, author)، وmovies(id, name, director).

قد يكرر الأعمدة المشتركة، ويجعل الاستعلام الموحد عن كل المنتجات أصعب.

مفيش اختيار أفضل في كل الحالات؛ الاختيار يعتمد على شكل البيانات، وطبيعة الاستعلامات، وقيود قاعدة البيانات والـ ORM.

5. Object-Relational Metadata Mapping Patterns — وصف الـ Mapping وإدارة الوصول للكائنات

الفكرة هنا إنك بدل ما تكتب تفاصيل تحويل كل كائن لجدول في أماكن متفرقة، يكون عندك وصف واضح للعلاقة بين نموذج المجال والتخزين، وواجهات مناسبة للوصول إلى الكائنات.

5.1 Metadata Mapping

بدل ما تكتب SQL وتحويل البيانات يدويًا لكل كلاس، تصف الـ Mapping باستخدام Annotations أو XML أو إعدادات Fluent.

مثلًا في SQLAlchemy:

from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column
from sqlalchemy import String


class Base(DeclarativeBase):
    pass


class Customer(Base):
    __tablename__ = "customers"
    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(100))

الـ ORM يقرأ الـ metadata ويفهم إن Customer مرتبط بجدول customers، وإن id مفتاح أساسي.

ملحوظةملحوظة: Metadata Mapping يصف طريقة الربط، لكنه لا يفرض عليك استخدام Domain Model أو Active Record؛ دي قرارات منفصلة نسبيًا.

5.2 Query Object

الفكرة إنك تمثل الاستعلام نفسه في كائن مستقل، بدل ما يكون مجرد String مبعثر في الكود.

class PendingOrdersQuery:
    def __init__(self, customer_id):
        self.customer_id = customer_id

    def execute(self, db):
        return db.fetch_all(
            """
            SELECT id, total
            FROM orders
            WHERE customer_id = %s
              AND status = %s
            """,
            [self.customer_id, "pending"],
        )

الكائن هنا يمثل استعلامًا محددًا وقابلًا لإعادة الاستخدام.

لكن مش كل كلاس اسمه Query هو بالضرورة تطبيق مميز للنمط، ومش كل استخدام لـ filter() في ORM يعني أنك تستخدم Query Object.

5.3 Repository

ده النمط الناقص من المرجع الأصلي الذي لازم نضيفه.

الفكرة: توفير واجهة تشبه مجموعة من كائنات المجال، بحيث يتعامل المستهلك مع الكائنات بدل ما يعرف تفاصيل SQL أو الجداول.

class OrderRepository:
    def get_by_id(self, order_id):
        ...

    def add(self, order):
        ...

    def find_pending(self):
        ...

المستهلك يطلب طلبًا أو مجموعة طلبات، بينما التنفيذ يتولى طريقة الاسترجاع والحفظ.

الفرقالفرق عن Data Mapper:
  • Repository ينظم واجهة الوصول إلى كائنات المجال.
  • Data Mapper يحول بين كائنات المجال وتمثيلها في مصدر البيانات.

ممكن تستخدم Repository يعتمد على Data Mapper داخليًا.

متىإمتى تحتاج Repository؟ لما تحب تفصل منطق التطبيق عن تفاصيل الاستعلامات والتخزين، خصوصًا لو عندك Domain Model واضح. لكنه مش مطلوب تلقائيًا فوق كل ORM.

6. Web Presentation Patterns — استقبال الطلبات وعرض النتائج

القسم ده يخص كيفية التعامل مع طلبات المستخدم، وتنسيق البيانات، وإنتاج الواجهة.

6.1 Model–View–Controller (MVC)

  • Model: البيانات وسلوك المجال أو نموذج التطبيق، حسب الإطار.
  • View: تمثيل النتيجة للمستخدم.
  • Controller: يستقبل التفاعل أو الطلب، ويحدد كيفية تنسيق الاستجابة.

مثلًا، عند عرض منتج:

HTTP Request
↓
Product Controller
↓
Application / Model
↓
Product View
↓
HTTP Response

الـ MVC لا يحدد وحده أين يجب أن توجد كل قاعدة أعمال، ولا يعني أن أي كود داخل Controller خطأ؛ المهم مسؤولية الكود وتعقيده. لكن وضع كل قواعد البزنس داخل Controllers يجعل فصلها وإعادة استخدامها واختبارها أصعب غالبًا.

6.2 Page Controller

كل صفحة أو إجراء له معالج خاص به.

مثلًا:

GET /products/10 -> ProductPageController
GET /cart -> CartPageController
POST /checkout -> CheckoutController

المعالج هنا مسؤول عن طلب محدد أو صفحة محددة.

6.3 Front Controller

بدل ما يكون لكل طلب مدخل مستقل إلى النظام، تمر الطلبات عبر نقطة دخول مركزية، ثم يجري توجيهها للمعالج المناسب.

Requests
↓
Front Controller
→ Product Handler
→ Cart Handler
→ Checkout Handler

في كثير من تطبيقات الويب، يوجد Front Controller ضمن بنية الإطار نفسه، مثل آليات التوجيه المركزية.

الفرقالفرق: Front Controller يركز على المدخل المركزي، بينما Page Controller يركز على معالج صفحة أو إجراء محدد.

6.4 Template View

قالب يحتوي على هيكل العرض وأماكن تُملأ ببيانات متغيرة.

<h1>{{ product.name }}</h1>
<p>{{ product.price }}</p>

القالب مسؤول عن إخراج العرض، وليس عن تنفيذ دورة الشراء بالكامل.

6.5 Transform View

عرض يحول بيانات المجال إلى صيغة العرض المطلوبة، مثل HTML.

المهم في النمط هو التحويل من نموذج بيانات إلى تمثيل مناسب للعرض؛ استخدام XSLT لتحويل XML إلى HTML مجرد مثال ممكن.

6.6 Two Step View

إنتاج العرض يتم على مرحلتين:

  1. تحويل البيانات إلى تمثيل منطقي خاص بالصفحة.
  2. تحويل هذا التمثيل إلى HTML النهائي، مع تطبيق الشكل العام المشترك.

ده يساعد على توحيد شكل الصفحات، لكن مش معناه بالضرورة إن كل مشروع يستخدم Layout وHeader وFooter يطبق النمط حرفيًا.

6.7 Application Controller

يتولى تنسيق تدفق إجراءات التطبيق، خاصة عندما تكون العملية متعددة الخطوات أو تحتاج قواعد تحدد الخطوة التالية.

مثلًا:

Cart
↓
Address
↓
Payment
↓
Confirmation

قد يحدد النظام إن العميل يرجع إلى العنوان إذا فشل التحقق، أو ينتقل للدفع إذا اكتملت البيانات.

الـ Application Controller هنا مختلف عن Controller في MVC: الأول يركز على تنسيق تدفق التطبيق، والثاني على معالجة الطلبات والتفاعل مع النموذج والعرض.

7. Distribution Patterns — التواصل بين العمليات والخدمات

المشكلة هنا مش مجرد تنظيم الكود داخل التطبيق؛ بل تكلفة الاتصال عبر الشبكة بين عمليات مستقلة.

7.1 Remote Facade

تخيل إن تطبيق الموبايل محتاج بيانات لوحة تحكم العميل.

بدل عدة استدعاءات:

GET /customer/5
GET /customer/5/orders
GET /customer/5/payments

ممكن توفر عملية أكبر:

GET /customer/5/dashboard

العملية الثانية ترجع البيانات المطلوبة في استدعاء واحد، لو ده مناسب لطبيعة الاستخدام.

الفائدةالفائدة: تقليل عدد الاستدعاءات البعيدة، وتقديم واجهة مناسبة للعميل.

لكن مش معنى كده إننا نجمع كل شيء في Endpoint واحد ضخم؛ لازم نحافظ على حجم الاستجابة، والصلاحيات، والاعتمادية، واحتياجات كل عميل.

7.2 Data Transfer Object (DTO)

كائن مخصص لنقل البيانات بين حدود التطبيق أو العمليات.

from dataclasses import dataclass
from decimal import Decimal

@dataclass

class OrderDTO:
    id: int
    total: Decimal
    status: str

الـ DTO هنا لا يحتاج إلى معرفة كيفية حفظ الطلب في قاعدة البيانات.

الفرقالفرق المهم: الـ DTO ليس هو الـ Domain Model نفسه بالضرورة. ممكن يكون الـ Domain Model غنيًا بالسلوك، بينما DTO يحتوي فقط على البيانات المطلوبة للتواصل.

ووجود DTO لا يعني أنك تحتاج Remote Facade؛ ممكن تستخدم DTO وحده، وممكن تستخدم الاثنين معًا.

8. Offline Concurrency Patterns — التعامل مع التعارضات

هنفترض إن موظفًا فتح طلبًا لتعديله، وفي نفس الوقت موظف آخر عدّل الطلب وحفظه.

المشكلةالمشكلة: إزاي نمنع ضياع التعديلات أو تضاربها؟

8.1 Optimistic Offline Lock

لا نحجز السجل من البداية. نسمح بالعمل، ثم نتحقق عند الحفظ إن البيانات لم تتغير بطريقة تتعارض مع التعديل.

مثلًا، جدول الطلبات يحتوي على version:

UPDATE orders
SET total = 150, version = version + 1
WHERE id = 10 AND version = 3;

لو عدد الصفوف المتأثرة صفر، فقد يكون سجل الطلب غير موجود أو أن الإصدار تغير، وبالتالي نحتاج إلى التحقق من السبب والتعامل مع التعارض.

8.2 Pessimistic Offline Lock

نحجز البيانات منطقيًا لفترة العمل، بحيث لا تسمح العملية لمستخدم آخر بإجراء تعديل متعارض قبل تحرير الحجز.

قد تحتاج إلى تخزين:

  • هوية صاحب الحجز.
  • وقت انتهاء الحجز.
  • طريقة تحريره عند الإلغاء أو الفشل.

وده ليس بالضرورة نفس قفل الصف داخل PostgreSQL؛ لأن قفل قاعدة البيانات عادةً ينتهي مع الـ Transaction، بينما حجز الأعمال قد يمتد لفترة أطول.

8.3 Coarse-Grained Lock

بدل حجز كل كائن صغير بشكل مستقل، نحجز مجموعة مترابطة من الكائنات كأنها وحدة واحدة.

مثلًا، تعديل طلب معين قد يتطلب حجز الطلب نفسه وبعض البيانات التابعة له.

8.4 Implicit Lock

بدل ما يطلب كل جزء من التطبيق الحجز يدويًا، تتولى طبقة مشتركة أو إطار العمل تطبيق سياسة الأقفال تلقائيًا.

مقارنة سريعة:

النمطالاستراتيجية
Optimisticاكتشاف التعارض عند إتمام العملية
Pessimisticمنع التعديل المتعارض عن طريق حجز مسبق
Coarse-Grainedحجز مجموعة مترابطة كوحدة
Implicitإخفاء تفاصيل تطبيق القفل خلف آلية مشتركة

اختيار النمط يعتمد على احتمال التعارض، وتكلفة الفشل، وطول العملية. ومهم جدًا عدم الخلط بين هذه الأنماط وبين مستويات العزل في قواعد البيانات؛ فهما مفهومان مرتبطان لكنهما ليسا الشيء نفسه.

9. Session State Patterns — أين تعيش حالة المستخدم؟

خلينا نفصل بين ثلاثة أشياء مختلفة:

  1. Authentication: مين المستخدم؟
  2. Session State: إيه الحالة المرتبطة بجلسة استخدامه؟
  3. Persistent Business Data: إيه البيانات الدائمة مثل سلة محفوظة أو طلب مؤكد؟

الأنماط الثلاثة هنا بتتكلم عن مكان تخزين حالة الجلسة.

9.1 Client Session State

الحالة محفوظة عند العميل.

مثال: بعض تفضيلات العرض أو بيانات مؤقتة غير حساسة في المتصفح.

لكن البيانات الموجودة في المتصفح يمكن تعديلها من العميل، ولذلك لا تعتمد عليها وحدها في حساب السعر أو تقرير صلاحية عملية شراء.

9.2 Server Session State

الحالة محفوظة على السيرفر، والعميل يحتفظ عادةً بمعرف جلسة يشير إليها.

مثال:

Browser Cookie: session_id=abc123
↓
Server
↓
Redis Session

ميزة ده إن البيانات الفعلية تظل تحت تحكم السيرفر، لكنك تحتاج لإدارة انتهاء الجلسة، والتخزين المشترك بين الخوادم عند التوسع، وحماية معرف الجلسة.

9.3 Database Session State

حالة الجلسة تُخزن في قاعدة بيانات، بحيث يمكن الاحتفاظ بها واسترجاعها عبر عمليات تشغيل مختلفة وفقًا لسياسة الاحتفاظ.

لكن ليس كل سجل محفوظ في قاعدة البيانات هو Session State؛ مثلًا سلة مشتريات محفوظة ككيان دائم قد تكون جزءًا من بيانات المجال.

وJWT؟ هو Token يمكن أن يحمل معلومات عن الهوية والصلاحيات، لكنه لا يمثل تلقائيًا أيًا من أنماط تخزين حالة الجلسة الثلاثة.

10. Base Patterns — الأنماط الأساسية اللي بتتكرر في أكتر من مكان

القسم ده مهم لأنه يحتوي على مفاهيم بتستخدمها في تطبيقات Enterprise مختلفة، مش مجرد أنماط تخص الداتابيز أو الويب.

10.1 Gateway

كائن يغلف طريقة التعامل مع نظام خارجي أو مورد معقد.

مثال: عندك بوابة دفع خارجية، وعايز باقي التطبيق يتعامل مع واجهة بسيطة بدل تفاصيل HTTP وAPI Keys وصيغ الطلبات.

class PaymentGateway:
    def charge(self, amount, payment_token):
        # Call external payment provider
        ...
الهدفالهدف هو عزل تفاصيل التواصل مع الطرف الخارجي عن بقية التطبيق.

10.2 Service Stub

بديل مبسط لخدمة حقيقية أثناء الاختبار.

مثلًا، بدل ما تتصل ببوابة دفع فعلية كل مرة، تستخدم Stub يرجع نتيجة نجاح أو فشل متوقعة.

class FakePaymentGateway:
    def charge(self, amount, payment_token):
        return {"status": "success"}

ده مثال أقرب إلى Fake Test Double، بينما Service Stub بالمعنى الدقيق يوفر بديلًا مبسطًا لاستدعاء خدمة. المهم إنك لا تعتمد على الخدمة الخارجية في كل اختبار.

10.3 Mapper

مكون ينقل البيانات بين كائنين أو نموذجين مختلفين من غير ما يجعل كل واحد منهما مسؤولًا عن معرفة تفاصيل الآخر.

مثال: تحويل بيانات API إلى كائن داخلي في التطبيق.

def to_customer_dto(customer):
    return {
        "id": customer.id,
        "display_name": customer.name,
    }

ده مثال على وظيفة تحويل بسيطة؛ الـ Mapper كنمط أوسع قد يتعامل مع نماذج كائنات مستقلة.

10.4 Layer Supertype

كلاس أساسي مشترك لكائنات تنتمي إلى طبقة معينة، بحيث يجمع السلوك أو الوظائف المشتركة بينها.

لكن وجود Base Class لا يعني إنك لازم تحط فيه كل الوظائف المشتركة؛ لو الوظائف غير مترابطة، قد يكون استخدام Composition أنسب.

10.5 Separated Interface

تفصل تعريف الواجهة عن تنفيذها، بحيث يستطيع مكون آخر الاعتماد على الواجهة من غير الارتباط المباشر بحزمة التنفيذ.

مثلًا، منطق الطلبات يعتمد على PaymentGateway كواجهة، بينما التنفيذ الحقيقي يتصل بمزود دفع معين.

10.6 Registry

يوفر نقطة معروفة للوصول إلى مجموعة من الخدمات أو الكائنات المسجلة.

لكن الـ Registry العام قد يخلق اعتمادًا خفيًا ويصعّب الاختبارات، لذلك مش بديلًا تلقائيًا عن Dependency Injection.

10.7 Value Object

كائن تتحدد مساواته بالقيم التي يحملها، وليس بمعرف مستقل.

مثلًا، مبلغ مالي مكوّن من قيمة وعملة:

from dataclasses import dataclass
from decimal import Decimal

@dataclass(frozen=True)
class Money:
    amount: Decimal
    currency: str

في المثال ده، مبلغ 100 EGP يساوي مبلغًا آخر بنفس القيمة والعملة، بصرف النظر عن كونهما كائنين مختلفين في الذاكرة.

10.8 Money

نمط مخصص لتمثيل الأموال بطريقة تراعي القيمة والعملة والعمليات المالية.

مثلًا، جمع 100 EGP مع 50 USD لا يصح من غير تحويل للعملة وفق قواعد واضحة.

استخدام Decimal بدل float مهم عادةً للحسابات المالية، لكنه وحده لا يكفي لتنفيذ نظام مالي دقيق.

10.9 Special Case

بدل ما تكرر شروط التعامل مع حالة خاصة في أماكن متعددة، تمثل الحالة بكائن يوفر سلوكًا مناسبًا.

مثال: بدل ما كل جزء من التطبيق يتحقق إن العميل غير موجود، يمكن إرجاع كائن UnknownCustomer بسلوك محدد، إذا كان ده مناسبًا لتصميم النظام.

لكن مش كل حالة غير موجودة تحتاج إلى Special Case؛ أحيانًا None أو استثناء واضح أبسط وأصح.

10.10 Plugin

يسمح باختيار تنفيذات مختلفة أثناء الإعداد أو التشغيل، بدل ربط النظام بتنفيذ واحد ثابت.

مثلًا، التطبيق يستخدم مزود دفع محليًا في بيئة الاختبار، ومزودًا آخر في الإنتاج.

11. إزاي الأنماط دي تشتغل مع بعض في مشروع حقيقي؟

هنجمع أهم الأفكار في عملية واحدة: تأكيد طلب شراء.

  1. 1
    العميل يرسل الطلبMVC / Front Controller / DTO — يستقبل السيرفر الطلب ويتحقق من شكل البيانات وصلاحيات الوصول.
  2. 2
    بدء عملية الأعمالService Layer + Transaction Script أو Domain Model — تُنسق الخطوات، وتُطبق قواعد الطلب والمخزون.
  3. 3
    قراءة البيانات وتعديلهاRepository / Data Mapper / Identity Map — يتم استرجاع الكائنات المطلوبة وتحديثها وفق تصميم التخزين.
  4. 4
    ضمان صحة العمليةUnit of Work + Transaction + Concurrency Control — تُكتب التغييرات ضمن حدود المعاملة المناسبة، مع التعامل مع التعارضات.
  5. 5
    التواصل مع بوابة الدفعGateway / Remote Facade / DTO حسب الحاجة — يُستدعى النظام الخارجي باستخدام واجهة مناسبة، مع مراعاة فشل الشبكة والتكرار الآمن للطلبات.

ده نموذج توضيحي، مش قائمة مكونات لازم تنفذها كلها. مثلًا، الدفع الخارجي يحتاج تصميمًا إضافيًا للتعامل مع نجاح الدفع وفشل حفظ الطلب؛ لأن Transaction محلية في PostgreSQL لا تجعل العملية الخارجية جزءًا من نفس المعاملة تلقائيًا.

12. الخريطة النهائية للمراجعة

القسمالسؤال الأساسيأهم الأنماط
Domain Logicأين وكيف أنفذ قواعد الأعمال؟Transaction Script, Domain Model, Table Module, Service Layer
Data Sourceكيف أنظم الوصول إلى البيانات؟Table Data Gateway, Row Data Gateway, Active Record, Data Mapper
OR Behavioralكيف أتابع وأحمّل وأحفظ الكائنات؟Unit of Work, Identity Map, Lazy Load
OR Structuralكيف أمثل الكائنات وعلاقاتها في الجداول؟Identity Field, Foreign Key Mapping, Embedded Value, Inheritance Mappers
OR Metadata Mappingكيف أصف الربط وأوفر واجهة للوصول إلى الكائنات؟Metadata Mapping, Query Object, Repository
Web Presentationكيف أستقبل الطلبات وأنتج العرض؟MVC, Page Controller, Front Controller, Template View
Distributionكيف أنقل البيانات وأقلل الاتصالات البعيدة؟Remote Facade, DTO
Offline Concurrencyكيف أتعامل مع تعارضات التعديل؟Optimistic Offline Lock, Pessimistic Offline Lock

التصنيف ده ملخص لأهم الأنماط التي ناقشناها، وليس فهرسًا كاملًا لكل الأنماط الفرعية الموجودة في الكتاب.

13. أهم حاجة بالنسبة لك كمطور Odoo وPython

ما تحاولش تحفظ كل Pattern كأنه مطلوب منك تنفذه يدويًا في كل مشروع. الأفضل إنك تقدر تعمل ثلاث حاجات:

  1. تتعرف على النمط: لما تشوف الكود، تفهم هو بيحل أي مشكلة.
  2. تحدد المسؤولية: تفرق بين قواعد البزنس، وتنسيق العملية، والوصول للبيانات، وإدارة المعاملات.
  3. تختار بناءً على المشكلة: مش بناءً على إن النمط مشهور أو إن المعمارية تبدو أكثر تعقيدًا.

مثلًا، في Odoo، الـ ORM بيوفر بالفعل آليات للتعامل مع الكائنات والسجلات والتخزين المؤقت وإدارة المعاملات. مش معنى إنك درست Unit of Work أو Identity Map إنك لازم تبني تنفيذًا خاصًا بهما فوق Odoo.

الخطوة الأهم بعد فهم المرجع: دراسة الفروق العملية بين الأنماط المتشابهة، خصوصًا:

  • Transaction Script مقابل Domain Model.
  • Service Layer مقابل Domain Service.
  • Repository مقابل Data Mapper مقابل Active Record.
  • Unit of Work مقابل Database Transaction.
  • Identity Map مقابل Cache.
  • MVC مقابل Layered Architecture.
  • Gateway مقابل Remote Facade.

دول أكثر الفروق اللي هتساعدك تستخدم الأنماط في تصميم الأنظمة بدل ما تكتفي بمعرفة تعريفاتها.
