01

DBMS introduction

Database and DBMS

A database is the organised store of data. A DBMS (Database Management System) is the software that lets users create, manipulate, and administer that store: keep it secure, retrieve it quickly, change it, and add new data when needed.

Library picture

Books sit shelf-by-shelf by subject, so you walk straight to the C-Programming rack instead of digging through every pile. The library catalog works like a DBMS index: it makes searching easy.

Why a DBMS is needed

A DBMS keeps data consistent, lets many users work at once, enforces security, and can restore data after a failure (backups and recovery).

Separate spreadsheets

If every college department kept its own Excel file, the same student’s name, phone, and address would be copied again and again. Admissions might update the address while the Fees sheet still has the old one, so the copies no longer match.

Main advantages

Security

Decide exactly who can view or change which data.

A fee clerk sees only names and fee status. The principal’s login also shows marks. Nobody else can quietly peek at everything.

No extra copies

Store data once, in a structured way. Controlled copies (indexes) may still exist for speed.

A student’s address lives in one Student table. Admissions, Exams, and Fees all read that copy, so they see the same up-to-date address.

Accuracy — ACID

Every update is all-or-nothing and stays valid.

  • Atomicity — all or nothing.
  • Consistency — data stays valid.
  • Isolation — concurrent work does not interfere.
  • Durability — committed changes survive crashes.

Issuing a library book writes “Issued = Yes” and “Available copies = total − 1” together. If power fails mid-update, the DBMS rolls the whole action back.

Speed — indexing

B-trees give O(log n) search for ranges. Hash indexes give O(1) for exact matches.

A librarian types a student ID and the index jumps to that row instead of scanning thousands of rows.

Growth — scalability

Grow vertically (more resources on one machine) or horizontally (more servers) with little change to the application.

If the college admits five times as many students, attach more storage or compute. Existing queries keep working.

Popular database types

TypeDefinitionUse caseReal-life picture
Relational (SQL) Tables with a defined schema, linked by primary and foreign keys, with ACID guarantees. Highly structured tasks. UPI transfers: each transfer records debit and credit atomically as one transaction.
Document Schema-flexible JSON/BSON documents, with optional field checks. Flexible menus or profiles. Swiggy menus: a restaurant’s JSON can add a field such as spice level without a schema change.
Key-value Distributed hash tables with collision handling. A key retrieves a value. Ultra-fast look-ups. Flipkart session storage: temporary browsing history, not the transactional cart.
Graph Nodes (people or things) and edges (links). Connections and networks. Fraud detection: accounts linked by shared devices or IPs, such as a ring of fake profiles.
Time-series Time-stamped data (sensor logs, stock ticks) with fast time-range scans. Sensors and stock prices. An IMD weather station stores temperature every minute to spot heat waves.
Object-oriented Software objects stored as they are, attributes and behaviour together. Embedded or niche apps. A medical device saves each sensor object with its current status, ready to reload.
  • Choose the database for the problem, not for popularity.
  • SQL is a language. Many non-relational databases also accept SQL-like queries.

Why might Flipkart use a key-value store for user sessions, while UPI requires a relational database?

02

Architecture

The architecture of a database system describes where each software piece lives and how the pieces talk to each other. That layout decides performance, security, and how far the system can grow.

One-tier, two-tier, and three-tier

ArchitectureDesignExampleWhat to notice
One-tier The user interface and the database engine run on the same machine. A student runs a Python script with SQLite. The app and the database share one process. Setup is instant, but the system is single-user and uses a lot of local resources.
Two-tier A client application talks directly to a dedicated database server, often through ODBC or JDBC. Lab PCs run a Java GUI that connects straight to a central MySQL server for lab grades. Many users get better performance than one-tier, but clients reach the database server directly.
Three-tier The client talks to an application server, which queries the database. A mobile app calls a REST API (for example Node.js). That middle tier authenticates and queries PostgreSQL. Business logic and security sit in the middle. The database stays shielded. Clients stay light, and the API can scale without holding session state.

Distributed databases

A distributed database stores pieces of the data on two or more servers in different places, yet presents them as one logical database.

Three campuses

An educational trust with campuses in Delhi, Mumbai, and Bengaluru keeps each city’s attendance on a local server so lookups stay fast. Records sync either asynchronously (eventual consistency) or through distributed transactions (strong consistency), depending on what the trust needs.

CAP theorem

In a distributed system, partition tolerance is mandatory. The real trade-off is between consistency and availability.

Consistency (C)

Every node shows the same data at a given moment.

Availability (A)

Every request gets a timely answer. That answer might not be the newest data.

Partition tolerance (P)

The system keeps working when nodes cannot talk to each other.

ScenarioTwo propertiesWhy
UPI mess-wallet payments Consistency + Availability Money transfers must never diverge, even if a partition causes a short delay. The system may block a transaction during a partition to prevent double-spending. A brief outage can be tolerated.
Digital notice-board website Availability + Partition tolerance Showing an older notice is better than the board going dark during a Wi-Fi outage.
Intra-college coding-contest scoreboard Availability + Consistency Partitions are rare on the campus LAN, so participants expect scores that are both current and instantly visible.

03

Data abstraction

Data abstraction hides how data is stored (file formats, indexes, block layout) and shows users only the structures and operations they need. Separating how data is stored from what it means improves security, flexibility, and maintenance.

Three levels

LevelDefinitionCollege example
Physical Exact location in bytes on disk: file structures, indexes, and data blocks. Attendance is stored as 8 KB blocks on SSD, with RAID-1 mirroring. A B-tree maps roll number to block addresses. Students never see this.
Logical The whole database as tables, columns, data types, and relationships. A Students table has Roll No (primary key), Name (VARCHAR), and a foreign key to Courses. Constraints enforce referential integrity. This is what faculty mean when they write SQL.
View A custom logical subset for a particular user. The warden sees Roll No, Name, and a computed FeeStatus. The examination branch sees Roll No, Name, and semester marks.

Each higher level is insulated from changes at the level beneath it. The ladder runs physical (lowest) → logical → view (highest). Knowledge flows upward. Changes should flow downward.

Data independence

TypeDefinitionExample
Logical independence Change the logical schema without rewriting application programs. The college splits Address into Street, City, and Pin Code. The hostel fee system and the attendance app need no code changes, because their views are adjusted.
Physical independence Change storage without affecting the logical schema. IT moves attendance from HDDs to faster SSDs and adds an index on Date. Faculty and student SQL stays the same.
  • Full data independence is hard. Even partial independence cuts maintenance cost a lot.
  • In daily student life, mobile apps show the view level, developers design the logical level, and the physical level stays in the server room.

Think about it

How did Instagram’s logical schema and physical storage have to change as the product grew from photo sharing to Stories, Reels, and DMs — and which of those changes could stay hidden from the app?

Data models

A data model is the formal grammar for how facts are organised inside a database. The model you pick affects performance, flexibility, and how hard the system is to maintain.

ModelCore structureIdeal for
HierarchicalParent → child treeOne-to-many chains
NetworkRecords linked by several parent–child sets (many-to-many)Complex associations
RelationalTables, rows, and columns, joined by keysGeneral-purpose data
Object-orientedPersistent programming objectsComplex, behaviour-rich data
Entity–relationship (ER)A diagram of entities and relationshipsThe conceptual design stage

Hierarchical

A strict top-down tree. Each child has exactly one parent.

University → College → Department → Course → Student. A query for “CSE, 2022 batch” follows the path from the root to the leaves.

Network

A record may have several parents, so many-to-many links are natural.

A student links to several clubs. Each club links to many students and to several events. Finding everyone at a coding marathon means walking those linked sets.

Relational

Two-dimensional tables. Primary and foreign keys enforce relationships. Queries use SQL.

STUDENT (roll no, name, programme), COURSE (code, title, credits), MARKS (roll no, code, grade). Joins let the exam section publish marksheets.

Object-oriented

Classes are stored as defined in an object-oriented language, attributes and methods together.

In a robotics database, each Robot object stores arrays of Sensor objects. Fetching a robot brings the associated objects with it.

Entity–relationship

A picture-first map of reality into entities, attributes, and relationships, drawn before physical implementation.

Designers draw Student, Course, and Instructor, with relationships ENROLLED_IN and TAUGHT_BY. That map later guides the relational tables.

05

ER model

The ER model is a conceptual blueprint, not an implementation. It names entities, attributes, and relationships so a real-world situation can become a database design.

Terms

TermDefinitionExample
EntityA strong entity (Student) has its own unique key. A weak entity (Dependent) needs a strong entity to be identified.One student, or one particular course offering.
AttributeA property of an entity.Roll number (key), student name (simple), course credits (derived from hours).
Entity setA collection of similar entities.Every student enrolled in the university.
RelationshipA logical association among entities.A student ENROLLED_IN a course.
Relationship setAll instances of a relationship. Binary (two entity sets) or ternary (three).All student–course enrolments, or Student ↔ Course ↔ Instructor.

Notation

Rectangle

Entity set. A strong entity is a single rectangle. A weak entity is a double rectangle. The partial key uses a dashed underline (bed number in Occupancy).

Ellipse

Attribute. Double ellipse: multivalued (phone numbers). Dashed ellipse: derived (age). Underlined name: primary key.

Diamond

Relationship set. An identifying relationship of a weak entity uses a double diamond (Hostel Room → Occupancy).

Line

Connects the shapes. Cardinality marks sit on the line.

  • 1:1 — |──| — Student ↔ Library Card.
  • 1:N — |──< — Department → Students.
  • M:N — >──< — Students ↔ Courses.

Cardinality and participation

SymbolMeaningExample
1:1Each entity links to exactly one on the other side.A library card must belong to one student (total on the card side). A student might have no card if it was lost (partial on the student side).
1:NOne entity may relate to many on the other side.One instructor teaches many courses. Each course has exactly one instructor that semester.
M:NMany relate to many. In a relational design this becomes an associative table.ENROLLMENT with composite key (StudentID, CourseID).

Total participation: every entity must take part. Every library card is assigned to a student.

Partial participation: some entities stay out. Not every student joins a club.

Weak entities

A weak entity has no primary key of its own. It is identified by a strong owner plus a partial key. When the owner is deleted, the dependent rows should be deleted too (cascading delete).

Hostel occupancy

Owner: Hostel Room (room No). Weak entity: Occupancy, partial key bed Number (dashed underline), identifying relationship drawn as a double diamond.

Generalization

Generalization builds a superclass–subclass hierarchy and keeps shared attributes on the superclass. It combines lower-level entities into a higher one by collecting what they have in common (“many become one”).

[PERSON]
   /    \
[STUDENT]  [INSTRUCTOR]

STUDENT and INSTRUCTOR inherit name from PERSON. STUDENT adds programme and roll number. INSTRUCTOR adds department and salary. A campus email list reads only PERSON. A programme query reads only STUDENT.

Specialization

Specialization splits a superclass into subclasses that are exclusive or overlapping. It may be total (every entity belongs to a subclass) or partial (some entities belong to none). Distinct features are pushed downward (“one becomes many”).

[STUDENT]  [INSTRUCTOR]
       \      /
       [PERSON]

PERSON holds name and address. STUDENT holds programme and roll number. INSTRUCTOR holds department and salary. The same query rule applies: everyone uses PERSON; programme-specific questions use STUDENT alone.

Aggregation

Aggregation treats a relationship, together with the entities in it, as one higher-level unit so that unit can itself take part in another relationship.

Project submission

The exam cell wants to know which projects were submitted. A submission needs a student, a project, and a faculty guide, joined by WORKS_ON. Instead of linking all three separately to Submission Status, wrap WORKS_ON and its entities in a dashed box labelled Project Submission, then link that box to Submission Status.

A relationship, not a standalone entity. Attribute: RANKING (1st to watch, 2nd, …). Connects PROFILE ↔ MOVIE: one profile, many movies.

Attributes: ACTOR_ID (primary key), FIRSTNAME, LASTNAME. ACTOR — (1:N) — AWARD, with optional participation. Connected to MOVIE by Starred_by.

A relationship. Attribute: CHARACTER_NAME (for example 'Tony Stark'). Connects ACTORS ↔ MOVIE.

06

Relational model

Every relational database — a college ERP or a canteen app — follows the same four-part grammar. Understand the parts and the rules that protect them, and the tables can hold marks, fees, and attendance without losing them.

Keep the ladder in mind: Domain → Attribute → Tuple → Relation.

Building blockDefinitionExample
Domain The set of legal values for a column, including constraints. Roll-number domain: any 8-digit integer from 21000000 to 21999999. In SQL: RollNo INT CHECK (RollNo BETWEEN 21000000 AND 21999999).
Attribute One column. Every value comes from one domain. RollNo INT, Name VARCHAR(30), Programme CHAR(10), MobileNo CHAR(10).
Tuple One complete row about exactly one real-world item. Values are atomic (1NF): split Name into FirstName and LastName rather than packing both into one cell. One student’s roll number, name, programme, and mobile number.
Relation The whole table: many tuples under the same columns. The STUDENT table of everyone enrolled this year.

Schema and instance

Schema (intention)

The stable structure: table name, attributes, domains, and constraints. It does not change when a student joins or leaves.

STUDENT (roll_no INT PRIMARY KEY, name VARCHAR(30), programme CHAR(10), mobile_no VARCHAR(10))

Think of the empty worksheet template.

Instance (extension)

The rows sitting in the table right now. Tomorrow’s instance may have new students, or fewer if someone drops out.

Think of the worksheet after the marks have been filled in.

 Each row is a tuple. Each column is an attribute with its own domain.

Integrity constraints

Key constraint

Every table has at least one candidate key: a column or column set that uniquely identifies each row and never repeats. A key may be one column (RollNo) or composite (StudentID, CourseID).

Roll number is unique. Inserting the same roll number twice is rejected.

Entity integrity

A primary-key column cannot contain NULL. An empty roll number would leave a row that nobody can identify.

Referential integrity

A foreign key must match an existing primary key in the referenced table. NULL is allowed only when the relationship is optional.

MARKS.Roll No references STUDENT.Roll No. Uploading marks for roll number 22109999 fails if that student is not in STUDENT.

07

Keys

A key is one or more columns that pick out a single exact row. Without keys, duplicates creep in and a query can return the wrong student, the wrong mark, or both.

Every primary key is a candidate key, and every candidate key is a super key. The reverse is not true.

KeyDefinitionExample
Super keyAny column set that uniquely identifies rows. Extra columns are allowed.{rollNo, mobileNo}, {rollNo}, {email}.
Candidate keyA minimal super key. Drop any column and it stops being unique.{rollNo} or {email}. Each stands alone.
Primary keyThe one candidate key the DBA chooses as the official row identifier.The college chooses rollNo for STUDENT.
Alternate keyAny remaining candidate key. Often indexed for faster lookup.Search by email.
Composite keyA key built from two or more columns. As a candidate key it is minimal.MARKS {rollNo, courseCode} identifies one grade.
Foreign keyA column set that points at the primary (or alternate) key of another table.MARKS.rollNo → STUDENT.rollNo and MARKS.courseCode → COURSE.code.

Worked tables

Foreign-key check

Inserting roll number 22109999 into MARKS fails when that roll number is missing from STUDENT.

Checks used in exams

  • Minimality. Drop one column from the key. If the rest no longer identifies the row, the key was minimal.
  • NULL rule. In a composite primary key, no column may be NULL. A foreign key may be NULL when the relationship is optional.
  • Composite vs super. A composite candidate key is a minimal multi-column key. A super key is any unique column set, and it may include columns that are not needed for uniqueness.
08

Normalisation

Normalisation splits large, unstructured tables into smaller related tables so the same fact is not stored over and over. That removes update anomalies and keeps the data consistent.

Functional dependency

X → Y means: if two tuples agree on attribute set X, they must agree on attribute set Y. Y is functionally dependent on X.

Example: Roll No → Student Name. The same roll number never belongs to two different names.

DependencyRelationExample
Full X → Y, and Y depends on every attribute in X. For any proper subset A of X, A does not determine Y. Grade needs both Roll No and Course ID (CS101). Neither alone is enough.
Partial X → Y where X is a composite key AZ, and a proper subset A already determines Y. Student Name depends only on Roll No, not on Course ID. Partial dependencies violate 2NF, so Student Name moves to a STUDENT table.
Trivial X → Y where Y is a subset of X. Roll No, Name → Name. If you already know the name, you know the name.
Non-trivial X → Y where Y is not a subset of X. Roll No → Dept_Name. The department is determined by the roll number, and it is not part of the roll number itself.
Transitive A → C is transitive when it comes from A → B and B → C. Roll number determines department, and department determines building. Changing a department’s building would otherwise mean updating every student row.
Multivalued A →→ B and A →→ C, with B and C independent of each other. Roll No →→ Hobbies and Roll No →→ Sports. Hobbies and sports vary independently.

1NF through BCNF

FormIn shortRuleCollege illustration
1NF One value per cell Every cell holds one atomic value. No repeating groups. Store each course on its own row. Do not put “CS101, MA102” in one cell.
2NF Whole key, not a part 1NF, and no partial dependency on a composite key. If the key is {roll No, course Code}, student Name (depends only on roll No) must move to another table.
3NF No transitive chain 2NF, and no transitive dependency. Every non-prime attribute depends only on a super key. In COURSE, course Code → instructor ID and instructor ID → instructor Name. Move instructor details out.
BCNF Left side must be a key For every FD X → Y, X must be a super key. Stronger than 3NF. If instructor ID → course Code also holds, make a TEACHES table so both sides are keys: TEACHES(Instructor ID, Course Code).

Lossless join and dependency preservation

Lossless join

After you split a table, joining the pieces must recreate the original rows exactly: no extras, no missing rows.

Dependency preservation

Every original functional dependency can still be enforced without joining the tables back together.

Textbook decompositions aim for both. BCNF sometimes forces a choice: keep the lossless join, and give up perfect dependency preservation.

Boyce–Codd normal form

Rule: in every functional dependency X → Y, X itself must be a candidate key.

Under the usual college rule — one instructor teaches many courses — every dependency already has a candidate key on the left, so the schema is in BCNF.

If the college instead required “an instructor teaches exactly one course” (instructor ID → course Code), BCNF would break. The fix is an associative table TEACHES (instructor ID, course Code) so both resulting tables satisfy BCNF.

Final BCNF set for the common “one instructor, many courses” rule:

  • STUDENT (roll No PK, student Name, programme)
  • INSTRUCTOR (instructor ID PK, instructor Name)
  • COURSE (course Code PK, course Name, credits, instructor ID FK)
  • RESULT (roll No FK, course Code FK, grade) with primary key roll No + course Code

Joins are lossless. Grade stays tied to student plus course, and instructor stays tied to course, without stitching the tables back together on every update.

09

Denormalisation

Denormalisation deliberately adds controlled redundancy so common queries can skip expensive joins. The normalised tables remain the source of truth.

  1. Combine normalised tables vertically (fewer tables).
  2. Add derived columns horizontally (pre-computed values).
  3. Create materialised views (saved query results).

When it helps

Heavy read, light write

The placement dashboard shows current CGPA often, and updates it once a semester. Skipping the join of STUDENT and RESULT on every page load is worth a stored copy.

Aggregates used again and again

The canteen prints a monthly mess bill from daily swipes, then reuses that total all month. Pre-storing the total saves thirty daily sums.

Star schema for reports

The annual NAAC report wants student, course, and programme in one query. A wider table makes the analytics query simpler and faster.

Usual motives: speed, simpler code, easier analytics, or a slow network between servers.

Trade-off numbers

MetricNormalisedDenormalisedImpact
Read performance100 ms per join10 ms flat10× faster
Write performance5 ms20 ms, plus sync4× slower
Storage100 GB150–300 GB+50–200%
ConsistencyImmediateEventual (batch)Risk of stale copies

Pros: fewer joins, faster SELECTs, simpler BI queries, lower CPU on a busy server.

Cons: repeated data uses storage, extra columns can go stale (update anomalies), and triggers or batch jobs must keep the copies in sync.

Denormalise only after measuring that joins are the real bottleneck.

During result season the exam branch must list roll number, name, programme, course name, credits, instructor name, and grade for 5,000 students every hour.

Pain point

The report joins STUDENT × RESULT × COURSE × INSTRUCTOR. At about 20 ms per row × 5,000 rows, that is 100 seconds.

Pre-computed mess balance

Normalised set: SWIPE (student ID, date, amount) — thousands of rows a month — and STUDENT (student ID, name, programme).

Helper table: MESS_BALANCE (student ID PK, month, total amount). The kiosk reads the balance instead of summing every swipe on the spot.

Safe use

  • Measure first. Use EXPLAIN and look at real query times.
  • Touch only the hot paths. Leave the rest normalised.
  • Refresh automatically: triggers, materialised views, or a nightly sync.
  • Document which fields are copies and which table owns the truth.
  • Keep a rollback plan if storage or update cost gets out of hand.
10

Transactions and concurrency

A transaction is a small, complete job the database treats as one package. Like a registered parcel: the courier delivers the whole parcel or brings it back, never half of it.

Publish Result

Three steps belong together: insert the new grade for every subject, recalculate each CGPA, and set “Result Published = YES”. If power fails after step 1, the database also undoes step 1, so grades and CGPA cannot clash.

ACID

PropertyPromiseWhat it coversScenario
Atomicity All or nothing. The whole transaction succeeds or fails together, including crashes, constraint violations, and deadlocks. Power fails during a fee payment. Neither account is updated. The log shows the attempt.
Consistency Database rules hold. Primary keys, foreign keys, and CHECK constraints are valid before and after, even if several transactions run together or the system fails mid-way. A student transfer keeps department quotas valid. No student exists without a department.
Isolation Transactions do not interfere. Isolation levels from Read Uncommitted up to Serializable, each blocking a known set of anomalies. Two teachers grade the same paper. Serializable makes one wait. Read Committed may show an intermediate state.
Durability Committed work survives crashes. Write-ahead logging (WAL), synchronous replication, and checksum verification. After a crash, grades are recovered from the WAL. No submission is lost.

Pros: data stays correct, recovery reaches the last commit, and many users can run transactions together safely.

Cons: logging and locking add overhead, the engine is harder to build, and strict ACID across many servers needs distributed consensus.

Life cycle

ACTIVE

SQL statements are running.

PARTIALLY COMMITTED

The last statement has finished. The database is flushing log records.

COMMITTED

The success message has gone to the user. The job is permanent.

ABORTED

An error happened. The database undoes every change and returns to the original state.

Schedules

Serial

Run transaction 1 completely, then transaction 2. Always safe. Users wait longer because nothing overlaps.

Interleaved

Mix the steps: T1, T2, T1, and so on. Better CPU use, faster for many users. Rules are required so the result still matches some serial order.

A serializable schedule is a safe interleaving: the final result matches some serial execution.

FlavourTestExample
Conflict-serializable Build a precedence graph of who uses the same data. No cycle means the schedule is safe. T1 writes a CGPA and T2 later reads it. The edge is T1 → T2. No loop means the schedule is safe.
View-serializable Same final values and the same “first read” data as some serial run. It is a superset of conflict-serializability. Blind writes (a write without a prior read) can still pass. Marks and attendance end up identical to some serial run, even if individual operations would not commute.

Recoverability ladder

Serializable decides order. Recoverability decides when a transaction may commit. Strict means “hands off my data until I am done.”

  • Recoverable. If T2 read data written by T1, T2 may commit only after T1 commits. Otherwise T2 would depend on data that might roll back.
  • Cascading. Reading uncommitted data is allowed. If T1 aborts, every T2 and T3 that touched T1’s dirty writes must abort too — a domino effect.
  • Cascadeless (ACA). A transaction may read only committed data. No domino of aborts, but another transaction may still overwrite uncommitted data.
  • Strict. Nobody may read or write a value T1 changed until T1 commits or aborts. No dirty reads and no dirty writes. Most real systems get this from Strict Two-Phase Locking (S2PL).
  • Non-recoverable — avoid it. T2 reads T1’s uncommitted value and commits before T1. If T1 later aborts, T2’s bad data is stuck. Exam keyword: dirty commit.

Three anomalies, hostel version

PhenomenonWhat happensHostel twist
Dirty read T1 changes fees and has not committed. T2 reads the change. If T1 rolls back, T2 saw fake data. A senior sets Mess Bill = ₹0 while testing. You look before Undo and leave thinking you owe nothing.
Non-repeatable read T1 reads a row twice. T2 commits an update between the reads, so the value differs. At 10 AM the list shows Room 101. After lunch the warden moves you to Room 202. At 2 PM the list says 202.
Phantom read T1 selects rows matching a condition. T2 inserts a new qualifying row and commits. T1’s rerun shows an extra row. You list students with 85%+ attendance to plan a trip. While you book the bus, two friends clear their backlog and appear when you refresh.

Conflict-serializability test

Serializability means concurrent transactions leave the database as if they had run one after another, in some order.

  1. Draw a node for each transaction.
  2. Draw an arrow Ti → Tj when Ti writes a row and Tj later reads or writes that same row.
  3. If the graph has no loops, the schedule is safe.

Ananya’s grade

T1 writes the grade. T2 later reads it. An arrow from T1 to T2, with no path back, means there is no loop.

Why concurrency control

On result day, teachers, students, and placement staff hit the database together. Without control they can read half-updated data, overwrite each other, or deadlock. The rules keep the data safe and the system quick.

  • Banking: deposits and withdrawals stay accurate under simultaneous access.
  • E-commerce: no double booking and no inventory mistakes.
  • Social media: consistent data while many people interact at once.
  • Reservations: availability stays accurate and overbooking is prevented.

Techniques

Locking

A shared (S) lock lets many transactions read, and nobody write. An exclusive (X) lock lets one transaction read and write; everyone else waits.

Two-phase locking (2PL)

Growing phase: take every lock you need. Shrinking phase: release locks, and take no new ones. No lock after a release guarantees serializability. Strict 2PL holds locks until commit or abort.

Teacher T1 takes an X-lock on (roll 22104567, CS101) to change the grade. Placement office T2 asks for an S-lock on the same row and waits until T1 commits, then reads the final mark.

Timestamp ordering

Each transaction gets a timestamp at the start. If two fight over a row, the older timestamp wins; the newer one waits or rolls back. This suits many reads and few writes, such as students refreshing RESULT_FLAT while teachers rarely update grades.

Optimistic control

Assume clashes are rare. Transactions read without locks. At commit the database checks for conflicts and, if it finds one, rolls a transaction back to restart. Suitable for read-heavy reports that change infrequently.

Race conditions, deadlocks, and lock_timeout

Race condition

Two transactions touch the same data, and the final result depends on which one happens to run first. Without a lock or a version check, one update can erase the other.

Two fee clerks both read a balance of 1000 and both subtract 200. Each writes 800. One payment disappears. A lock makes the second clerk wait, then subtract from 800.

Deadlock

A cycle of waits. T1 holds Ananya’s grade row and waits for her fee row. T2 holds the fee row and waits for the grade row. Neither can move.

The DBMS searches for that cycle. After deadlock_timeout (often about one second) it aborts one transaction, the victim, and lets the other continue. The aborted transaction can be retried.

lock_timeout

How long one statement will wait to obtain a lock before it gives up. A wait can be long even when there is no cycle, because the other transaction is simply still working.

deadlock_timeout decides when to look for a wait cycle. lock_timeout decides when to stop waiting at all. A lock timeout can fire while only one other transaction holds the row.

SET lock_timeout = '2s';
UPDATE marks
SET grade = 9.1
WHERE roll_no = 22104567;

If that grade row is still locked after two seconds, the UPDATE stops with a lock-timeout error instead of waiting.

Recovery

Recovery puts the database back after a crash, a software fault, or a human error, so admissions and exam results can run again.

Failures: a single transaction (logic error or constraint), the whole system, the storage media, or a natural disaster.

Backup and restore

Regular copies of the database. Daily attendance backups can be loaded if the live system crashes.

Log-based recovery

A log of every operation. The fee portal’s log either finishes a payment or cancels it, so nothing is duplicated or lost.

Shadow paging

A backup page exists while the new page is written. A profile update keeps the old consistent copy until the new one is saved.

Checkpoint

A snapshot at a known time. Course registration saved every 15 minutes only has to replay the last 15 minutes after a crash.

Rollback and rollforward

Rollback undoes uncommitted work. Rollforward reapplies committed operations from the log. A scholarship form that fails mid-way is rolled back; once fixed, successful applications are rolled forward.

  • Back up often, and keep a copy off site (admission data on a cloud server outside campus).
  • Practice a restore so you know it works.
  • Automate recovery so fewer steps depend on a person.

Many DBMSs also offer snapshot isolation and MVCC (multi-version concurrency control). Each reader sees a consistent snapshot, so readers and writers block each other less.

The optimizer is the planner. It does not run the query. It turns a query tree into one plan tree: the sequence of scans and joins it believes is cheapest. Bad statistics or a hidden index produce a confident, slow plan.

B-tree and B+-tree

  • B-tree: keys in internal nodes guide the search. Leaves hold keys and row pointers.
  • B+-tree (what most DBMSs use): every key is copied into the leaves, and the leaves are linked left to right. A range such as CGPA BETWEEN 8 AND 9 is a short walk along that chain.

Internal nodes are like a library guide that points at the right drawer. The drawer is the leaf that holds the record.

Scale up and scale out

Vertical (scale-up)

A bigger machine: more RAM, faster SSDs, more CPUs. Like adding RAM sticks to the library PC.

Horizontal (scale-out)

More machines, with data split or copied across them. Like opening three fee-payment desks instead of one.

Sharding

Sharding splits a large database into smaller independent pieces, each on its own host. Lookups stay local. A university chain keeps Delhi on Server-A and Mumbai on Server-B. Only a cross-campus query touches both.

  • Shard: one independent partition, such as one department’s student records.
  • Shard key: the column that decides the destination, such as Branch.
  • Shared-nothing: each shard runs on its own, without sharing disk or memory.
MethodHowTrade-off
RangeRoll numbers 1–1000 go to shard 1.Simple. Data can pile up unevenly.
HashA hash of Admission ID picks the server.Even spread. Adding or removing a shard means moving data, though consistent hashing limits how much.
DirectoryA lookup table maps Course ID to a department server.Flexible. A wrong or stale map sends rows to the wrong shard.
GeoDelhi students go to the Delhi server, with failover to Mumbai.Low latency for nearby users. Dense cities can still overload one shard.

Choose a shard key with many distinct values (cardinality), avoid a few extremely popular keys (hotspots), and avoid a key that only grows in one direction, such as a sequential timestamp, because new writes all land on the latest shard.

A poor shard key

Sharding feedback by “courses completed” (11 or more courses → shard C) overloads shard C as students progress.

RBAC

Role-based access control attaches permissions to roles, not to individual people.

  • Student → SELECT marks, pay fees.
  • Faculty → INSERT and UPDATE marks for their own courses.
  • Admin → full rights.

Roll number 22104567 inherits Student rights on first login. The rules stay short and easy to audit.
