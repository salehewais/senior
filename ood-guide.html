ما هو OOD؟
Object-Oriented Design

OOD هو منهجية تصميم البرمجيات اللي بتبني النظام على أساس كائنات (Objects) بدل ما تبنيه على functions أو procedures. كل object بيمثل حاجة من العالم الحقيقي وعنده بيانات (data) وسلوك (behavior).

🎯 الهدف من OOD

تحويل المتطلبات (requirements) إلى نموذج تصميم واضح بيحدد الكلاسات وعلاقاتها قبل ما تكتب أي كود.

🔑 المفهوم الأساسي

كل شيء في النظام هو object — سواء كان user أو order أو payment — وكل object مسؤول عن نفسه.

📐 الفايدة

كود أسهل في الفهم، الصيانة، والتوسيع. بتقدر تعدّل جزء من النظام من غير ما تكسر الباقي.

🌍 التطبيق

مستخدم في Java, C++, C#, Python, Ruby, Swift وكل اللغات الحديثة تقريباً.

الـ Getters & Setters

بتتحكم في إزاي الـ data تتقرأ أو تتعدّل. ممكن تضيف validation جوا الـ setter بدل ما تسمح بالتعديل المباشر.

TypeScript
class BankAccount {
  private balance: number = 0;     // ❌ لا يُقرأ من برّا مباشرة
  private pin: string;

  constructor(pin: string) {
    this.pin = pin;
  }

  public deposit(amount: number): void {
    if (amount <= 0) throw new Error("Amount must be positive");
    this.balance += amount;           // ✅ التحقق قبل التعديل
  }

  public getBalance(): number {
    return this.balance;              // ✅ قراءة آمنة بدون تعديل
  }

  public withdraw(amount: number, pin: string): void {
    if (pin !== this.pin) throw new Error("Wrong PIN");
    if (amount > this.balance) throw new Error("Insufficient funds");
    this.balance -= amount;
  }
}

// الاستخدام
const acc = new BankAccount("1234");
acc.deposit(500);
console.log(acc.getBalance());  // 500
// acc.balance = 9999; ❌ Error! private field
✅
الفايدة الأساسية: لو غيّرت الـ implementation من جوا مش هتأثر على أي حاجة بتستخدم الكلاس — طالما الـ public interface مش اتغيّر.
🧬
الوراثة: الكلاس الابن (child) بياخد خصائص وسلوك الكلاس الأب (parent) تلقائياً. بتعيد استخدام الكود وبتبني عليه.

TypeScript
class Animal {                               // Parent class
  constructor(public name: string) {}

  eat(): void  { console.log(`${this.name} is eating`); }
  sleep(): void { console.log(`${this.name} is sleeping`); }
  move(): void  { console.log(`${this.name} is moving`); }
}

class Dog extends Animal {                  // Child class — يرث من Animal
  constructor(name: string, public breed: string) {
    super(name);                             // استدعاء constructor الأب
  }

  bark(): void  { console.log("Woof!"); }  // سلوك خاص بـ Dog
  fetch(): void { console.log("Fetching..."); }

  move(): void {                             // Override لسلوك الأب
    console.log(`${this.name} runs on 4 legs`);
  }
}

class Cat extends Animal {
  purr(): void   { console.log("Purr..."); }
  climb(): void  { console.log("Climbing..."); }
}

const dog = new Dog("Rex", "Labrador");
dog.eat();     // ✅ موروثة من Animal
dog.bark();    // ✅ خاصة بـ Dog
dog.move();    // ✅ overridden — "Rex runs on 4 legs"

console.log(dog instanceof Animal); // true — Dog IS an Animal
⚠️
Favor Composition over Inheritance: الوراثة العميقة بتعمل coupling قوي. لو الـ hierarchy وصلت لأكتر من 3 مستويات، فكّر في استخدام Composition بدلها.
🎭
تعدد الأشكال: نفس الـ interface بيتصرف بشكل مختلف حسب الـ object. بتكتب كود عام بيشتغل مع أنواع مختلفة.
🗣️لما بتقول "اتكلم!" للكلب بيعوي، للقطة بتموأ، للببغاء بيتكلم. نفس الأمر، نتيجة مختلفة حسب الكائن — ده هو Polymorphism.
Runtime Polymorphism

القرار بيتاخد وقت تشغيل البرنامج. بيحصل عن طريق Method Overriding. الأكثر شيوعاً في OOD.

Compile-time Polymorphism

القرار بيتاخد وقت الـ compilation. بيحصل عن طريق Method Overloading — نفس الاسم، parameters مختلفة.

TypeScript
// ─── Runtime Polymorphism (Method Overriding) ───
abstract class Shape {
  abstract area(): number;
  describe(): void {
    console.log(`Area = ${this.area().toFixed(2)}`);  // نفس الكود لكل shape
  }
}

class Circle extends Shape {
  area() { return Math.PI * this.radius ** 2; }
  constructor(private radius: number) { super(); }
}

class Rectangle extends Shape {
  area() { return this.w * this.h; }
  constructor(private w: number, private h: number) { super(); }
}

class Triangle extends Shape {
  area() { return 0.5 * this.base * this.height; }
  constructor(private base: number, private height: number) { super(); }
}

// ✅ نفس الكود بيتعامل مع كل الأنواع
const shapes: Shape[] = [
  new Circle(5),
  new Rectangle(4, 6),
  new Triangle(3, 8),
];
shapes.forEach(s => s.describe());
// Area = 78.54
// Area = 24.00
// Area = 12.00

// ─── Compile-time Polymorphism (Overloading) ───
class Calculator {
  add(a: number, b: number): number;
  add(a: string, b: string): string;
  add(a: any, b: any) { return a + b; }   // نفس الاسم، سلوك مختلف
}
✅
الفايدة العملية: مش محتاج تكتب if (animal instanceof Dog) ... else if (animal instanceof Cat) ... — بيتعامل مع كل الأنواع بنفس الكود.
🎨
التجريد: بتحدد الـ "إيه" من غير ما تقول الـ "إزاي". بتعمل واجهة (interface) أو abstract class تحدد الشكل العام.
🚗لما بتوصّل سيارة بتعرف إن فيه دركسيون وبنزين وكبح — مش محتاج تعرف إزاي المحرك بيشتغل جوا. بتتعامل مع الـ interface مش الـ implementation.
Abstract Class

كلاس مش ممكن تعمل منه object مباشرة. بيحدد blueprint للـ subclasses. ممكن يكون فيها implemented methods وأيضاً abstract methods.

Interface

عقد (contract) بيحدد الـ methods اللي لازم أي كلاس ينفذها. مفيش implementation خالص. كلاس واحد ممكن ينفذ أكتر من interface.

TypeScript
// ─── Abstract Class ───
abstract class DatabaseConnection {
  protected isConnected = false;

  abstract connect(): void;          // لازم كل ابن ينفذها
  abstract disconnect(): void;       // لازم كل ابن ينفذها
  abstract query(sql: string): any[]; // لازم كل ابن ينفذها

  executeQuery(sql: string) {          // ✅ implementation مشتركة
    if (!this.isConnected) this.connect();
    return this.query(sql);
  }
}

class MySQLConnection extends DatabaseConnection {
  connect()    { console.log("MySQL connected"); this.isConnected = true; }
  disconnect() { console.log("MySQL disconnected"); }
  query(sql: string) { /* MySQL-specific implementation */ return []; }
}

class PostgreSQLConnection extends DatabaseConnection {
  connect()    { console.log("PostgreSQL connected"); this.isConnected = true; }
  disconnect() { console.log("PostgreSQL disconnected"); }
  query(sql: string) { /* PostgreSQL-specific */ return []; }
}

// ─── Interface ───
interface Serializable {
  serialize(): string;
  deserialize(data: string): void;
}

interface Printable {
  print(): void;
}

class User implements Serializable, Printable {  // ✅ أكتر من interface
  serialize() { return JSON.stringify(this); }
  deserialize(data: string) { Object.assign(this, JSON.parse(data)); }
  print() { console.log(this); }
}

Classes & Objects
اللبنة الأساسية في OOD

الـ Class هو blueprint أو template. الـ Object هو instance حقيقي منه. زي الفرق بين خرائط البيت (class) والبيت نفسه (object).

Class

تعريف — بيحدد الـ attributes والـ methods. موجود بس في الكود، مش في الـ memory.

Object

instance حقيقي من الـ class. بياخد مساحة في الـ memory ومالو state خاصة بيه.

TypeScript — Class Anatomy
class Car {
  // ─── Properties (Fields) ───
  static totalCars: number = 0;         // static — مشترك بين كل الـ instances
  public  brand: string;
  private speed: number = 0;
  protected year: number;
  readonly vin: string;                  // لا يتغير بعد الإنشاء

  // ─── Constructor ───
  constructor(brand: string, year: number) {
    this.brand = brand;
    this.year  = year;
    this.vin   = generateVIN();
    Car.totalCars++;
  }

  // ─── Methods ───
  accelerate(amount: number): void {
    this.speed = Math.min(this.speed + amount, 200);
  }

  brake(): void {
    this.speed = Math.max(this.speed - 10, 0);
  }

  // ─── Getter / Setter ───
  get currentSpeed() { return this.speed; }
  get isMoving()     { return this.speed > 0; }

  // ─── Static Method ───
  static getTotalCars() { return Car.totalCars; }

  // ─── toString ───
  toString() { return `${this.brand} (${this.year}) — ${this.speed}km/h`; }
}

// إنشاء objects
const car1 = new Car("Toyota", 2023);
const car2 = new Car("BMW", 2024);

car1.accelerate(80);
console.log(car1.toString());     // Toyota (2023) — 80km/h
console.log(Car.getTotalCars());  // 2

Relationships بين Classes
Association · Aggregation · Composition · Inheritance · Realization

العلاقات هي الروابط بين الـ classes. تحديد نوع العلاقة الصح هو من أهم قرارات التصميم.

Association
A → B
Weak link

A يعرف B — علاقة عامة. مش فيه ownership. الـ objects ممكن تعيش مستقلة. ممكن تكون one-to-one أو one-to-many أو many-to-many.

Teacher → Student — المدرس بيعرف الطلاب لكن لو المدرس راح الطلاب مش بيتأثروا.
Aggregation
A ◇─ B
Has-a (weak)

A يحتوي B — لكن B ممكن يعيش من غير A. الـ ownership موجودة لكن مش حصرية. "part-of" relationship بدون lifecycle dependency.

Department ◇─ Professor — لو القسم اتحذف الأستاذ بيفضل موجود.
Composition
A ◆─ B
Has-a (strong)

A يحتوي B — ولو A مات B مات معاه. الـ ownership حصرية والـ lifecycle مشترك. أقوى نوع من الـ containment.

House ◆─ Room — لو البيت اتهدم الأوض مش موجودة. أو Order ◆─ OrderItem.
Inheritance
A ◁── B
Is-a

B هو نوع من A — الـ subclass بيرث كل خصائص وسلوك الـ parent. أقوى نوع coupling. الابن هو الأب ولكن بزيادة.

Car is-a Vehicle — Manager is-a Employee — AdminUser is-a User.
Realization
A ◁ - - B
Implements

B بينفذ الـ interface A. A بيحدد الـ contract وB بيحقق هذا الـ contract. بتستخدمها للـ interface implementation.

Dog implements IAnimal — EmailService implements INotifiable.
TypeScript — كل العلاقات في مثال واحد
// Association — Driver يعرف Car
class Driver {
  constructor(private car: Car) {}        // reference بس
  drive() { this.car.accelerate(60); }
}

// Aggregation — Team يحتوي Players (لو Team اتحذف Players فاضلين)
class Team {
  private players: Player[] = [];
  addPlayer(p: Player) { this.players.push(p); }
  removePlayer(p: Player) { /* يمشي من الـ team بس لسه موجود */ }
}

// Composition — Order يحتوي OrderItems (Order مات = items ماتت)
class Order {
  private items: OrderItem[] = [];
  addItem(productId: string, qty: number) {
    this.items.push(new OrderItem(productId, qty));  // Order بيخلق الـ items
  }
}

// Inheritance — Manager is-a Employee
class Employee { work() { console.log("Working..."); } }
class Manager extends Employee {
  manage() { console.log("Managing team..."); }
}

// Realization — EmailService implements INotifiable
interface INotifiable {
  notify(msg: string): void;
}
class EmailService implements INotifiable {
  notify(msg: string) { console.log(`Email sent: ${msg}`); }
}

SOLID Principles
الـ 5 مبادئ الأساسية للتصميم الجيد

SOLID هو اختصار لـ 5 مبادئ وضعها Robert C. Martin. أي كود بيطبّق الـ SOLID بيكون أسهل في الفهم والصيانة والتوسيع.

S
Single Responsibility Principle — SRP
كل كلاس المفروض يكون ليه سبب واحد بس للتغيير. يعني كل كلاس بيعمل حاجة واحدة بس وبيعملها كويس.
لو وصفت وظيفة الكلاس واحتجت تستخدم "و" — ده علامة إنه بيعمل أكتر من حاجة وبيخرق الـ SRP.
Bad vs Good
// ❌ BAD — UserManager بيعمل كل حاجة
class UserManager {
  createUser()    { /* DB logic */ }
  sendEmail()     { /* Email logic */ }
  generateReport(){ /* Report logic */ }
  validateInput() { /* Validation */ }
}

// ✅ GOOD — كل كلاس مسؤول عن حاجة واحدة
class UserRepository  { create() {} find() {} }
class EmailService     { send() {} }
class ReportGenerator  { generate() {} }
class UserValidator    { validate() {} }
O
Open/Closed Principle — OCP
الكلاس لازم يكون مفتوح للـ extension (ممكن تضيف features) ومغلق للـ modification (مش محتاج تغيير الكود الموجود).
لو كل ما أضفت feature جديدة احتجت تعدّل كلاسات موجودة — ده بيخرق الـ OCP وبيرفع خطر الـ bugs.
Bad vs Good
// ❌ BAD — كل payment type جديد بيعدّل calculateFee
class PaymentProcessor {
  calculateFee(type: string) {
    if (type === "credit") return 0.03;
    if (type === "debit")  return 0.01;
    // كل payment جديد = تعديل في الكود = خطر
  }
}

// ✅ GOOD — كل payment type هو extension مستقل
interface PaymentMethod { calculateFee(): number; }

class CreditCard implements PaymentMethod { calculateFee() { return 0.03; } }
class DebitCard  implements PaymentMethod { calculateFee() { return 0.01; } }
class Crypto     implements PaymentMethod { calculateFee() { return 0.005; } }
// ✅ أضفنا Crypto من غير ما نعدّل أي كود موجود!
L
Liskov Substitution Principle — LSP
الـ subclass لازم يقدر يحل محل الـ parent class من غير ما يكسر النظام. ما ينفعش الابن يلغي أو يتجاهل سلوك الأب.
لو عندك if (obj instanceof Subclass) في الكود — ده علامة خطر إن الـ LSP اتخرق.
Bad vs Good
// ❌ BAD — Square بيخرق سلوك Rectangle (LSP violation)
class Rectangle {
  setWidth(w: number)  { this.width = w; }
  setHeight(h: number) { this.height = h; }
}
class Square extends Rectangle {
  setWidth(w: number)  { this.width = this.height = w; } // 💥 كسر السلوك!
  setHeight(h: number) { this.width = this.height = h; } // 💥
}

// ✅ GOOD — Shape مستقل لكل شكل
abstract class Shape { abstract area(): number; }
class Rectangle2 extends Shape {
  constructor(private w: number, private h: number) { super(); }
  area() { return this.w * this.h; }
}
class Square2 extends Shape {
  constructor(private side: number) { super(); }
  area() { return this.side ** 2; }
}
I
Interface Segregation Principle — ISP
الكلاس ما لازمش يتبع interface فيها methods مش محتاجها. أحسن تعمل interfaces صغيرة ومتخصصة بدل interface كبيرة.
لو كلاس بينفذ interface وبيخلّي methods فاضية أو بيرمي exceptions — ده بيخرق الـ ISP.
Bad vs Good
// ❌ BAD — Interface كبيرة جداً
interface IWorker {
  work(): void;
  eat(): void;
  sleep(): void;
}
class Robot implements IWorker {
  work() { console.log("Working"); }
  eat()  { throw new Error("Robot doesn't eat!"); }  // 💥 ISP violated
  sleep(){ throw new Error("Robot doesn't sleep!"); } // 💥
}

// ✅ GOOD — interfaces صغيرة ومتخصصة
interface IWorkable  { work():  void; }
interface IFeedable  { eat():   void; }
interface ISleepable { sleep(): void; }

class HumanWorker implements IWorkable, IFeedable, ISleepable {
  work() {} eat() {} sleep() {}   // ✅ كل الـ methods منطقية
}
class RobotWorker implements IWorkable {
  work() {}                          // ✅ بس اللي محتاجه
}
D
Dependency Inversion Principle — DIP
الـ modules العالية (high-level) ما لازمش تعتمد على الـ modules الدنيا (low-level) مباشرة. الاتنين لازم يعتمدوا على abstractions.
اعتمد على interfaces وabstract classes، مش على concrete implementations. ده بيسهّل الـ testing والـ swap.
Bad vs Good
// ❌ BAD — UserService مربوط بـ MySQLDB مباشرة
class MySQLDB    { save(data: any) {} }
class UserService {
  private db = new MySQLDB();         // 💥 tight coupling!
  createUser(data: any) { this.db.save(data); }
}

// ✅ GOOD — UserService تعتمد على interface
interface IDatabase { save(data: any): void; }

class MySQLDB2    implements IDatabase { save(d: any) { /* MySQL */  } }
class MongoDB      implements IDatabase { save(d: any) { /* MongoDB */ } }
class InMemoryDB   implements IDatabase { save(d: any) { /* Testing */  } }

class UserService2 {
  constructor(private db: IDatabase) {}  // ✅ Dependency Injection
  createUser(data: any) { this.db.save(data); }
}

// ✅ في production نستخدم MySQL، في tests نستخدم InMemory
const service = new UserService2(new MySQLDB2());
const testSvc  = new UserService2(new InMemoryDB());
✂️
Other Design Principles
DRY · KISS · YAGNI · Cohesion · Coupling · SoC · Composition · Interfaces · Boy Scout

غير الـ SOLID، في مبادئ تانية مهمة بتشكّل طريقة تفكير المصمم الجيد.

🔁 DRY — Don't Repeat Yourself

كل معلومة أو logic لازم يكون في مكان واحد بس في النظام. لو نفس الكود موجود في أكتر من مكان — ده violation.

💡
الحل: Extract الكود المتكرر في function أو class مشترك.
💋 KISS — Keep It Simple, Stupid

الحل الأبسط دايماً أفضل. مقاومة إغراء over-engineering. الـ complexity الزيادة بتقتل الـ maintainability.

💡
لو الكود صعب تشرحه لزميلك — ده علامة إنه معقد أوي.
🚫 YAGNI — You Aren't Gonna Need It

ما تبنيش حاجة إلا لما تحتاجها فعلاً. لا تضيف features "على المستقبل" من غير requirement حقيقي.

⚙️ CoC — Convention over Configuration

اتبع الـ conventions المتعارف عليها بدل ما تعمل configuration لكل حاجة. بيقلل الـ decisions المطلوبة.

📦 LoD — Law of Demeter

"Talk only to your immediate friends." الكلاس ما يتكلمش إلا مع الـ objects اللي بيعرفها مباشرة. يقلل الـ coupling.

🧩 Low Coupling · High Cohesion

Low Coupling: الـ classes تعتمد على بعض بأقل قدر ممكن — تغيير كلاس واحد ما يكسرش الباقي. High Cohesion: كل class أو module بيجمع logic مرتبط ببعض في مكان واحد وبيعمل شغلة واحدة كويس.

💡
الهدف: modules مستقلة وواضحة — سهل تختبرها وتعدّلها من غير ripple effects.
🔓 SoC — Separation of Concerns

كل جزء من النظام مسؤول عن concern واحدة بس: UI، business logic، data access، logging. مثال: الـ UI ما يتكلمش مع الـ Database مباشرة — في layer بينهم.

💡
SoC غالباً بيتحقق بـ layers أو modules (MVC، Clean Architecture).
🧱 Composition over Inheritance

فضّل تركيب الـ behavior من objects/components بدل الوراثة العميقة. الـ inheritance بيقفل التصميم وبيعمل coupling قوي بين parent و child.

💡
استخدم has-a (composition) بدل is-a (inheritance) لما السلوك قابل للتبديل.
🔌 Program to an Interface

Program to an Interface, Not an Implementation — اعتمد على الـ abstractions (interfaces / abstract types) مش الـ concrete classes. بيخلي الكود flexible وقابل للـ testing والـ swapping.

💡
مثال: IPaymentGateway بدل StripePayment في الـ constructor — DI بيبني على المبدأ ده.
🏕️ The Boy Scout Rule

"Leave the campground cleaner than you found it." كل ما تلمس ملف أو module — سيبه أحسن شوية: rename، extract method، fix warning، تحسين تسمية.

💡
مش refactor ضخم — تحسينات صغيرة مستمرة بتمنع تراكم الـ technical debt.

class QueryBuilder {
  private table  = "";
  private fields: string[] = ["*"];
  private conditions: string[] = [];
  private limitVal = 0;
  private orderBy = "";

  from(table: string) {
    this.table = table;
    return this;                        // Method chaining ✅
  }
  select(...fields: string[]) {
    this.fields = fields;
    return this;
  }
  where(condition: string) {
    this.conditions.push(condition);
    return this;
  }
  limit(n: number) { this.limitVal = n; return this; }
  order(field: string) { this.orderBy = field; return this; }

  build(): string {
    let q = `SELECT ${this.fields.join(", ")} FROM ${this.table}`;
    if (this.conditions.length) q += ` WHERE ${this.conditions.join(" AND ")}`;
    if (this.orderBy) q += ` ORDER BY ${this.orderBy}`;
    if (this.limitVal) q += ` LIMIT ${this.limitVal}`;
    return q;
  }
}

  .from("users")
  .select("id", "name", "email")
  .where("age > 18")
  .where("active = true")
  .order("name")
  .limit(10)
  .build();
// SELECT id, name, email FROM users WHERE age > 18 AND active = true ORDER BY name LIMIT 10

// اتصال DB — غالي في الإنشاء
class DbConnection {
  constructor(public id: number) {
    console.log(`Connection #${id} opened`);
  }
  query(sql: string) { return `[${this.id}] ${sql}`; }
  close() { console.log(`Connection #${this.id} closed`); }
}

class ConnectionPool {
  private available: DbConnection[] = [];
  private inUse = new Set<DbConnection>();
  private nextId = 1;

  constructor(private maxSize: number) {}

  acquire(): DbConnection {
    const conn = this.available.pop()
      ?? new DbConnection(this.nextId++);
    this.inUse.add(conn);
    return conn;
  }

  release(conn: DbConnection) {
    if (!this.inUse.has(conn)) return;
    this.inUse.delete(conn);
    if (this.available.length < this.maxSize) {
      this.available.push(conn);
    } else conn.close();
  }
}

const pool = new ConnectionPool(3);
const c1 = pool.acquire();
c1.query("SELECT * FROM users");
pool.release(c1);

Observer Event system
بيعرّف علاقة one-to-many — لما object واحد (Subject) بيتغير، كل الـ objects اللي مشتركين فيه (Observers) بيتبلّغوا تلقائياً.

TypeScript
interface Observer { update(data: any): void; }

class EventEmitter {
  private observers: Map<string, Observer[]> = new Map();

  subscribe(event: string, observer: Observer) {
    if (!this.observers.has(event)) this.observers.set(event, []);
    this.observers.get(event)!.push(observer);
  }

  unsubscribe(event: string, observer: Observer) {
    const obs = this.observers.get(event) ?? [];
    this.observers.set(event, obs.filter(o => o !== observer));
  }

  emit(event: string, data: any) {
    (this.observers.get(event) ?? []).forEach(o => o.update(data));
  }
}

class Logger implements Observer {
  update(data: any) { console.log("[LOG]", data); }
}
class EmailAlert implements Observer {
  update(data: any) { console.log("[EMAIL]", data); }
}

const emitter = new EventEmitter();
emitter.subscribe("order.created", new Logger());
emitter.subscribe("order.created", new EmailAlert());
emitter.emit("order.created", { id: 42, total: 150 });
// [LOG] {id: 42, total: 150}
// [EMAIL] {id: 42, total: 150}

بيعرّف عائلة من الـ algorithms، بيغلّف كل واحد منهم، وبيخليهم interchangeable. بيتغير الـ algorithm من غير تغيير الـ context.

TypeScript
interface SortStrategy {
  sort(data: number[]): number[];
}

class BubbleSort implements SortStrategy {
  sort(data: number[]) {
    const arr = [...data];
    for (let i = 0; i < arr.length; i++)
      for (let j = 0; j < arr.length - i - 1; j++)
        if (arr[j] > arr[j+1]) [arr[j], arr[j+1]] = [arr[j+1], arr[j]];
    return arr;
  }
}

class QuickSort implements SortStrategy {
  sort(data: number[]) { return [...data].sort((a, b) => a - b); }
}

class Sorter {
  constructor(private strategy: SortStrategy) {}

  setStrategy(s: SortStrategy) { this.strategy = s; } // تغيير runtime
  sort(data: number[]) { return this.strategy.sort(data); }
}

const sorter = new Sorter(new QuickSort());
console.log(sorter.sort([5,2,8,1]));    // [1, 2, 5, 8]

sorter.setStrategy(new BubbleSort());   // تغيير الـ algorithm وقت التشغيل
console.log(sorter.sort([5,2,8,1]));    // [1, 2, 5, 8]

interface Command { execute(): void; undo(): void; }

class TextEditor {
  private content = "";
  add(text: string)    { this.content += text; }
  remove(n: number)   { this.content = this.content.slice(0, -n); }
  getText()            { return this.content; }
}

class AddTextCommand implements Command {
  constructor(private editor: TextEditor, private text: string) {}

  undo()    { this.editor.remove(this.text.length); }

  private history: Command[] = [];

  execute(cmd: Command) { cmd.execute(); this.history.push(cmd); }
  undo() {
    const cmd = this.history.pop();
    if (cmd) cmd.undo();
  }
}

Memento State snapshot
بيحفظ الحالة الداخلية لـ object من غير ما يكشف تفاصيل الـ implementation. بيستخدم في Undo/Redo.
امتى: Text editor undo، Game save points، Form drafts.
TypeScript
class EditorMemento {
  constructor(readonly content: string, readonly cursor: number) {}
}

class TextEditor {
  private content = "";
  private cursor = 0;

  insertText(text: string) {
    this.content = this.content.slice(0, this.cursor) + text + this.content.slice(this.cursor);
    this.cursor += text.length;
  }

  save(): EditorMemento {
    return new EditorMemento(this.content, this.cursor);
  }

  restore(m: EditorMemento) {
    this.content = m.content;
    this.cursor = m.cursor;
  }

  getContent() { return this.content; }
}

class History {
  private stack: EditorMemento[] = [];
  push(m: EditorMemento) { this.stack.push(m); }
  pop(): EditorMemento | undefined { return this.stack.pop(); }
}

const editor = new TextEditor();
const history = new History();
editor.insertText("Hello");
history.push(editor.save());
editor.insertText(" World");
console.log(editor.getContent());  // Hello World
editor.restore(history.pop()!);

interface Expression {

}

class NumberExpr implements Expression {
  constructor(private value: number) {}
  evaluate() { return this.value; }
}

class AddExpr implements Expression {
  constructor(private left: Expression, private right: Expression) {}
  evaluate() { return this.left.evaluate() + this.right.evaluate(); }
}

class SubtractExpr implements Expression {
  constructor(private left: Expression, private right: Expression) {}
  evaluate() { return this.left.evaluate() - this.right.evaluate(); }

  new NumberExpr(3)

abstract class DataExporter {
  export(data: object[]) {  // skeleton ثابت
    const validated = this.validate(data);
    const formatted = this.format(validated);
    return this.write(formatted);
  }

  protected validate(data: object[]) {
    return data.filter(row => Object.keys(row).length > 0);
  }

  protected abstract format(data: object[]): string;
  protected abstract write(content: string): string;
}

class CsvExporter extends DataExporter {
  format(data: object[]) {
    const keys = Object.keys(data[0] ?? {});
    return [keys.join(","), ...data.map(r => keys.map(k => (r as any)[k]).join(","))].join("\n");
  }
  write(c: string) { return `CSV:\n${c}`; }
}

class JsonExporter extends DataExporter {
  format(data: object[]) { return JSON.stringify(data, null, 2); }
  write(c: string) { return `JSON:\n${c}`; }
}

interface OrderState {

  deliver(order: Order): void;
  getName(): string;
}

  deliver() { this.state.deliver(this); }

Mediator Communication hub
بيقلل الـ coupling بين objects بأنه بيخليهم يتواصلوا من خلاله بدل ما يتواصلوا مع بعض مباشرة.

TypeScript
class ChatRoom {
  private users: User[] = [];

  join(user: User) {
    this.users.push(user);
    user.setRoom(this);
    this.broadcast(`${user.name} joined`, user);
  }

  sendMessage(from: User, msg: string) {
    this.broadcast(`${from.name}: ${msg}`, from);
  }

  private broadcast(msg: string, sender: User) {
    this.users.filter(u => u !== sender).forEach(u => u.receive(msg));
  }
}

class User {
  private room?: ChatRoom;
  constructor(public name: string) {}
  setRoom(room: ChatRoom) { this.room = room; }
  send(msg: string) { this.room?.sendMessage(this, msg); }
  receive(msg: string) { console.log(`[${this.name}] ${msg}`); }
}

const room = new ChatRoom();
const ali = new User("Ali");
const sara = new User("Sara");
room.join(ali);
room.join(sara);
ali.send("Hello everyone!");
Chain of Responsibility Request pipeline
بيمرر الـ request على سلسلة من الـ handlers. كل handler بيقرر إما يعالجه أو يمرره للتالي.
امتى: Middleware pipeline، Logging levels، Event handling.
TypeScript
interface HttpRequest {
  path: string;
  token?: string;
  body?: unknown;
}

abstract class Middleware {
  private next?: Middleware;
  setNext(m: Middleware) { this.next = m; return m; }
  handle(req: HttpRequest): void {
    if (this.process(req) && this.next) this.next.handle(req);
  }
  protected abstract process(req: HttpRequest): boolean;
}

class AuthMiddleware extends Middleware {
  process(req: HttpRequest) {
    if (!req.token) { console.log("401 Unauthorized"); return false; }
    return true;
  }
}
class ValidationMiddleware extends Middleware {
  process(req: HttpRequest) {
    if (!req.body) { console.log("400 Bad Request"); return false; }
    return true;
  }
}
class HandlerMiddleware extends Middleware {
  process(req: HttpRequest) {
    console.log(`200 OK — ${req.path}`);
    return false;  // نهاية السلسلة
  }
}

const auth = new AuthMiddleware();
const validation = new ValidationMiddleware();
const handler = new HandlerMiddleware();
auth.setNext(validation).setNext(handler);
auth.handle({ path: "/api/orders", token: "abc", body: {} });

interface AstVisitor {
  visitNumber(n: NumberNode): string;
  visitBinary(b: BinaryNode): string;
}

interface AstNode {
  accept(v: AstVisitor): string;
}

class NumberNode implements AstNode {
  constructor(public value: number) {}
  accept(v: AstVisitor) { return v.visitNumber(this); }
}

class BinaryNode implements AstNode {
  constructor(public op: string, public left: AstNode, public right: AstNode) {}
  accept(v: AstVisitor) { return v.visitBinary(this); }
}

class CodeFormatter implements AstVisitor {
  visitNumber(n: NumberNode) { return String(n.value); }
  visitBinary(b: BinaryNode) {
    return `(${b.left.accept(this)} ${b.op} ${b.right.accept(this)})`;
  }
}

// ─── Abstract Class: "هو نوع من..." + shared behavior ───
abstract class Employee {
  constructor(protected name: string, protected salary: number) {}

  getDetails() { return `${this.name} - $${this.salary}`; }  // shared

  abstract calculateBonus(): number;                          // يختلف لكل نوع
  abstract getRole(): string;
}

class Manager extends Employee {
  calculateBonus() { return this.salary * 0.2; }
  getRole() { return "Manager"; }
}

// ─── Interface: "بيقدر يعمل..." — capabilities ───
interface Exportable  { exportToPDF(): string; }
interface Printable   { print(): void; }
interface Archivable  { archive(): void; }

class Invoice extends Document
  implements Exportable, Printable, Archivable {  // ✅ متعدد

OOD Process
خطوات التصميم من البداية للنهاية

إزاي بتعمل OOD لمشروع حقيقي؟ في 6 خطوات أساسية بتمشي فيهم.

Requirements Analysis — فهم المتطلبات

قرا الـ requirements كويس. استخرج الـ nouns — دول هم الـ objects المحتملة. الـ verbs دي الـ methods. مثلاً: "المستخدم بيطلب منتج ويدفع" → User, Product, Order, Payment.

Identify Objects & Classes — تحديد الـ Classes

حوّل الـ nouns لـ classes. حدد الـ attributes (data) والـ behaviors (methods) لكل class. مش لازم تكمّل كل حاجة دلوقتي — ابدأ بالأساسيات.

Define Responsibilities — تحديد المسؤوليات

كل class مسؤول عن إيه بالظبط؟ طبّق SRP هنا. لو class بيعمل أكتر من حاجة — قسّمه. استخدم CRC cards (Class-Responsibility-Collaboration).

Model Relationships — رسم العلاقات

حدد العلاقات بين الـ classes: إيه الـ associations؟ إيه الـ aggregations؟ إيه الـ compositions؟ ارسم الـ UML class diagram.

Apply Design Patterns — تطبيق الـ Patterns

بعد ما حددت الـ classes والعلاقات، شوف فيه design pattern بيحل مشكلة موجودة. مش بتبحث عن patterns تحشرها — بتشوف لو المشكلة محتاجها.

Refine with SOLID — مراجعة وتحسين

راجع التصميم على ضوء الـ SOLID principles. طرح الأسئلة: كل class ليه مسؤولية واحدة؟ مش محتاج تعدّل كلاسات موجودة لإضافة features؟ الـ coupling مقبول؟

مثال تطبيقي — نظام مكتبة
// Step 1 — Requirements: "طالب بيستعير كتاب من المكتبة لفترة محددة"

// Step 2 — Objects: Student, Book, Library, Loan

// Step 3 — Responsibilities
class Book {                        // مسؤولية: بيانات الكتاب
  constructor(
    public id: string,
    public title: string,
    private available: boolean = true
  ) {}
  isAvailable() { return this.available; }
  checkout()    { this.available = false; }
  return_()     { this.available = true; }
}

class Student {                      // مسؤولية: بيانات الطالب
  private loans: Loan[] = [];
  constructor(public id: string, public name: string) {}
  addLoan(loan: Loan) { this.loans.push(loan); }
  getActiveLoans() { return this.loans.filter(l => !l.isReturned()); }
}

class Loan {                         // مسؤولية: إدارة الاستعارة
  private returned = false;
  private dueDate: Date;

  constructor(public book: Book, public student: Student) {
    this.dueDate = new Date(Date.now() + 14 * 24 * 60 * 60 * 1000); // 14 days
  }
  return_()    { this.returned = true; this.book.return_(); }
  isOverdue()  { return !this.returned && new Date() > this.dueDate; }
  isReturned() { return this.returned; }
}

class Library {                       // مسؤولية: إدارة العمليات
  private books: Book[] = [];

  addBook(book: Book)    { this.books.push(book); }

  borrowBook(student: Student, bookId: string): Loan {
    const book = this.books.find(b => b.id === bookId);
    if (!book || !book.isAvailable()) throw new Error("Book not available");
    book.checkout();
    const loan = new Loan(book, student);
    student.addLoan(loan);
    return loan;
  }
}

Anti-Patterns
الأخطاء الشائعة في OOD — اعرفها عشان تتجنبها

الـ Anti-patterns هي الـ patterns السيئة — حلول بتبدو منطقية لكن بتعمل مشاكل على المدى البعيد.

🍝 Spaghetti Code

كود بلا structure أو organization. كل حاجة متشابكة مع بعض. مستحيل تفهمه أو تعدّله من غير ما تكسر حاجة تانية.

✅
الحل: Refactor لـ classes وapply الـ SRP.
🔫 God Object / God Class

كلاس واحد بيعرف كل حاجة ويعمل كل حاجة في النظام. بيخرق الـ SRP بشكل صارخ وبيكون single point of failure.

✅
الحل: Split لـ classes أصغر ومتخصصة.
⚙️ Over-Engineering

تعقيد زيادة عن اللازم. إضافة abstractions وpatterns من غير ما فيه حاجة تستدعي كده. بيصعّب الفهم والصيانة.

✅
الحل: YAGNI و KISS — ابني اللي محتاجه بس.
🤫 Anemic Domain Model

Classes فيها data بس من غير behavior. كأنها data structures مش objects. كل الـ logic في service classes كبيرة.

✅
الحل: حط الـ behavior جوا الـ class اللي بيمثل الـ domain.
🔗 Tight Coupling

Classes بتعتمد على بعض مباشرة. أي تغيير في class بيأثر على كل الـ classes التانية. بيصعّب الـ testing والـ reuse.

✅
الحل: Dependency Injection والـ DIP.
📋 Copy-Paste Programming

نسخ ولصق الكود بدل ما تعمل abstraction. بيخرق الـ DRY وبيصعّب التحديث — لو فيه bug لازم تصلحه في كل مكان.

✅
الحل: Extract الكود المتكرر في method أو class مشترك.
