1) Python Fundamentals

الفرق بين list و tuple?

list mutable (تتغير)، tuple immutable. List أبطأ قليلاً في الذاكرة. Tuple مناسبة للـ keys في dict وللـ return values ثابتة. في Odoo: domains أحياناً tuples، record IDs tuples.

إمتى تستخدم set?

للتجميعات بدون تكرار، membership tests سريعة O(1). مثال: seen = set(records.ids) لإزالة duplicates، أو intersection بين recordsets.

Explain generators

Functions تستخدم yield بدل return — تنتج values lazily واحدة واحدة بدون تحميل كل القائمة في الذاكرة. مفيدة لمعالجة datasets كبيرة.

الفرق بين yield و return?

return ينهي الدالة ويرجع value واحدة. yield يوقف مؤقتاً ويرجع value ويحتفظ بالـ state — الدالة تصبح generator.

Explain decorators

Functions تلف functions أخرى لتعديل سلوكها بدون تغيير الكود الأصلي. Syntax: @decorator. في Odoo: @api.depends, @api.constrains كلها decorators تعدّل metadata وbehavior.

Explain context managers (with)

Objects implementing __enter__ و __exit__ — تضمن cleanup. مثال: with open(...). في Odoo: cursor transactions — cr.savepoint() context manager للـ rollback جزئي.

Shallow copy vs deep copy?

Shallow: ينسخ المرجع الخارجي، nested objects مشتركة. Deep: ينسخ كل المستويات.recursively. copy.copy() vs copy.deepcopy(). مهم لما تعدّل dict/list داخل record values.

Explain GIL

Global Interpreter Lock — thread واحد بس ينفّذ Python bytecode في نفس الوقت. Multithreading مش effective للـ CPU-bound tasks. Odoo workers = multiprocessing (processes منفصلة)، كل worker process له Python interpreter خاص.

Multithreading vs multiprocessing?

Threading: threads في process واحد — good for I/O-bound. Multiprocessing: processes منفصلة — bypass GIL، good for CPU-bound. Odoo production يستخدم multi-worker (processes) + gevent للـ longpolling.

Metaclasses?

Class of a class — تتحكم في إنشاء classes. Odoo ORM يستخدم metaclass (MetaModel) لبناء models، fields، و tables تلقائياً من class definition.

Explain MRO

Method Resolution Order — ترتيب البحث عن methods في inheritance chain (C3 linearization). في Odoo: _inherit chains — super() يتبع MRO. مهم لما عندك multiple inheritance.

Monkey patching?

تعديل class/module at runtime بدون تغيير source. Odoo extension via _inherit is structured monkey patching — تضيف/تعدّل methods على models موجودة.

*args and **kwargs?

*args = tuple of positional args. **kwargs = dict of keyword args. في Odoo overrides: def create(self, vals_list): return super().create(vals_list) — لازم pاس نفس signature.

Closures?

Inner function تحتفظ بالـ variables من outer scope حتى بعد ما outer function تخلص. مفيدة في decorators و callbacks.

__new__ vs __init__?

__new__ ينشئ الـ instance (class method). __init__ يinitialize الـ instance بعد الإنشاء. ORM Odoo يoverride __new__ لإنشاء recordsets مش instances عادية.

Descriptors?

Objects with __get__, __set__, __delete__. Odoo fields are descriptors — record.name triggers field's __get__ which reads from cache/DB.

is vs ==?

is = same object in memory (identity). == = equal values. في Odoo: record is record2 rarely useful؛ compare record.id == record2.id or use record == record2 (recordset comparison).

@classmethod vs @staticmethod?

@classmethod receives class as first arg (cls). @staticmethod no implicit first arg. Odoo @api.model ≈ classmethod — method on model level not record level.

2) PostgreSQL

Explain indexes

Data structure (usually B-tree) يسرّع SELECT/WHERE/JOIN على columns مفهرسة. Trade-off: أسرع reads، أبطأ writes + مساحة إضافية. في Odoo: index=True على field.

B-tree vs Hash indexes

B-tree (default): equality + range queries + sorting. Hash: equality only (=)، no range. PostgreSQL B-tree covers 99% of Odoo use cases.

Composite indexes

Index على multiple columns. ترتيب الأعمدة مهم — leftmost prefix rule. مثال: index على (company_id, state, date) يخدم queries filter بـ company_id أولاً.

VACUUM?

ينظف dead tuples بعد UPDATE/DELETE، يمنع bloat، يحدّث visibility map. PostgreSQL autovacuum يشتغل تلقائياً. مهم بعد bulk deletes في Odoo migrations.

ANALYZE?

يحدّث statistics للـ query planner (row counts, distribution). بدونها planner يختار plans سيئة. VACUUM ANALYZE بعد bulk data changes.

Transactions & ACID

Transaction = unit of work. ACID: Atomicity (all or nothing), Consistency (valid state), Isolation (concurrent txs), Durability (committed = permanent). Odoo: كل request = transaction — rollback on error.

Isolation levels

Read Uncommitted → Read Committed (PG default) → Repeatable Read → Serializable. Higher = less anomalies, more locking. Odoo relies on Read Committed + application-level locking for critical sections.

Deadlocks?

Two transactions wait for each other's locks — PG kills one. Fix: consistent lock ordering, shorter transactions, retry logic. في Odoo: common in concurrent writes on same records.

EXPLAIN ANALYZE

Shows query execution plan + actual timings. Detect: Seq Scan (bad on large tables), missing indexes, high cost nodes. Essential for Odoo performance debugging.

LEFT JOIN vs INNER JOIN

INNER: only matching rows from both tables. LEFT: all rows from left table + matching from right (NULL if no match). Use LEFT when optional relation.

CTE (WITH clauses)

Named subquery in same statement — improves readability. Can be recursive. PG 12+ can inline/materialize depending on planner.

Window functions

Aggregate over row sets without GROUP BY collapsing rows. ROW_NUMBER(), RANK(), LAG(), SUM() OVER (PARTITION BY ...). Useful in complex SQL reports bypassing ORM.

Partial indexes

Index on subset: CREATE INDEX ... WHERE state = 'done'. Smaller, faster when queries always filter same condition.

Materialized views

Pre-computed query result stored on disk. Fast reads, stale until REFRESH. Alternative to stored computed fields for heavy analytics.

db_maxconn vs max_connections

Odoo db_maxconn = max connections per worker to PG. PG max_connections = total server limit. Formula: workers × db_maxconn + longpolling + admin headroom ≤ max_connections.

3) Odoo Architecture & Inheritance

_inherit vs _name vs _inherits?
  • _name + no _inherit = model جديد + table جديد.
  • _inherit = 'existing.model' = Classical inheritance — extend model موجود (same table, merge fields/methods).
  • _inherits = {'parent.model': 'parent_id'} = Delegation — composition. Model جديد table جديد + FK للـ parent. Access parent fields via delegation. مثال: res.users inherits res.partner.
استخدم _inherit للـ extension. _inherits لما محتاج model منفصل logically لكن يshare بيانات partner.
Module dependencies & circular deps?

depends في manifest — Odoo loads modules in topological order. Circular dependency = install fails. Fix: extract shared logic لـ third module، or use _inherit without hard dependency via late loading (bad practice). Best: refactor into base module both depend on.

Record lifecycle & safe overrides?
def create(self, vals_list):
    # pre-processing
    records = super().create(vals_list)
    # post-processing
    return records

def write(self, vals):
    res = super().write(vals)
    return res

def unlink(self):
    # cleanup before delete
    return super().unlink()

Always call super(). Don't break return values. Avoid recursive writes in create/write.

@api.model vs @api.depends vs @api.onchange vs @api.constrains?
  • @api.model — method on model, not specific records.
  • @api.depends — computed field dependencies.
  • @api.onchange — UI-only field reactions.
  • @api.constrains — validation on create/write (backend).
Translations — _() role?

_('Sale Order') marks string for export/import via PO files. At runtime returns translated string based on user language. Use on user-visible strings in Python. XML: string="..." auto-translatable. env._() or self.env._() in Odoo 16+.

Registry?

odoo.registry — per-database cache of all models, fields, constraints. Built at startup/module install. Invalidated on module update. Each worker has own registry in memory.

ir.model.data & noupdate?

ir.model.data maps XML ID (module.name) → database record. noupdate="1" = on module upgrade, don't overwrite record if exists — protects user customizations.

Hooks?
  • pre_init_hook — before module install (DB not ready fully).
  • post_init_hook — after install.
  • post_load — after registry loaded (server start).
  • uninstall_hook — before uninstall cleanup.

4) Odoo ORM

Model vs AbstractModel vs TransientModel?
  • models.Model — persistent, real DB table, data stays.
  • models.AbstractModel — no table, mixin for shared fields/methods (mail.thread).
  • models.TransientModel — temporary table, auto-vacuumed (wizards, cron cleanup).
create / write / unlink / copy?
  • create(vals_list) — insert records, returns recordset.
  • write(vals) — update records in recordset.
  • unlink() — delete records.
  • copy(default=None) — duplicate record (+ lines if copy=True on O2M).
@api.model_create_multi?

Decorator for batch create — receives list of dicts, creates all in optimized batch. Odoo 13+ default. Override must handle vals_list not single dict. Much faster than loop create().

search vs browse vs read vs search_read vs search_fetch vs search_count?
  • search(domain) — returns recordset of IDs (lightweight).
  • browse(ids) — recordset from IDs without DB check.
  • read(['fields']) — dicts with field values (DB hit).
  • search_read(domain, fields) — search + read in one call (common for APIs).
  • search_fetch(domain, fields) — Odoo 17+ optimized: fetch only needed columns.
  • search_count(domain) — COUNT query, no records loaded.
read_group?

SQL GROUP BY wrapper. self.read_group(domain, ['amount:sum'], ['partner_id', 'state']) — powers pivot/graph views. Always prefer over Python loops for aggregations.

env & components?
  • env — Environment: bundles cr, uid, context, registry.
  • env.cr — database cursor (transaction).
  • env.user — current user record.
  • env.company — current company. env.companies — all allowed.
  • env.context — dict of contextual flags.
  • env.ref('module.xml_id') — resolve XML ID to record.
Recordsets — immutable? duplicates?

Recordset = ordered collection of IDs + env. Operations return NEW recordsets (immutable style). Can contain duplicates if you do recordset + recordset with overlapping IDs — use .ids set if needed.

filtered / mapped / sorted?
  • filtered(lambda r: r.state == 'done') or filtered('state') — filter in memory.
  • mapped('partner_id.name') — extract field values across records.
  • sorted(key=lambda r: r.date) — sort recordset.
NewId?

Placeholder ID for unsaved records in UI (id like NewId_0x...). record.id is falsy or special. Can't search/write to DB until saved.

Context & with_context?

Dict passed through env affecting behavior. record.with_context(key=value) returns same records with new env context. Common keys: default_field, tracking_disable, mail_create_nolog, prefetch_fields=False, lang.

active_id / active_ids?

Set by UI when opening wizards/actions. active_id = single selected record. active_ids = list of selected records. active_model = model name. Access via context in wizards.

sudo() — when to avoid?

sudo() runs as superuser — bypasses record rules (NOT ACL unless uid=1). Use only for system operations (cron, automated emails). Avoid for user-facing logic — security hole. sudo(False) reverts to original user.

Command API?
from odoo import Command
'line_ids': [
    Command.create({'product_id': 1, 'qty': 5}),
    Command.update(line_id, {'qty': 10}),
    Command.delete(line_id),
    Command.link(existing_id),
    Command.unlink(link_id),
    Command.clear(),
    Command.set([id1, id2]),
]
flush / invalidate?

flush_recordset() — push pending ORM changes to DB. invalidate_recordset() — clear cache. Needed when mixing raw SQL with ORM on same records.

5) Fields

Field types differences?
  • Char — short text, indexed, max ~255.
  • Text — long text, no index by default.
  • Html — sanitized HTML, widget renders rich text.
  • Boolean — True/False/NULL.
  • Integer / Float — numbers. Use Float carefully (precision).
  • Monetary — Float + currency_field.
  • Selection — fixed choices list.
  • Date / Datetime — date vs timestamp.
  • Binary — file content in DB or filestore.
  • Image — Binary with resize (max_width/max_height).
  • Json — JSONB column (Odoo 16+).
Many2one / One2many / Many2many?
  • Many2one — FK column in this table → one related record. ondelete='cascade/restrict/set null'.
  • One2many — reverse of Many2one on other model. Virtual — no column here. Needs inverse_name.
  • Many2many — relation table with two FK columns. relation, column1, column2 optional.
Field parameters?
  • required — NOT NULL + UI validation.
  • copy=False — skip on duplicate.
  • readonly=True — UI readonly (not DB enforced).
  • tracking=True — log changes in chatter.
  • compute/store/inverse/search — computed field config.
  • company_dependent=True — stored in ir.property per company.
  • index=True — DB index.
  • groups — field-level access restriction.

6) Computed Fields

Computed fields & @api.depends?
total = fields.Float(compute='_compute_total', store=True)

@api.depends('line_ids.price_subtotal')
def _compute_total(self):
    for rec in self:
        rec.total = sum(rec.line_ids.mapped('price_subtotal'))

@api.depends tells ORM when to recompute — critical for correctness and performance.

Stored vs non-stored?
  • Non-stored — computed on read, always fresh, can't search/group (unless search method), slower on large recordsets.
  • Stored (store=True) — saved in DB, searchable, faster reads, recomputed on dependency change. Use for fields in domains/reports.
inverse?

Makes computed field writable — user edits trigger inverse method to update source fields. inverse='_inverse_total'.

Custom search on computed field?
amount_total = fields.Float(compute='_compute_amount', search='_search_amount')

def _search_amount(self, operator, value):
    return [('line_ids.price_subtotal', operator, value)]  # domain translation
Circular dependencies?

A depends on B, B depends on A — infinite recompute loop. Fix: restructure fields, use related stored fields, or compute both from shared source. Detect via logs/warnings on install.

7) Constraints

Python vs SQL constraints?
  • Python (@api.constrains) — flexible logic, cross-field validation, runs in ORM layer, can show UserError message. Slower, can be bypassed by SQL.
  • SQL (_sql_constraints) — DB-level, fast, enforced always (UNIQUE, CHECK). Less flexible error messages.

Use SQL for uniqueness/integrity. Python for complex business rules.

8) Onchange

Explain onchange

@api.onchange('partner_id') — triggered in UI when field changes. Updates other fields on same form (not saved yet). Returns warnings/domains.

Onchange vs compute?
  • Onchange: UI only, before save, interactive UX.
  • Compute: backend, on read/write, always consistent, works via API too.
Why onchange isn't enough for validation?

Onchange doesn't run on RPC/API/import/cron writes. User can bypass UI. Always enforce business rules in @api.constrains or create/write overrides.

9) Security

Groups & implied_ids?

res.groups define roles. implied_ids = auto-grant sub-groups (Sales/User implies Employee). Creates hierarchy. Users get union of all group permissions.

ACL vs Record Rules?
  • ACL (ir.model.access) — model-level CRUD permissions per group. Can user access this model at all?
  • Record Rules (ir.rule) — row-level filtering via domain. WHICH records can they see/edit?

Both must pass. ACL checked first, then rules filter records.

Global vs non-global rules?

Global rules (global=True): AND together for all users. Non-global: OR within same group, AND across groups. Misconfigured rules = data leaks or AccessErrors.

sudo bypasses rules?

Yes — record rules skipped with sudo(). ACL still applies (unless superuser uid=1 has all access). Never use sudo to "fix" security — fix rules/ACL properly.

Hide field — view groups or record rules?

View/field groups = UI hiding only — NOT security (user can still access via RPC). For real security: ACL + record rules + field groups attribute together.

10) Controllers & HTTP

@http.route basics
@http.route('/api/orders', type='json', auth='user', methods=['POST'])
def get_orders(self, **kw):
    return request.env['sale.order'].search_read([], ['name', 'amount_total'])
auth modes?
  • auth='user' — must be logged in (default safe).
  • auth='public' — website visitor or logged user.
  • auth='none' — no DB user, no session — dangerous, use carefully.
type='http' vs type='json'?

json — JSON-RPC body, auto parse/serialize. http — raw HTTP, you handle request/response manually (HTML, files, custom JSON).

CSRF?

Odoo validates CSRF token on state-changing HTTP requests. csrf=False only for external webhooks with other auth (signature verification). Never disable without alternative protection.

11) Views

View types?

form (detail), tree/list (rows), kanban (cards), search (filters/groupby), graph (charts), pivot (cross-tab), calendar, activity, gantt, cohort — each optimized for different UX.

XPath positions?
  • inside — append inside element.
  • before/after — sibling position.
  • replace — replace element entirely.
  • attributes — modify attributes (add/remove attribute nodes).
attrs vs modifiers (Odoo 17+)?

Old: attrs="{'invisible': [('state','!=','draft')]}". New (17+): direct Python expressions: invisible="state != 'draft'". Cleaner, same logic.

domain on field?

Filters selectable records in relational fields. domain="[('company_id', '=', company_id)]". Can use context variables.

12) Actions & Menus

Action types?
  • ir.actions.act_window — open views (most common).
  • ir.actions.server — execute Python code/email/actions on records.
  • ir.actions.client — trigger OWL client action (tag).
  • ir.actions.report — generate PDF/QWeb report.
  • ir.actions.act_url — redirect to URL.

13) Reports & QWeb

QWeb directives?
  • t-if — conditional render.
  • t-foreach — loop (t-as for alias).
  • t-call — include sub-template.
  • t-set — set variable.
  • t-field — render field with formatting (dates, monetary).
  • t-esc — escape HTML (plain text, safe).
t-field vs t-esc?

t-field — uses field formatter (respects user language, monetary, widgets). t-esc — raw value HTML-escaped. Use t-field for model fields, t-esc for plain strings.

wkhtmltopdf problems?

Version compatibility (0.12.5 common), CSS flexbox issues, slow on large HTML, memory leaks. Fix: simplify template, paginate, use background jobs, or switch to alternative engines in newer Odoo versions.

14) Scheduled Actions (Cron)

How cron works?

ir.cron records with interval (minutes/hours/days/weeks), next call datetime, model method to execute. Worker checks due crons, runs as specified user_id. One cron at a time per DB (lock).

Avoid duplicate execution?

Odoo has DB-level lock for crons. For custom jobs: use advisory locks, check state flag, or queue job with unique job UUID. Set realistic intervals.

Cron for 1-hour job?

No. Cron has timeout (~limit_time_real_cron). Use: Queue Job (OCA), dedicated worker process, or chunked cron with progress tracking (process 1000 records per run).

15) Mail Framework

mail.thread & mail.activity.mixin?

mail.thread — chatter, followers, message_post, tracking. mail.activity.mixin — scheduled activities (calls, todos). Inherit both for full collaboration features.

Tracking fields?

tracking=True on field — logs old→new value in chatter on write. Uses mail.tracking.value. Disable with tracking_disable in context for bulk ops.

Suppress mail logging?

Context keys: mail_create_nolog, mail_notrack, tracking_disable. Essential for imports/migrations performance.

16) Performance

N+1 problem?

Loop over N records, each accesses related field → N extra queries. Fix: prefetch (automatic if same recordset batch), use mapped(), read() with all fields, or search_read.

Bad: for order in orders: print(order.partner_id.name) — 1 + N queries. Good: orders.mapped('partner_id.name') — 2 queries.
Prefetching?

ORM batches related field reads — when you read partner_id on 100 records, one query fetches all partners. Disable: with_context(prefetch_fields=False) when reading many fields you don't need.

ORM cache?

Records cached in memory per transaction. Re-read same field = no DB hit. Invalidated on write/unlink. Stale cache issues when mixing SQL + ORM — use flush/invalidate.

When raw SQL?

Heavy reports, bulk updates millions of rows, complex aggregations ORM can't express efficiently. Always parameterized queries: cr.execute("SELECT ... WHERE id = %s", [id]) — NEVER string format user input.

50K slow records — what to do?
  1. Profile (--log-sql, Odoo profiler, query counter).
  2. Find N+1, loops with search(), missing indexes.
  3. Fix: batch ops, stored computed, read_group, SQL.
  4. Background job for heavy reports.
  5. EXPLAIN ANALYZE on slow queries.

17) Multi Company

company_id / company_ids / check_company?

Records have company_id. Users have company_ids (allowed) + company_id (current). check_company=True on relational fields validates same company. Record rules filter by company.

company_dependent fields?

Stored in ir.property — different value per company on same record. E.g., account payable per company for shared partner.

Data leak investigation?
  1. Audit record rules on affected model — missing company domain?
  2. Check sudo() usage in controllers/cron.
  3. Review shared records (company_id=False).
  4. Check mail.message followers cross-company.
  5. Test with user in company A — search records from company B.

18) Integrations & APIs

XML-RPC vs JSON-RPC?

Both call Odoo models via RPC. XML-RPC older, XML encoding. JSON-RPC lighter, JSON encoding — preferred for new integrations. Same authentication (db, uid, password/api key).

Webhook integration design?
  1. Controller with signature verification (HMAC).
  2. Store raw payload in queue table immediately (outbox).
  3. Process async via cron/queue job.
  4. Idempotency key — skip duplicates.
  5. Retry with exponential backoff.
External system goes offline?

Outbox pattern: save intent locally first, sync later. Retry queue, dead letter for failures. Never lose data — transactional local write before external call. Reconciliation cron.

Queue Job vs Celery vs Cron?
  • Cron — simple scheduled, not for heavy/async.
  • Queue Job (OCA) — Odoo-native, channels, retries, UI — best for Odoo projects.
  • Celery — external broker (Redis/RabbitMQ), more infra, good for multi-system.

19) JavaScript / OWL

What is OWL?

Odoo Web Library — Odoo's React-like component framework. Declarative templates, reactive state, component composition. Replaced old Widget system from Odoo 14+.

Components, Props, State?

Component = UI unit with template. Props = inputs from parent (read-only). State (useState) = internal reactive data — changes trigger re-render.

Lifecycle hooks?

onWillStart (async setup), onMounted (DOM ready), onWillUpdateProps, onWillUnmount (cleanup). Like React lifecycle.

Services & Registries?

Services = singletons injected via useService('rpc'). Registry = catalog of components, fields, services. Extend via registry.category('fields').add(...).

Patching?
import { patch } from "@web/core/utils/patch";
import { ListController } from "@web/views/list/list_controller";
patch(ListController.prototype, {
    async onClickCreate() { /* custom */ }
});
Odoo JS services?

action — open views/actions. orm/rpc — backend calls. notification — toasts. dialog — modals.

Asset bundles?

In manifest 'assets': {'web.assets_backend': ['module/static/src/js/*.js']}. Bundled and minified. Extend existing bundles, don't replace entirely.

20) Website & Portal

Portal access?

Portal users = restricted public users linked to partner. Record rules limit to own records (e.g., own invoices). portal module provides base templates/routes.

website_published?

Boolean field — controls public website visibility. Combined with website record rules and multi-website (website_id).

21) Module Development

__manifest__.py key fields?

name, version (16.0.1.0.0), depends, data (load order matters!), assets, license, installable, application (shows as app), auto_install.

Odoo CLI useful commands?
odoo-bin -c odoo.conf -d mydb -u my_module --stop-after-init
odoo-bin shell -d mydb --no-http
odoo-bin -d mydb --test-enable -i my_module --stop-after-init
Studio vs custom code?

Studio: quick customizations, non-dev friendly, harder to version control. Custom modules: full control, git, tests, portable. Senior knows when Studio is enough vs when code is required.

22) Deployment & DevOps

Workers configuration?

workers = (2 × CPU cores) + 1 rule of thumb. Each worker = separate process. Also need gevent worker for longpolling (bus). max_cron_threads for crons.

Key odoo.conf options?

db_host, db_name, data_dir (filestore), workers, limit_time_cpu, limit_time_real, proxy_mode, db_maxconn, log_level, admin_passwd.

nginx reverse proxy?

Proxy pass to Odoo (8069) + longpolling (8072). Set proxy_mode = True. SSL termination at nginx. Gzip, client max body size for uploads.

Docker compose components?

Services: odoo (app), postgres (db), nginx (proxy optional). Volumes: filestore, PG data. Env vars for credentials. Separate dev/staging/prod compose files.

PostgreSQL tuning?

shared_buffers ~25% RAM, work_mem for sorts, effective_cache_size ~75% RAM, max_connections match Odoo pool. Monitor with pg_stat_statements.

Backup strategy?

pg_dump (database) + filestore copy (attachments). Both required — attachments not in DB (since filestore). Test restore regularly.

23) Upgrade & Migration

Module upgrade?

-u module_name reloads data files (respecting noupdate), runs migrations, updates views. Always test on staging clone first.

Migration scripts?

In migrations/16.0.2.0.0/pre-migrate.py and end-migrate.py. migrate(cr, version) function. pre = before model update, end/post = after.

OpenUpgrade?

OCA project for Community version upgrades (14→15→16→17). Provides migration scripts for standard modules. Custom modules need your own migration scripts.

Data migration strategies?

CSV import, RPC scripts, SQL ETL, intermediate staging DB. Use tracking_disable, batch creates, validate counts/checksums after migration.

24) Testing

TransactionCase vs SavepointCase vs HttpCase?
  • TransactionCase — each test method rolled back after run.
  • SavepointCase — savepoints allow nested rollback (faster suite).
  • HttpCase — HTTP/RPC level tests, browser tours, controller tests.
Mocking external APIs?
@patch('requests.post')
def test_sync(self, mock_post):
    mock_post.return_value.json.return_value = {'status': 'ok'}
    self.env['my.sync'].sync_data()
    mock_post.assert_called_once()
Run tests?

odoo-bin -d test_db --test-enable -i module --stop-after-init --log-level=test. Use separate test DB — tests create/delete data.

25) Architecture

Design large module?

Split by domain: models/, views/, security/, data/, wizards/, reports/. Base module + feature modules. Abstract mixins for shared behavior. Clear dependencies. Config models for flexibility.

When split module?

When: independent features, different install needs, team ownership, reduce upgrade risk. Keep core + extensions pattern (sale + sale_custom).

Avoid cyclic dependencies?

Extract shared code to base module. Use _inherit without depends when absolutely needed. Event/hook pattern instead of direct imports. Dependency graph review in PR.

SOLID in Odoo?
  • S — one model one responsibility.
  • O — extend via _inherit not modify core.
  • L — overrides respect super contract.
  • I — small mixins vs god models.
  • D — depend on abstractions (config params, mixin interfaces).
Customization vs configuration?

Prefer standard Odoo flows, Studio, server actions, automated actions before custom code. Code when: performance, complex logic, integration, standard doesn't fit. Document why custom was needed.

26) Debugging

AccessError debugging?
  1. Check ACL for user's groups on model.
  2. Check record rules — test domain manually in shell.
  3. Check field-level groups.
  4. Check if sudo() needed (last resort).
  5. Read full traceback — which method, which uid.
Who changed field value?

tracking=True fields show in chatter. Or audit via mail.tracking.value. For untracked: server logs, custom audit model, PG triggers (last resort).

Performance debugging?

--log-sql, Odoo profiler (debug mode), query counter, EXPLAIN ANALYZE, identify N+1, check indexes, monitor worker memory/CPU.

Deadlocks?

Check PG logs for deadlock detail. Fix lock ordering, shorten transactions, retry on OperationalError. Common: two users editing interdependent records.

27) Business Domains

Sales flow?

Quotation (draft) → Sent → Sale Order (confirmed) → Delivery (stock.picking) → Invoice (account.move) → Payment. Each step creates linked documents.

Purchase flow?

RFQ → PO confirmed → Receipt → Vendor Bill. Routes determine auto PO from SO (MTO, dropship).

Inventory basics?

stock.move = individual movement. stock.picking = group of moves. Routes (buy, manufacture, cross-dock). Rules: pull/push. Quant = actual stock in location.

28) سيناريوهات واقعية — الإجابات

سيناريو 1: Approval Workflow
  1. Model approval.stage configurable (sequence, group, email template).
  2. State machine on document: draft → pending_approval → approved → done.
  3. M2M/O2M approval.history for audit trail.
  4. Record rules: each group sees only their stage records.
  5. Server actions / automated actions for notifications.
  6. Don't hardcode stages — config table for future extensibility.
سيناريو 2: Million records slow module
  1. Profile first — don't guess.
  2. Add indexes on filtered/sorted fields.
  3. Convert frequent computed fields to stored.
  4. Replace search-in-loop with batch/SQL/read_group.
  5. Archive old records (active=False).
  6. Pagination on views, limit default searches.
  7. Partition heavy reports to background jobs.
سيناريو 3: Unreliable external system
  1. Outbox table: save payload + status (pending/synced/failed).
  2. Process via queue job with retries.
  3. Idempotency keys prevent duplicates.
  4. Reconciliation cron compares both systems.
  5. Dead letter queue for manual review.
سيناريو 4: 1-hour job — Cron?

No. Use Queue Job or dedicated worker. If must use cron: chunk into 5-min batches with progress field (processed_count/total). Cron timeout will kill long jobs.

سيناريو 5: Multi-company data leak
  1. Reproduce with test users in separate companies.
  2. Audit ir.rule on leaked model — add ('company_id', 'in', company_ids).
  3. Check records with company_id=False (shared).
  4. Review sudo() in controllers.
  5. Fix, deploy, audit all related models.
سيناريو 6: Report 50K invoices slow
  1. Check template — nested loops, t-foreach on lines?
  2. Simplify QWeb — pre-fetch data in report model method.
  3. Use SQL to prepare summary data.
  4. Background report with email notification when ready.
  5. Pagination or date-range splitting.
سيناريo 7: @api.depends with search+write

Problem: infinite recursion — compute triggers write triggers compute again. Fix: move logic out of compute, use write override, or use with_context(skip_compute=True) flag. Never write same model inside its own compute.

سيناريو 8: Legacy data migration
  1. Map fields external → Odoo models.
  2. Staging DB or CSV intermediate.
  3. Script with batch create, tracking_disable.
  4. Validate: record counts, checksums, sample manual review.
  5. post_init_hook for one-time setup.
  6. Rollback plan before go-live.

29) Team Lead & Soft Skills

Code review checklist?
  • Security: ACL, rules, no unnecessary sudo.
  • Performance: no search in loops, stored vs computed choice.
  • Correct API usage: constrains not onchange for validation.
  • Naming, manifest version bump, translations.
  • Tests for critical logic.
  • No hardcoded IDs — use XML IDs.
  • Migration scripts if schema changes.
Task estimation?

Break into subtasks. Estimate best/worst/likely. Add buffer for testing, review, unknowns. Track actual vs estimate to improve. Include dependency wait time.

Technical debt?

Maintain backlog of debt items. Allocate 15-20% sprint capacity. Prioritize debt causing bugs/performance. Refactor when touching area anyway (boy scout rule).

Client wants anti-standard feature?

Explain trade-offs: upgrade pain, maintenance cost, performance. Propose standard alternative. If must customize: document decision, isolate custom code, plan for upgrade impact.

Mentoring juniors?

Pair programming, review with explanations not just fixes, progressive task complexity, share debugging techniques, encourage reading Odoo source code.
