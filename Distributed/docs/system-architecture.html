System architecture

This page is the picture of the commerce platform as the tree implements it after Extension Phases 0–7. Links below are relative paths beside this file.

Two limits.
  • The live saga worker has no command-result reply. Inventory and ERP calls in services/order-service/src/order_service/infrastructure/saga/worker.py return unknown, so that process does not reach COMPLETED against a running Odoo. The eight scenarios drive the orchestrator with test ports. They are not a live Odoo reply.
  • This page was written by reading the tree. Compose and kind were not started to produce it.

Components

The browser and the phone talk only to HTTP through the gateway. They do not open Postgres, RabbitMQ, Redis, or Odoo.

Clients

React storefront

services/frontend. React and Vite. Login, register, products, cart, checkout, orders. The cart stays in the browser (commerce.cart) until checkout posts one order.

Clients

React Native

mobile/react-native-app. Same gateway HTTP API. Auth, catalog, cart, checkout, orders, device tokens. The cart is memory on the device. There is no notification inbox API and no FCM.

Edge

Traefik

deploy/gateway and the kind gateway. Routing, CORS, request IDs, JWT forward-auth, and a coarse in-memory rate limit. Token rules are security.md. Not a business service and not a database owner. kind already runs a second Traefik as the Ingress controller.

Writer

Order service

FastAPI in services/order-service. Owns accounts, the catalog, and orders in order_db. The saga orchestrator is a process in this service, not a separate service. Simulated payment is an adapter here.

Read model

Reporting

Django in services/reporting-service. Projections in reporting_db are eventually consistent. The consumer applies the broker stream in its own transaction.

ERP

Odoo

Odoo 18 Community in services/odoo. CreateErpOrder creates one sales order. OrderConfirmed is recorded and does not create a second sales order. Stock authority stays in odoo_db.

Messages

Flask notifications

services/notification-service and notification_db. Consumes q.notification.delivery. Mock email and mock push. Device-token HTTP only. It does not open order_db.

Shared, not truth

RabbitMQ and Redis

Topic topology commerce-platform-topology, plus the direct exchange commerce.commands. Exchanges, retries, and dead letters are rabbitmq.md. Redis is the product cache, the shared rate limits, and the short order-create lock. It is not the catalog.

Four databases

A transaction does not open more than one of them. Compose runs four Postgres servers: postgres, reporting-postgres, notification-postgres, and odoo-db.

DatabaseOwnerWhat it holds
order_db Order service Accounts, customers, products, orders, order items, the outbox, processed inventory events, inventory snapshots, refresh tokens, and saga_instances. orders.saga_status mirrors the saga row.
reporting_db Django Order, item, product, customer, inventory, and payment projections, plus processed events. They lag the order row until the consumer applies the event.
notification_db Flask device_tokens, processed_events, order_contacts, notification_deliveries. The service refuses a DSN named order_db, reporting_db, or odoo_db.
odoo_db Odoo Odoo’s schema, including sale.order, reservations, and commerce_event_outbox for InventoryUpdated only.

Workflows

Pick a path. Each panel is what the code does today.

  1. The storefront or the React Native app holds the cart locally. Checkout does not send a cart total. Prices are read from order_db when the order is created.
  2. The client calls the gateway. Public auth routes skip JWT forward-auth. Other /api/v1 routes, except /api/v1/internal and device tokens, require it.
  3. POST /api/v1/orders commits the order as PENDING and an OrderCreated outbox row in one order_db transaction. The HTTP handler does not publish. The publisher is outbox.md.
  4. The outbox publisher later sends the envelope to commerce.events. Django may still have no projection row after the create response.

Confirm commits CONFIRMED, saga status STARTED, the saga_instances row, and OrderConfirmed together. It does not call Odoo or the payment adapter. The worker python -m order_service.infrastructure.saga.worker loads non-terminal rows. Compose does not define a saga-worker service.

The happy path the orchestrator knows, when ports report success, is below. COMPLETED means reserve, simulated payment, and ERP create finished. The parcel is still on the order status machine.

confirm → STARTED→ ReserveInventory→ INVENTORY_RESERVED→ simulated charge→ PAYMENT_CONFIRMED→ CreateErpOrder→ ODOO_ORDER_CREATED→ COMPLETED

Against a running Odoo the shipped worker still returns unknown for those commands, because it has no command-result reply. It writes the command to the outbox and does not mark the reservation succeeded. See saga-pattern.md.

After confirm, GET on the order service returns CONFIRMED and saga status STARTED. Django order_projections can still be missing, or PENDING at version 1, until OrderConfirmed is applied. as_of is the newest projection timestamp, not the order-service clock.

PaymentConfirmed and PaymentFailed land in payment_projections only after the reporting consumer applies payment.*. The order status stays CONFIRMED. A recorded refund is not a guaranteed movement of money. The matrix is consistency-models.md.

The notification consumer binds q.notification.delivery to order.confirmed, order.cancelled, order.shipped, order.delivered, payment.confirmed, and payment.failed. It declares that queue itself. Mock adapters append notification_deliveries rows. They do not open SMTP or FCM.

The phone registers a device token with POST /api/v1/device-tokens. The notifications screen reads that list. Session notes stay in the app. There is no inbox endpoint. Detail is flask-notification-service.md.

Product get and list are cache-aside. A hit returns Redis and does not read order_db. A miss or a Redis error reads Postgres. A miss then fills Redis. The TTL is 30 seconds. Create and update delete the product key and list pages after the Postgres commit. Redis and Postgres are not one atomic update.

Get and list record product_cache_hits_total, product_cache_misses_total, product_cache_errors_total, and product_cache_duration_seconds with operation get or list. Those series are on the Dependencies and Platform overview dashboards. Orders are not cached. Login, register, and order create fail closed when Redis is down. See caching-strategy.md.

Ingress public → Ingress-controller Traefik → commerce-gateway Traefik → Service order-service (ClusterIP, port 8000) → ready order pods

The Deployment starts at 2 replicas. Readiness is GET /health/ready. Probe timings and the HPA are kubernetes.md. Compose runs one order-service container, so that path is the kind Service, not Compose. No equal request count was measured. See load-balancing.md.

Saga in the order service

There is no saga service. State is a row in saga_instances, committed with the order and the outbox. Process memory is not the record. Commands go out on commerce.commands: ReserveInventory, ReleaseInventory, CreateErpOrder, CancelErpOrder. Routing and retry are rabbitmq.md. The publisher is outbox.md.

Two machines stay separate. Order status is PENDING → CONFIRMED → PROCESSING → SHIPPED → DELIVERED, and cancel only from PENDING. Saga status is STARTED, INVENTORY_RESERVED, PAYMENT_CONFIRMED, ODOO_ORDER_CREATED, COMPLETED, COMPENSATING, COMPENSATED, FAILED, MANUAL_INTERVENTION_REQUIRED. A payment failure does not cancel the order. Failed compensation becomes MANUAL_INTERVENTION_REQUIRED, not COMPENSATED.

Odoo creates the sales order from CreateErpOrder. Reporting still consumes OrderConfirmed. Warehouse milestones are HTTP calls from Odoo to /api/v1/internal, not broker messages. payment_circuit_state copies the simulated breaker. There is no payment provider.

Django projections

Strong consistency stops at one order_db transaction. reporting_db and odoo_db catch up from events and commands. Stock on the product page is inventory_snapshots, a projection of InventoryUpdated. Odoo remains the stock authority. Saga COMPLETED does not mean DELIVERED.

The lag walkthrough uses the in-memory order unit of work and the reporting suite’s SQLite database. It does not start Compose or kind. The write-up is consistency-models.md.

Flask notifications

Flask listens on port 8002. The consumer exports metrics on port 9100. kind runs two consumer replicas. processed_events.event_id makes a duplicate ack safe. Retry and dead-letter are rabbitmq.md. How to read the series is observability.md.

Email has no address in these payloads, so the mock stores account:<account_id>. Push stores one row per device token, or no-device when the account has none. FCM credentials are not read.

Product cache

Keys are catalog:product:{product_id} and catalog:list:{limit}:{offset}. Every order-service API replica uses the same Redis. There is no per-pod cache and no single-flight lock. A fill that started before a delete can put an old price back until the 30 second TTL.

Ingress path

On kind the public Ingress selects the gateway Service. That Ingress controller does not load the commerce route file. The commerce gateway loads deploy/compose/dynamic.yaml and forwards http://order-service:8000 to the Kubernetes Service, which selects ready pods. The route file does not list pod addresses.

Traefik sends /api/v1/reports to Django, /api/v1/device-tokens to Flask, and the rest of the public API to the order service. Other paths, except /ping, go to the storefront. The gateway does not route /health/live, /health/ready, or /api/v1/internal.

Storefront and phone

Both clients use the gateway. The React cart is browser storage. The React Native cart is on the device and is cleared in memory after checkout. Neither client owns saga state. The phone’s notifications screen is device tokens plus notes kept in the app. The app was not launched on a device or emulator. Commands from this machine are in the app README.

What is not drawn

  • A separate saga service.
  • A real payment provider. Payment is SimulatedPayment inside the order service.
  • FCM, SMTP, or a notification inbox API.
  • A server-side cart. The cart is on the device, or in the browser for the storefront.
  • A sales order created from OrderConfirmed.
  • Saga COMPLETED as parcel delivery.
