المفاهيم الأساسية — Core Concepts

اللبنة الأساسية اللي بيتبني عليها كل حاجة
🗄️ Table, Row, Column
  • Table: جدول لتخزين بيانات من نفس النوع
  • Row (Record/Tuple): صف = سجل واحد من البيانات
  • Column (Attribute): عمود = خاصية أو حقل
  • Schema: الهيكل العام لقاعدة البيانات
🔑 Primary Key & Foreign Key
  • Primary Key: معرف فريد لكل row — لا يتكرر، مش null
  • Foreign Key: بيشاور على PK في جدول تاني لربط الجداول
  • Composite Key: مفتاح مكوّن من أكتر من عمود
  • Surrogate Key: ID اصطناعي (مش بيانات حقيقية)
📋 Data Types الشائعة
  • INT / BIGINT: أعداد صحيحة
  • VARCHAR(n): نص بطول متغير
  • TEXT: نص طويل
  • DATE / DATETIME / TIMESTAMP: تواريخ وأوقات
  • BOOLEAN: true/false
  • DECIMAL(p,s): أعداد عشرية دقيقة
⚙️ Constraints
  • NOT NULL: الحقل لازم يكون فيه قيمة
  • UNIQUE: القيمة لا تتكرر في العمود
  • CHECK: شرط على البيانات (مثلاً age > 0)
  • DEFAULT: قيمة افتراضية لو مفيش قيمة
  • PRIMARY KEY: NOT NULL + UNIQUE
  • FOREIGN KEY: تكامل المراجع
SQL — إنشاء جدول مع Constraints
CREATE TABLE students (
    id         INT           PRIMARY KEY AUTO_INCREMENT,
    name       VARCHAR(100)  NOT NULL,
    email      VARCHAR(150)  UNIQUE NOT NULL,
    age        INT           CHECK (age > 0 AND age < 120),
    gpa        DECIMAL(3,2) DEFAULT 0.00,
    dept_id    INT,
    created_at TIMESTAMP    DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (dept_id) REFERENCES departments(id)
);
02

SQL Language

DDL · DML · DCL · TCL
🏗️ DDL — Data Definition Language
  • CREATE: إنشاء جدول/قاعدة بيانات/view
  • ALTER: تعديل هيكل جدول موجود
  • DROP: حذف الجدول كله مع بياناته
  • TRUNCATE: مسح كل البيانات وبس (أسرع من DELETE)
  • RENAME: إعادة تسمية جدول
✏️ DML — Data Manipulation Language
  • SELECT: جلب بيانات
  • INSERT: إضافة بيانات
  • UPDATE: تحديث بيانات موجودة
  • DELETE: حذف صفوف محددة
  • MERGE: دمج INSERT + UPDATE (Upsert)
🔐 DCL — Data Control Language
  • GRANT: إعطاء صلاحيات لمستخدم
  • REVOKE: سحب الصلاحيات
🔄 TCL — Transaction Control Language
  • COMMIT: تأكيد التغييرات وحفظها
  • ROLLBACK: التراجع عن التغييرات
  • SAVEPOINT: نقطة وسطية للتراجع ليها
  • SET TRANSACTION: تحديد خصائص الـ transaction
SQL — أمثلة عملية
-- DDL
ALTER TABLE students ADD COLUMN phone VARCHAR(20);
ALTER TABLE students DROP COLUMN phone;

-- DML
INSERT INTO students (name, email, age) 
VALUES ('أحمد', 'ahmed@email.com', 22);

UPDATE students SET gpa = 3.8 WHERE id = 1;

DELETE FROM students WHERE age < 18;

-- DCL
GRANT SELECT, INSERT ON students TO 'user1';
REVOKE INSERT ON students FROM 'user1';
03

Joins — ربط الجداول

أهم حاجة في الـ SQL وبتتسأل فيها كتير في الـ Interviews
INNER JOIN
بيجيب الصفوف اللي ليها تطابق في الجدولين — التقاطع فقط
LEFT JOIN (LEFT OUTER)
كل الجدول الأيسر + التطابقات من الأيمن. اللي ملوش تطابق بيجيلو NULL
RIGHT JOIN (RIGHT OUTER)
عكس LEFT JOIN — كل الجدول الأيمن + التطابقات من الأيسر
FULL OUTER JOIN
كل الصفوف من الجدولين. اللي ملوش تطابق بيجيلو NULL في العمود التاني
✕
CROSS JOIN
الـ Cartesian Product — كل صف من الأول مع كل صف من التاني (n × m صف)
🔁
SELF JOIN
الجدول بيعمل JOIN مع نفسه — مفيد في الهياكل الشجرية (employee → manager)
SQL — أمثلة على Joins
-- INNER JOIN: الطلاب اللي ليهم قسم
SELECT s.name, d.dept_name
FROM students s
INNER JOIN departments d ON s.dept_id = d.id;

-- LEFT JOIN: كل الطلاب (حتى اللي مفيهمش قسم)
SELECT s.name, d.dept_name
FROM students s
LEFT JOIN departments d ON s.dept_id = d.id;

-- SELF JOIN: الموظف ومديره
SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.id;

Normalization — التسوية

إزاي تنظم جداولك عشان تتجنب التكرار والمشاكل
💡
ليه Normalization؟
لتجنب: Data Redundancy (تكرار البيانات) · Update Anomaly · Insert Anomaly · Delete Anomaly
1NF — First Normal Form
القاعدة: كل خلية فيها قيمة واحدة فقط (Atomic) + لا تكرار في الصفوف
✗ غلط: عمود "phones" فيه "01001, 01002" | ✓ صح: صف لكل رقم
2NF — Second Normal Form
القاعدة: 1NF + كل عمود non-key يعتمد على الـ Primary Key كلها (مش جزء منها)
بيطبق بس لو في Composite Key. أي Partial Dependency لازم يتحل بجدول منفصل
3NF — Third Normal Form
القاعدة: 2NF + لا Transitive Dependency (A→B→C مش مقبول)
مثال: student → dept_id → dept_name — لازم dept_name يكون في جدول departments
BCNF — Boyce-Codd Normal Form
القاعدة: إصدار أقوى من 3NF — كل Determinant لازم يكون Candidate Key
بيحل حالات نادرة ما بيحلهاش 3NF في حالة أكتر من Candidate Key
4NF & 5NF
للحالات المتقدمة: تتعامل مع Multi-valued Dependencies و Join Dependencies
نادر الاستخدام في العملي — أكتر نظري
⚠️
Denormalization
أحياناً بنتراجع عن الـ Normalization عمداً لتحسين الـ Performance في حالات الـ Read-heavy مثل Data Warehouses — بنضيف بيانات مكررة عشان نتجنب كتير من الـ Joins.

Indexes — الفهارس

بيسرعوا الـ queries بشكل ضخم لو اتعملوا صح
📌 Clustered Index
  • ترتيب البيانات الفعلي في الـ disk بيكون بترتيبه
  • واحد بس لكل جدول (عادةً الـ PK)
  • أسرع للـ range queries
📌 Non-Clustered Index
  • هيكل منفصل بيشاور على البيانات الأصلية
  • ممكن يكون عندك أكتر من واحد
  • مفيد للـ columns اللي بتبحث بيها كتير
📌 Composite Index
  • Index على أكتر من عمود مع بعض
  • ترتيب الأعمدة مهم جداً (Leftmost Prefix Rule)
  • مثال: (last_name, first_name)
📌 Unique Index & Full-Text
  • Unique: يمنع تكرار القيم في العمود
  • Full-Text: للبحث النصي الذكي (MATCH AGAINST)
  • Partial Index: Index على جزء من البيانات بشرط
⚠️
Indexes مش دايماً كويسة!
الـ Index بيبطأ الـ INSERT/UPDATE/DELETE لأنه بيحتاج يتحدث. استخدمه بس على الأعمدة اللي بتبحث بيها أو بتعمل عليها JOIN كتير.
SQL — إنشاء Index
-- Non-Clustered Index بسيط
CREATE INDEX idx_student_email ON students(email);

-- Composite Index
CREATE INDEX idx_name ON students(last_name, first_name);

-- Unique Index
CREATE UNIQUE INDEX idx_unique_email ON students(email);

-- شوف الـ Index بيتستخدم ولا لأ
EXPLAIN SELECT * FROM students WHERE email = 'ahmed@email.com';

Transactions & ACID

ضمان سلامة البيانات حتى لو في أعطال
A
Atomicity
الـ Transaction كلها تنجح أو كلها تفشل — مفيش نص عملية
C
Consistency
البيانات دايماً في حالة صحيحة قبل وبعد الـ Transaction
I
Isolation
كل Transaction معزولة عن التانية — مش بيشوفوا بعض وهم شغالين
D
Durability
بعد الـ COMMIT البيانات اتحفظت — حتى لو في crash

🔒 Isolation Levels

Isolation Level Dirty Read Non-Repeatable Read Phantom Read أداء
Read Uncommitted ✅ ممكن✅ ممكن✅ ممكن أسرع
Read Committed ❌ ممنوع✅ ممكن✅ ممكن متوسط
Repeatable Read ❌ ممنوع❌ ممنوع✅ ممكن متوسط
Serializable ❌ ممنوع❌ ممنوع❌ ممنوع أبطأ
SQL — Transaction Example
START TRANSACTION;

-- تحويل فلوس من حساب لحساب
UPDATE accounts SET balance = balance - 1000 WHERE id = 1;
UPDATE accounts SET balance = balance + 1000 WHERE id = 2;

-- لو كل حاجة تمام
COMMIT;

-- لو في مشكلة
-- ROLLBACK;

-- SAVEPOINT
SAVEPOINT after_first_update;
ROLLBACK TO after_first_update;

Stored Procedures, Functions, Views & Triggers

منطق البيزنس جوه قاعدة البيانات
⚙️ Stored Procedure
  • كود SQL محفوظ ومُسمى — بتناديه بـ CALL
  • ممكن يرجع قيم (OUT parameters)
  • بيتنفذ على السيرفر مباشرةً
  • ممكن فيه Control Flow (IF, LOOP, WHILE)
🔢 User-Defined Functions (UDFs)
  • زي Procedure لكن بترجع قيمة واحدة دايماً
  • ممكن تستخدمها جوه SELECT
  • مش بتعمل تعديل على البيانات (Scalar Function)
  • Table-Valued Functions بترجع جدول
👁️ Views
  • Query محفوظة تشتغل كأنها جدول افتراضي
  • بتبسط الـ complex queries
  • بتخفي بيانات حساسة
  • لا بتحفظ بيانات (إلا Materialized View)
⚡ Triggers
  • كود بيتنفذ أوتوماتيك عند INSERT/UPDATE/DELETE
  • BEFORE / AFTER trigger
  • مفيد للـ Audit logs والـ Validation
  • لكن بيصعّد الـ Debugging
SQL — أمثلة
-- View
CREATE VIEW top_students AS
SELECT name, gpa FROM students WHERE gpa > 3.5;

SELECT * FROM top_students; -- بتستخدمها كجدول عادي

-- Stored Procedure
CREATE PROCEDURE GetStudentsByDept(IN dept_id INT)
BEGIN
    SELECT * FROM students WHERE dept_id = dept_id;
END;

CALL GetStudentsByDept(3);

-- Trigger: Audit log عند الحذف
CREATE TRIGGER before_student_delete
BEFORE DELETE ON students
FOR EACH ROW
BEGIN
    INSERT INTO audit_log(action, student_id, deleted_at)
    VALUES ('DELETE', OLD.id, NOW());
END;

Query Optimization

اعمل الـ query أسرع بدون تغيير النتيجة
🔍 Execution Plan
  • استخدم EXPLAIN / EXPLAIN ANALYZE قبل أي query
  • شوف الـ cost وعدد الصفوف المتوقعة
  • دور على Full Table Scans وشيلها
  • في PostgreSQL: EXPLAIN (ANALYZE, BUFFERS)
🚀 أهم Tips للـ Optimization
  • استخدم Indexes على الأعمدة اللي في WHERE / JOIN
  • اجتنب SELECT * — حدد الأعمدة اللي محتاجها
  • اجتنب Functions على الأعمدة في WHERE (بتعطل الـ Index)
  • استخدم EXISTS بدل IN لو الـ subquery كبيرة
  • LIMIT الـ results لو مش محتاج كلها
⚠️ أسباب بطء الـ Query
  • Full Table Scan (مفيش Index)
  • N+1 Query Problem
  • Missing JOIN Conditions
  • Implicit Type Conversion
  • Non-SARGable WHERE clause
SQL — Optimization Examples
-- ❌ بطيء: Function على العمود بتعطل الـ Index
SELECT * FROM students WHERE YEAR(created_at) = 2024;

-- ✅ سريع: Range condition بيستخدم الـ Index
SELECT * FROM students 
WHERE created_at BETWEEN '2024-01-01' AND '2024-12-31';

-- ❌ بطيء: IN مع subquery كبيرة
SELECT * FROM students WHERE id IN (SELECT student_id FROM enrollments);

-- ✅ سريع: EXISTS
SELECT * FROM students s
WHERE EXISTS (SELECT 1 FROM enrollments e WHERE e.student_id = s.id);

Relationships — أنواع العلاقات

إزاي الجداول بتتكلم مع بعض
1️⃣ One-to-One (1:1)
  • كل صف في جدول A ليه صف واحد بالظبط في B
  • مثال: User ↔ UserProfile
  • التطبيق: FK في أي جدول مع UNIQUE constraint
1️⃣➕ One-to-Many (1:N)
  • الأكثر شيوعاً — صف واحد في A ليه أكتر من صف في B
  • مثال: Department (1) ↔ Students (N)
  • التطبيق: FK في الجدول "الكتير"
➕➕ Many-to-Many (M:N)
  • صف في A ممكن يتصل بأكتر من صف في B والعكس
  • مثال: Students ↔ Courses
  • التطبيق: Junction Table (Enrollments) فيها FKs من الجدولين
🔁 Self-Referencing
  • الجدول بيشاور على نفسه
  • مثال: Employee → Manager (نفس جدول employees)
  • مفيد للهياكل الشجرية والـ Hierarchies

Subqueries & Advanced SQL

CTEs · Window Functions · Correlated Subqueries
SQL — Subqueries
-- Subquery في WHERE
SELECT name FROM students
WHERE gpa > (SELECT AVG(gpa) FROM students);

-- Correlated Subquery (بتتنفذ لكل صف)
SELECT name, gpa
FROM students s1
WHERE gpa > (SELECT AVG(gpa) FROM students s2 
               WHERE s2.dept_id = s1.dept_id);

-- CTE (Common Table Expression)
WITH dept_avg AS (
    SELECT dept_id, AVG(gpa) AS avg_gpa
    FROM students
    GROUP BY dept_id
)
SELECT s.name, s.gpa, d.avg_gpa
FROM students s
JOIN dept_avg d ON s.dept_id = d.dept_id;
SQL — Window Functions
-- ROW_NUMBER: ترقيم الصفوف في كل قسم
SELECT name, dept_id, gpa,
    ROW_NUMBER() OVER (PARTITION BY dept_id ORDER BY gpa DESC) AS rank_in_dept
FROM students;

-- RANK vs DENSE_RANK
-- RANK: 1,2,2,4  |  DENSE_RANK: 1,2,2,3
RANK() OVER (ORDER BY gpa DESC)
DENSE_RANK() OVER (ORDER BY gpa DESC)

-- LAG / LEAD: القيمة قبل / بعد
SELECT name, gpa,
    LAG(gpa) OVER (ORDER BY id) AS prev_gpa,
    LEAD(gpa) OVER (ORDER BY id) AS next_gpa
FROM students;

Aggregate Functions & Grouping

تلخيص وتجميع البيانات
SQL — Aggregation
-- الـ Aggregate Functions الأساسية
SELECT
    COUNT(*)         AS total_students,
    COUNT(DISTINCT dept_id) AS num_depts,
    AVG(gpa)          AS avg_gpa,
    MAX(gpa)          AS highest_gpa,
    MIN(gpa)          AS lowest_gpa,
    SUM(gpa)          AS sum_gpa
FROM students;

-- GROUP BY + HAVING
SELECT dept_id, AVG(gpa) AS avg_gpa, COUNT(*) AS num_students
FROM students
GROUP BY dept_id
HAVING AVG(gpa) > 3.0   -- HAVING بيفلتر بعد GROUP BY
ORDER BY avg_gpa DESC;

-- ROLLUP: بيضيف Total rows
SELECT dept_id, COUNT(*)
FROM students
GROUP BY dept_id WITH ROLLUP;
💡
WHERE vs HAVING
WHERE بيفلتر الصفوف قبل الـ Grouping — HAVING بيفلتر بعد الـ Grouping. مينفعش تستخدم Aggregate Function في WHERE.

Database Design — ER Diagram

التصميم الصح قبل ما تكتب سطر SQL
🔷 Entities & Attributes
  • Entity: شيء بنحفظ بياناته (مثل: Student, Course)
  • Attribute: خاصية للـ Entity (name, age, gpa)
  • Key Attribute: بيميز الـ Entity (underlined في الـ ER)
  • Derived Attribute: بيتحسب من attribute تاني (العمر من تاريخ الميلاد)
  • Multi-valued Attribute: ممكن يكون فيه أكتر من قيمة (phone numbers)
🔗 Relationships & Cardinality
  • Cardinality: عدد الـ instances في العلاقة (1:1, 1:N, M:N)
  • Participation: Total (لازم يشارك) أو Partial (اختياري)
  • Weak Entity: Entity مش ليها PK خاص بيها — بتعتمد على entity تانية
  • ISA Relationship: للـ Inheritance (Employee → Manager, Technician)
🗂️ تحويل ER → Tables
  • كل Entity بتبقى Table
  • 1:N — FK في الجانب الـ N
  • M:N — Junction Table جديدة
  • 1:1 — FK في أي جدول (الأقل وصول)
  • Multi-valued Attribute — جدول منفصل

Concurrency Control

إزاي تتعامل مع أكتر من user في نفس الوقت
🔒 Locking
  • Shared Lock (S): للقراءة — أكتر من واحد يقدر يقرأ في نفس الوقت
  • Exclusive Lock (X): للكتابة — واحد بس والباقيين بيستنوا
  • Row-Level Lock: أدق وأقل blocking
  • Table-Level Lock: أبسط لكن أكتر blocking
💀 Deadlocks
  • A بتستنى B ، وB بتستنى A → طوق مغلق
  • الـ DB بيكتشفها أوتوماتيك ويعمل ROLLBACK لواحدة
  • الحل: ترتيب ثابت للـ locks
  • Timeout يتحكم في وقت الانتظار
⚖️ Optimistic vs Pessimistic
  • Pessimistic: لوك من الأول — مناسب لو التعارضات كتيرة
  • Optimistic: مفيش لوك — بيتأكد عند الـ Commit — مناسب لو التعارضات نادرة
  • MVCC: كل transaction بتشوف snapshot من البيانات — بيقلل الـ locking

Backup & Recovery

حماية البيانات من الضياع
نوع الـ Backup إيه اللي بيعمله المساحة وقت الاستعادة
Full Backup نسخة كاملة من كل حاجة كبيرة أسرع
Incremental Backup بس التغييرات من آخر backup (أي نوع) صغيرة جداً أبطأ (محتاج كل الـ incrementals)
Differential Backup التغييرات من آخر Full Backup متوسطة متوسط (Full + آخر Differential)
🕒 Point-in-Time Recovery
  • تقدر ترجع لأي لحظة في التاريخ
  • بيعتمد على Transaction Logs
  • مهم جداً في Production
📋 Transaction Logs (WAL)
  • Write-Ahead Log: بيتسجل التغيير قبل ما يتعمل
  • بيضمن الـ Durability في الـ ACID
  • مصدر الـ Point-in-Time Recovery

Security

حماية قاعدة البيانات من الهجمات والتسريب
👤 Authentication vs Authorization
  • Authentication: إثبات هويتك (مين أنت؟)
  • Authorization: إيه اللي مسموحك تعمله
  • Roles: مجموعة صلاحيات متجمعة مع بعض
  • Principle of Least Privilege: مديله بس اللي محتاجه
💉 SQL Injection
  • المهاجم بيضيف SQL code جوه الـ Input
  • مثال: '; DROP TABLE users; --
  • ✅ الحماية: Prepared Statements / Parameterized Queries
  • ✅ اعمل Input Validation دايماً
  • ✅ ORM بيحميك بشكل تلقائي غالباً
🔐 Encryption
  • At Rest: البيانات المخزنة على الـ disk مشفرة
  • In Transit: TLS/SSL للبيانات اللي بتتنقل
  • Column-level: تشفير أعمدة حساسة بس (passwords, credit cards)
  • استخدم bcrypt/Argon2 للـ passwords مش MD5

Scalability & Performance

لما البيانات تكبر والـ traffic يزيد
📦 Partitioning
  • Horizontal (Row): تقسيم الصفوف على partitions (مثلاً بالسنة)
  • Vertical (Column): تقسيم الأعمدة — الأعمدة الكتير المستخدمة في جدول منفصل
  • بيحسن الـ query performance على جداول ضخمة
🌐 Sharding
  • Horizontal partitioning على مستوى سيرفرات مختلفة
  • كل Shard = قاعدة بيانات مستقلة
  • بيحل مشكلة الـ Scale لكن بيزود الـ complexity
🔄 Replication
  • Master-Slave: Master للكتابة، Slaves للقراءة
  • Master-Master: الاثنين بيقدروا يكتبوا — أصعب تزامناً
  • بيزود الـ availability والـ read performance
🚀 Connection Pooling & Caching
  • Connection Pool: بيحافظ على connections جاهزة بدل ما تفتح وتقفل كل مرة
  • Query Cache: نتيجة الـ Query المتكررة بتتحفظ
  • Redis Layer: بتخزن الـ hot data في memory — أسرع بكتير

CAP Theorem
أي distributed system مقدرش يضمن الـ 3 مع بعض: Consistency + Availability + Partition Tolerance. RDBMS بيختار C+A، وكتير من NoSQL بيختار A+P.

ORM — Object-Relational Mapping

بتتكلم مع الـ DB بكود مش بـ SQL
❓ إيه هو ORM؟
  • Layer بتحوّل الـ Objects في الكود لـ SQL وبالعكس
  • بتشتغل مع الـ DB بلغة البرمجة العادية
  • مش محتاج تكتب SQL بإيدك (غالباً)
📦 أمثلة ORMs
  • Hibernate: Java
  • SQLAlchemy: Python
  • Entity Framework: .NET / C#
  • Sequelize / Prisma: Node.js
  • ActiveRecord: Ruby on Rails
  • Django ORM: Python/Django
⚖️ Pros vs Cons
  • ✅ أسرع في الـ Development
  • ✅ Database Agnostic
  • ✅ حماية من SQL Injection
  • ❌ ممكن يولد queries غير كفؤة
  • ❌ N+1 Query Problem شائعة
  • ❌ بيحتاج فهم الـ SQL الأساسي
