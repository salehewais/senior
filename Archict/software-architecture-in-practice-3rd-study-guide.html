Cheat sheet

Structures and views

A structure is a set of elements, their relations, and properties of both. A view is a representation of one structure, written for an audience. There is no single picture that is “the” architecture. Three families recur: module (static implementation units), component-and-connector (runtime elements and their attachments), and allocation (mapping software onto hardware, teams, or files).

Architecturally significant requirements

An ASR is a requirement that has a profound effect on the architecture. Most ASRs are quality-attribute requirements written as scenarios, plus a few constraints. Functionality alone rarely picks the architecture; many structures can compute the same functions with very different quality.

Scenarios

A usable quality requirement has six parts: source, stimulus, environment, artifact, response, response measure. A general scenario is a template for a quality attribute. A concrete scenario fills it in for one system and can be tested.

Tactics versus patterns

A tactic is a design decision that controls the response to a quality-attribute stimulus. A pattern is a named package of elements, relations, and tactics that solves a recurring problem in a context. Patterns are where tactics live together — and where their side effects show up.

Tradeoffs

A decision that helps one quality often hurts another. Name the sensitivity point (a property the response measure depends on) and the tradeoff point (a sensitivity point for more than one quality). Methods such as ATAM find these; CBAM asks which tradeoff is worth the money.

Part I — Introduction

Chapters 1–3 fix the vocabulary: architecture as structures you can reason with, the reasons a project invests in it, and the cycle of influence between architecture and its environment.

Chapter 1

What Is Software Architecture?

Study notes

  • Architecture is the set of structures needed to reason about the system: software elements, relations among them, and properties of both. “Early” or “major” decisions are a weaker definition, because many early decisions are not architectural and some architectural decisions arrive late.
  • Architecture is an abstraction. It keeps the information required for analysis and drops detail that does not affect the reasoning you care about.
  • Every system has an architecture, documented or not. Behavior belongs in the architecture when you need it to reason about qualities such as performance or availability. Having an architecture does not mean it is a good one.
  • Three structure families: module (code units), component-and-connector (runtime), and allocation (software mapped to the environment). A view documents one structure for a stakeholder.
  • A pattern is a reusable bundle of elements and relations that addresses a recurring problem. Choosing a pattern is choosing a package of quality consequences.
  • A “good” architecture is good for stated goals. The chapter separates process advice (who decides, document, evaluate, build incrementally) from product advice (clear modules and interfaces, few interaction styles, isolated commercial dependencies, few contention points).
  • Connects forward: structures are what later chapters analyze; patterns return in Chapter 13; views return in Chapter 18.
Exam deep dive

Key terms

Architecture
Structures of elements, relations, and properties sufficient to reason about the system.
Element
A piece of the structure. In a module structure it is a code unit; in a C&C structure a component is a runtime entity.
View
A representation of a structure, with a notation and an audience.
Module structures
Decomposition (is-a-submodule-of), uses (correctness dependency), layers (allowed-to-use), generalization (inherits-from), data model.
C&C structures
Runtime attachment. Examples: service structure, concurrency structure. Relation is attachment, not “uses.”
Allocation structures
Deployment (software onto hardware), implementation (modules onto files), work assignment (modules onto teams).
Pattern
A named, recurring design of elements and relations with known quality consequences.

What to be able to do

  • Give the book’s definition and say why “the major early decisions” is not the definition they want.
  • Classify a diagram as module, C&C, or allocation, and name which quality it helps you reason about.
  • List process recommendations and product recommendations for a sound architecture, in your own words.
Practice prompts

A teammate says the architecture is “the UML class diagram plus the database schema.” Which structures are missing, and what questions can you no longer answer?

The uses structure and the decomposition structure both contain modules. When would you consult one and ignore the other?

Pick a system you know. Name one module structure, one C&C structure, and one allocation structure that an architect would actually keep.

Chapter 2

Why Is Software Architecture Important?

Study notes

  • Architecture is the primary carrier of the system’s quality attributes. The same function set can be easy or hard to change, fast or slow, safe or fragile, depending on structure.
  • It is also a vehicle for managing change: likely changes should fall inside few modules, and the uses relation tells you what else must be present.
  • Early structures let you predict qualities (by analysis, models, or evaluation) before the code exists, and they constrain implementers so independent teams can build pieces that still fit.
  • Architecture is a communication medium among stakeholders who do not share a vocabulary. It also shapes the organization: work-assignment and team communication tend to follow the module structure.
  • Other payoffs: evolutionary prototyping along the architecture, better cost and schedule estimates, a reusable model for the next system, a smaller design vocabulary (patterns and tactics), and a basis for training new people.
  • Connects forward: prediction motivates Chapters 14 and 21; constraints on implementation motivate Chapters 19 and 20; reuse of a whole architecture motivates Chapter 25.
Exam deep dive

  2. Supports reasoning about and managing change
  3. Lets you predict system qualities
  4. Improves communication among stakeholders
  5. Carries the earliest hard-to-change design decisions
  6. Defines constraints on the implementation
  7. Influences the organizational structure
  8. Enables evolutionary prototyping
  9. Improves cost and schedule estimates
  10. Supplies a transferable, reusable model
  11. Allows independently developed components to be integrated
  12. Restricts the vocabulary of design alternatives

On an exam, do not stop at the label. Attach each role to a stakeholder who cares (customer, project manager, developer, new hire, acquirer).

Practice prompts

A manager says architecture work is “documentation overhead.” Which three roles from this chapter answer that claim for a project that will live five years and be built by four teams?

Explain, with a small example, how an architecture both enables a quality attribute and inhibits another one at the same time.

Chapter 3

The Many Contexts of Software Architecture

Study notes

  • Architecture sits in four contexts at once: technical (qualities, patterns, platforms), project life cycle (when architecture work happens), business (cost, schedule, market, organization), and professional (what the architect has seen and believes).
  • Stakeholders are people or groups with a concern. Different concerns demand different views. Missing a stakeholder usually means missing an ASR.
  • The architecture influence cycle: the developing organization, the technical environment, the customer’s business goals, and the architect’s experience shape the architecture. The finished architecture then shapes the organization, the technical environment, and the architect’s next project.
  • Professional context matters because architects reuse what worked for them. That bias should be examined, not denied.
  • Life-cycle context is the bridge into Part III: requirements, design, documentation, implementation, evaluation, and conformance are architecture activities, not a single phase called “architecting.”
Exam deep dive

Key terms

Stakeholder
Anyone with a stake in the system’s construction or operation. Concerns, not job titles, drive which views you produce.
Influence cycle
Environment and experience shape the architecture; the architecture feeds back into the organization and the next design.
Architecturally significant
A requirement or constraint that will change the structures you choose if it changes.

Four contexts

  • Technical — qualities, structures, existing platforms, standards.
  • Project life cycle — where architecture work sits relative to requirements, build, and test.
  • Business — time to market, cost, market differentiation, organizational politics.
  • Professional — education, prior systems, taste for particular patterns.
Practice prompts

Draw the influence cycle for a university registration system. Name one influence coming in and one influence the architecture will send back out.

Two architects propose different patterns for the same requirements. Using the professional context, why might both proposals be rational — and how would you decide?

List six stakeholders for an online bank and one concern each. Which concerns are unlikely to show up in a class diagram?

Chapters 4–14 are the technical core. Learn the six-part scenario and the seven design-decision categories once (Chapter 4), then reuse them for every quality attribute.

Chapter 4

Understanding Quality Attributes

Study notes

  • Requirements that matter to an architect fall into functional requirements, quality-attribute requirements, and constraints. Functionality says what the system does. Quality attributes say how well, under which conditions. Constraints remove design freedom.
  • Functionality and architecture are not the same axis. Many architectures can deliver the same functions. Quality attributes are what force a particular structure.
  • Quality-attribute names (“security,” “modifiability”) are too vague to design or test against. A scenario makes the requirement concrete and measurable.
  • A tactic is a design option aimed at controlling a quality-attribute response. Tactics are the atoms; later chapters group them and show them inside patterns.
  • Seven categories of design decisions recur in every quality-attribute checklist: allocation of responsibilities, coordination model, data model, resource management, mapping among elements, binding time, and choice of technology.
  • Qualities are not independent. The point of the chapter is a shared specification method so Chapters 5–13 can be compared.
Exam deep dive

Key terms

Quality attribute
A measurable property of the system’s response, distinct from the function being computed.
General scenario
A system-independent template for one quality attribute.
Concrete scenario
A general scenario filled in for a particular system; the response measure makes it testable.
Tactic
A design decision that influences the control of a quality-attribute response.
Constraint
A design decision that has already been made, or an imposed limit (platform, standard, deadline).

Six-part quality-attribute scenario

SourceWho or what generates the stimulus (user, external system, clock, attacker).
StimulusThe condition that arrives and needs a response.
EnvironmentThe conditions in force (normal load, overload, startup, attack already underway).
ArtifactWhat is stimulated: whole system, a process, a data store, a collection of systems.
ResponseWhat the system does when the stimulus arrives.
Response measureHow you know the response was good enough (time, percentage, effort, audit record).

Seven design-decision categories

These are the rows of every design checklist in Chapters 5–11. They are themes, not a copied table from the book.

  1. Allocation of responsibilities — who detects, who reacts, who records.
  2. Coordination model — how elements synchronize, what protocols they use, whether communication can change.
  3. Data model — what data is shared, copied, or kept consistent, and which entities matter to this quality.
  4. Management of resources — what resources exist and how contention is handled.
  5. Mapping among architectural elements — modules to runtime elements, runtime elements to processors, and so on.
  6. Binding time — when a decision is fixed: design, compile, deploy, startup, or runtime.
  7. Choice of technology — what the platform already gives you, and what you must build.
Practice prompts

Turn “the system shall be highly available” into a six-part scenario with a numeric response measure. Then turn “the system shall be easy to modify” into another. Which part was hardest to make measurable?

A requirement says the system must run on Linux. Is that a functional requirement, a quality attribute, or a constraint? What design freedom does it remove?

Why can two systems with identical functionality have opposite modifiability? Use the words structure and tactic in the answer.

Chapter 5

Availability

Study notes

  • Availability is readiness to deliver a service that still matches the specification. A fault is an internal defect that may become an error and then an observable failure. Tactics exist so faults do not become failures, or so the failure is bounded and repair is possible.
  • A common numeric form is MTBF / (MTBF + MTTR): lengthen the time between failures or shorten repair. Scheduled downtime is a design choice, not “free” availability.
  • Tactic families: detect faults, recover from faults (prepare and repair, then reintroduce), and prevent faults. Much of this is chosen from a platform rather than hand-built.
  • Redundancy is the workhorse of recovery, but copies must be managed: active (hot), passive (warm), and spare (cold) differ in switchover time and cost. State has to be resynchronized or the backup is a second source of faults.
  • The design checklist walks the seven decision categories with availability questions: who detects, how components coordinate during failover, where state lives, which resources are replicated, and when a failed node may rejoin.
  • Connects to security (recovery from attack reuses these tactics) and to performance (redundancy and voting add overhead).
Exam deep dive

Key terms

Fault
A defect or event that can cause an incorrect internal state.
Failure
A delivered service that no longer matches the specification, visible to an actor.
MTBF / MTTR
Mean time between failures and mean time to repair. Availability grows if either the interval grows or the repair shrinks.

General scenario shape

SourceInternal fault or an external indication of a fault.
StimulusA fault: crash, timing fault, incorrect response, omission.
EnvironmentNormal operation, startup, shutdown, repair mode, degraded mode.
ArtifactProcess, processor, channel, storage, the whole system.
ResponseDetect, log, notify, disable the source, be unavailable briefly, continue in degraded mode, and so on.
MeasureAvailability percentage, detection time, repair time, fraction of faults masked, allowed downtime.

Tactic categories

Detect faults
  • Ping/echo, monitor, heartbeat, timestamp
  • Sanity checking, condition monitoring, voting
  • Exception detection, self-test
Recover — preparation and repair
  • Active redundancy, passive redundancy, spare
  • Exception handling, rollback, software upgrade, retry
  • Ignore faulty behavior, degradation, reconfiguration
Recover — reintroduction
  • Shadow, state resynchronization, escalating restart, non-stop forwarding
Prevent faults
  • Removal from service, transactions, predictive model, exception prevention, increase competence set

Checklist themes

Ask, for each of the seven decision categories: where faults are detected, which component is allowed to fail over, how state is checkpointed, which processors are replicas, and whether a node can re-enter without a full outage.

Practice prompts

A payment service must keep answering within 2 seconds even if one data-center process dies. Write the scenario, then pick one detect tactic and one recover tactic and say what each costs in performance.

Contrast active redundancy, passive redundancy, and spare for a student-facing exam server. Which response measure changes as you move from hot to cold?

Why is “retry” both a recovery tactic and a possible cause of further failure? What would you pair it with?

Chapter 6

Interoperability

Study notes

  • Interoperability is the degree to which two or more systems can usefully exchange information. It has a syntactic side (can the bits be exchanged and parsed?) and a semantic side (do both sides mean the same thing?).
  • The stimulus is usually a request to exchange information or to cooperate on a task. The response is that the request is accepted and correctly handled, or rejected with a clear reason.
  • Two tactic groups: locate (discover a service at runtime) and manage interfaces (orchestrate a sequence of calls, or tailor an interface by adding or hiding capabilities such as translation and buffering).
  • Orchestration coordinates services that may not know about each other. Tailoring an interface is how you absorb a partner’s odd protocol without letting it leak through the system.
  • The third edition gives interoperability its own chapter because systems of systems, services, and the cloud made “it speaks our protocol” a first-class architectural problem, not a footnote of modifiability.
Exam deep dive

General scenario shape

SourceA system that wants to interoperate with ours.
StimulusA request to exchange information or to perform a joint service.
EnvironmentKnown at design time, or discovered at runtime; systems already in service.
ArtifactThe systems that wish to interoperate.
ResponseThe request is handled correctly, or rejected and reported.
MeasurePercentage of information exchanges accepted, or correctness of the exchanged meaning.

Tactic categories

Locate
  • Discover service — look up a capability in a known directory, possibly through several indirections, by name, type, or location.
Manage interfaces
  • Orchestrate — a controller sequences services (workflow engines; a mediator for simple cases).
  • Tailor interface — add translation, buffering, or smoothing, or hide functions the partner must not see.

Checklist themes

Who is responsible for discovery and for refusing a bad request? What coordination mechanism carries the exchange? Which data must be translated? Is the interface bound at design time or discovered later? Which technology (directory, workflow engine, adapter) is already chosen?

Practice prompts

A hospital system must accept lab results from three vendors that use different message layouts. Which tactic handles the layout difference, and which quality attribute gets worse if you apply it naively?

Explain the difference between syntactic and semantic interoperability with an example where the XML parses and the meaning is still wrong.

When is discover-service worth the indirection, and when is a fixed address the better architectural decision?

Chapter 7

Modifiability

Study notes

  • Modifiability is about the cost and time of change, and who can make the change. A change is a stimulus; the response is that the change is made, tested, and deployed inside a budget.
  • Four parameters drive the tactics: size of a module, coupling (chance a change to A also touches B), cohesion (unity of purpose inside a module), and binding time (how late the change can be applied).
  • High coupling spreads a change. Low cohesion means one change inside a module touches unrelated responsibilities. Splitting a module helps only if the split matches the likely change.
  • Deferring binding lets a later stakeholder (installer, operator, user) exercise a flexibility that a developer installed earlier. Late binding mechanisms cost more to build; that is itself a tradeoff.
  • Coupling tactics insert intermediaries, restrict who may depend on whom, encapsulate, refactor responsibilities, or lift a shared service into one place.
Exam deep dive

General scenario shape

SourceDeveloper, administrator, or user who requests a change.
StimulusA change: add, delete, or modify function, quality, platform, or capacity.
EnvironmentDesign time, compile time, build time, initiation time, or runtime.
ArtifactCode, data, interfaces, components, resources, configuration.
ResponseMake, test, and deploy the change; others are unaffected or the ripple is bounded.
MeasureEffort, money, calendar time, extent of the ripple, number of artifacts touched.

Tactic categories

Reduce the size of a module
  • Split module — so a likely change touches less code.
Increase cohesion
  • Increase semantic coherence — move a responsibility to the module whose purpose it matches.
Reduce coupling
  • Encapsulate, use an intermediary, restrict dependencies, refactor, abstract common services.
Defer binding
  • Compile or build: component replacement, compile-time parameterization, aspects.
  • Deployment: configuration-time binding. Startup: resource files.
  • Runtime: registration, dynamic lookup, interpreted parameters, name servers, plug-ins, publish-subscribe, shared repositories, polymorphism.

Checklist themes

Which responsibilities will change together and should share a module? Which dependencies are forbidden? What is bound late, and who is allowed to exercise that binding? What technology (build system, plug-in framework) carries the mechanism?

Practice prompts

A pricing rule changes every sales season and currently forces a code release. Propose a defer-binding tactic and state who exercises it. What new quality risk did you introduce?

Define coupling and cohesion in terms of change scenarios, not in terms of “modules should be independent.”

Why can abstract-common-services hurt performance or availability? Give a one-sentence tradeoff.

Chapter 8

Performance

Study notes

  • Performance is about time. Events arrive (periodic, stochastic, or sporadic), are queued, and must produce a response within a constraint: latency, throughput, deadline, or jitter.
  • Two sides of the tactic tree: control resource demand (do less work, or do it in a cheaper order) and manage resources (have more resources, or use them with less waste).
  • Demand-side moves include sampling less often, limiting how much work a response may do, prioritizing events, cutting overhead, bounding execution time, and using a more efficient algorithm.
  • Resource-side moves include adding hardware, introducing concurrency, keeping extra copies of data or of computations, bounding queues, and scheduling.
  • Almost every performance tactic taxes another quality: copies fight consistency, concurrency fights testability, dropping samples fights accuracy.
Exam deep dive

General scenario shape

SourceUsers, external systems, or internal events.
StimulusPeriodic, stochastic, or sporadic events arriving.
EnvironmentNormal or overload; operating mode.
ArtifactSystem or a specific processor, store, or process.
ResponseProcess events, change service level, or reject load.
MeasureLatency, deadline miss rate, throughput, jitter, miss ratio, data loss.

Tactic categories

Control resource demand
  • Manage sampling rate, limit event response, prioritize events
  • Reduce overhead, bound execution times, increase resource efficiency
Manage resources
  • Increase resources, introduce concurrency
  • Maintain multiple copies of computations, maintain multiple copies of data
  • Bound queue sizes, schedule resources

Checklist themes

Where do events arrive and who may shed load? What is shared and locked? Which data is replicated? What is the scheduling policy on the bottleneck resource? Which of these decisions are frozen by the platform?

Practice prompts

An intersection camera must keep up with rush hour. Write a performance scenario, then apply one demand-side tactic and one resource-side tactic. Which response measure moves?

“Maintain multiple copies of data” improves read latency. Which quality attributes become harder, and why?

Explain jitter in one sentence and name a system where average latency is fine but jitter is the real requirement.

Chapter 9

Security

Study notes

  • Security is the ability to protect data and services from unauthorized access while still providing access to legitimate actors. Confidentiality, integrity, and availability are the usual trio; authentication, authorization, and nonrepudiation are how you operationalize them.
  • What you protect is data at rest, data in transit, and computational processes. Threat modeling (attack paths, not a slogan) is how you find the stimuli.
  • Tactics follow the life of an attack: detect it, resist it, react while it is underway, and recover afterward. Recovery leans on availability tactics plus an audit trail.
  • Resisting an attack is a sequence: identify the actor, authenticate, authorize, limit access and exposure, encrypt, separate entities, and refuse dangerous defaults.
  • Security tactics routinely hurt usability and performance. The exam move is to name the tradeoff, not to pretend encryption is free.
Exam deep dive

General scenario shape

SourceAn attacker, or an authorized user who makes a mistake. May be identified or not, inside or outside.
StimulusUnauthorized attempt to display, modify, or delete data; to exhaust a service; or to insert unexpected input.
EnvironmentOnline or offline; firewall present or not; already connected or not.
ArtifactData in a store, data on a path, a process, or the whole system.
ResponseAuthenticate, block, audit, recover, lock out, or report.
MeasureTime to detect, fraction of attacks resisted, likelihood of identifying the attacker, data still consistent after recovery.

Tactic categories

Detect attacks
  • Detect intrusion, detect service denial, verify message integrity, detect message delay.
Resist attacks
  • Identify actors, authenticate actors, authorize actors, limit access, limit exposure, encrypt data, separate entities, change default settings.
React to attacks
  • Revoke access, lock computer, inform actors.
Recover from attacks
  • Restore service (availability tactics) and maintain an audit trail so the attack can be traced and the defense improved.

Checklist themes

Which actor is identified before any data moves? Where are audit records stored so an attacker cannot edit them? Which entities are separated onto different hosts? What is encrypted, and where are keys bound? Which defaults ship open?

Practice prompts

Write a security scenario for a stolen session cookie. Which detect tactic and which react tactic apply, and what do you need in the audit trail afterward?

Separate “authenticate” from “authorize” with an example where the first succeeds and the second must fail.

Why does the book treat recovery from attack as partly an availability problem?

Chapter 10

Testability

Study notes

  • Testability is the ease with which software can be made to show its faults. If a fault exists, a testable system makes it likely that the next test run will fail, and makes the failure diagnosable.
  • Two ideas dominate: controllability (put the system into the state you want, and feed it the inputs you want) and observability (see the state and the outputs that reveal a fault).
  • Tactics either control and observe system state, or limit complexity so there is less hidden behavior to test. Nondeterminism is the enemy of both.
  • Specialized test interfaces, record/playback, localized state, abstract data sources, sandboxes, and executable assertions are the usual control-and-observe tools. They must not become a back door in production without a conscious security decision.
  • Testability is designed in. Bolting a test harness onto an opaque, timing-dependent system is why “we’ll test it later” fails.
Exam deep dive

General scenario shape

SourceUnit tester, integration tester, system tester, or the running tests themselves.
StimulusA test completion milestone: a class, a subsystem, or the whole system is ready to be exercised.
EnvironmentDesign time, development, compile, integration, or deployment.
ArtifactThe piece under test.
ResponseControl state and inputs; observe outputs; execute the test suite.
MeasureEffort to find a fault, probability a fault is revealed, time to run the tests, length of the longest dependency chain in a test.

Tactic categories

Control and observe system state
  • Specialized interfaces, record/playback, localize state storage
  • Abstract data sources, sandbox, executable assertions
Limit complexity
  • Limit structural complexity (fewer dependencies, less cyclic structure)
  • Limit nondeterminism (control time, threads, and ordering enough that a failure can be repeated)

Checklist themes

Who can set internal state for a test? Can input sources be replaced without editing production logic? Where does nondeterminism enter? Are test interfaces identified so they can be locked down? Which bindings exist only in the test build?

Practice prompts

A defect appears only when two threads interleave in a rare order. Which testability tactic addresses the cause, and what would record/playback add?

Specialized test interfaces help testers and attract attackers. How would you bind them so they exist in test and not in production?

Why does limiting structural complexity belong under testability rather than only under modifiability?

Chapter 11

Usability

Study notes

  • Usability is how easily a user can accomplish a desired task and how the system supports that task. It covers learning, efficiency, remembering, error avoidance, and satisfaction — but the architectural question is which of those need runtime support.
  • Some usability is purely in the user interface. The architect cares when the UI needs information or control from the rest of the system: cancel a long operation, undo, estimate time remaining, adapt to the user.
  • Two tactic groups: support user initiative (the user drives: cancel, undo, pause/resume, aggregate commands) and support system initiative (the system anticipates, using a model of the task, the user, and the system).
  • Those models are architectural state. A task model knows the steps of a job; a user model knows preferences and expertise; a system model knows what the software is doing so it can explain itself.
  • Usability scenarios often trade off against performance (extra feedback) and modifiability (rules duplicated on client and server so validation feels instant).
Exam deep dive

General scenario shape

SourceAn end user.
StimulusA wish to learn the system, use it efficiently, minimize the impact of errors, adapt it, or feel confident.
EnvironmentRuntime, or configuration time.
ArtifactThe system or the portion the user is interacting with.
ResponseFeedback, cancellation, undo, aggregation, assistance matched to the user, or a predictable response time.
MeasureTask time, errors made, user satisfaction, learning time, ratio of successful operations to attempts.

Tactic categories

Support user initiative
  • Cancel, undo, pause/resume, aggregate.
Support system initiative
  • Maintain a task model, maintain a user model, maintain a system model.

Checklist themes

Which user commands must be cancellable deep in the system, not only in the widget? Where is undo state stored? Which component owns the user model, and when is it bound? What extra runtime traffic does feedback require?

Practice prompts

“Undo” of a submitted payment is not a UI detail. What architectural responsibilities does it create, and which other quality attribute does it stress?

Give an example of system initiative that needs a task model. What goes wrong if the model and the real workflow drift apart?

A designer wants client-side validation and server-side validation to feel instant. Why is that a modifiability problem as well as a usability choice?

Chapter 12

Other Quality Attributes

Study notes

  • The seven chapters before this one are a working set, not a closed list. Variability, portability, scalability, deployability, mobility, monitorability, and safety show up often enough to name, and each can be given the same treatment as availability or performance.
  • Variability (support a planned family of changes) and portability (move to a new platform) are special cases of modifiability with their own stimuli. Scalability is a performance concern about growing load. Deployability is about getting a build onto a host and rolling it forward or back.
  • Safety is a system property, not only a software property. A safe system avoids hazardous states; a reliable system is consistent with its specification. Those are not the same. Hazard analysis and fault trees are system-engineering tools the architect participates in.
  • Standard catalogs (such as ISO/IEC 25010) are useful checklists and dangerous if treated as requirements. Names overlap, and a catalog will not tell you the response measure for your system.
  • Bringing a new “x-ability” into the fold means writing a general scenario, listing tactics that control its response, and building a design checklist from the seven decision categories. That recipe is the chapter’s method.
Exam deep dive

Key terms

Variability
Planned modifiability: the architecture exposes variation points so a family of products can be built. Chapter 25 depends on this.
Portability
Ease of moving the software to a different computing environment. Often achieved by isolating platform dependencies behind a layer.
Deployability
How an executable gets onto a host, including update, rollback, and how much of the system must stop.
Safety
Avoiding harm. Distinct from availability and from reliability. Often a property of the whole system, not of software alone.
X-ability recipe
General scenario + tactics + checklist across the seven design decisions.

What the exam wants

  • Say why a quality-attribute name from a standard is not yet a requirement.
  • Show the three-step recipe on a quality the book did not give its own chapter (for example energy use, or legal auditability).
  • Distinguish safety from reliability with a short example.
Practice prompts

Apply the x-ability recipe to “energy efficiency” for a phone app. Draft the six scenario parts and name two tactics.

Chapter 13

Architectural Tactics and Patterns

Study notes

  • A pattern documents a recurring design as context, problem, and solution. The solution describes elements, relations, and the quality attributes those structures promote — and the ones they weaken.
  • Tactics are the mechanisms inside a pattern. A layered system is, among other things, an application of “restrict dependencies” and semantic coherence. You can add tactics to a pattern (a cache beside a layer, a replica beside a service) and you will change the tradeoff.
  • Real systems wear many patterns at once. A three-tier web system may also use replication, proxies, MVC inside a tier, and pub-sub for notifications.
  • The catalog is grouped by the kind of problem: separation of concerns (layers, broker, MVC), data flow (pipe-and-filter, map-reduce), shared state (shared-data), distribution (client-server, peer-to-peer, multi-tier), and loose coupling over time (publish-subscribe, service orientation).
  • Using tactics together is where design actually happens. The chapter’s warning is that tactics interact: a performance tactic can disable a modifiability tactic that the pattern was chosen for.
Exam deep dive

Pattern families in the catalog

Module-oriented
  • Layered — each layer is a virtual machine; strict layering allows use only of the layer below. Favors portability and modifiability; can add latency.
  • Broker — clients and servers communicate through a broker that locates services and forwards requests. Favors location independence; the broker is a complexity and availability focus.
  • Model-view-controller — separates state, presentation, and input handling. Favors independent change of UI; can scatter a single user action.
Component-and-connector
  • Pipe-and-filter — streams transformed by independent filters. Favors reuse and parallelism; awkward for interactive systems and shared global state.
  • Client-server — clients request, servers provide. Simple coordination; server can become a bottleneck and a single point of failure.
  • Peer-to-peer — peers are both clients and servers. Favors scalability and lack of a central choke point; harder to secure and to reason about consistency.
  • Service-oriented — distributed services with advertised interfaces, often independently owned. Favors interoperability and independent evolution; operational governance is the hard part.
  • Publish-subscribe — publishers emit events, subscribers receive them without knowing the publishers. Favors loose coupling; delivery order, loss, and debugging get harder.
  • Shared-data — components read and write a repository. Favors consistency of data and independent producers; the repository is a performance and availability bottleneck.
  • Map-reduce — parallel map over data partitions, then reduce. Favors throughput on large data; not a fit for tightly coupled interactive transactions.
Allocation
  • Multi-tier — execution structures placed on distinct hardware tiers (for example presentation, logic, data). Favors security boundaries and independent scaling; network hops add latency.

Tactic–pattern relationship

  • A pattern is a bundle of tactics plus the constraints on how elements may interact.
  • Choosing a pattern gets you its built-in tactics and its built-in weaknesses.
  • You strengthen a weak quality by adding a tactic, then you re-check the qualities the pattern was supposed to protect.
Practice prompts

A log-processing pipeline and an online shopping cart are both “data in, data out.” Which pattern fits each, and which tactic inside the wrong pattern would fight the problem?

Name two tactics already present in a strict layered pattern, and one tactic you might add for availability. What does that addition do to the layering rule?

Chapter 14

Quality Attribute Modeling and Analysis

Study notes

  • Analysis asks whether the architecture will satisfy a quality-attribute scenario, before or after the code exists. Different techniques buy different confidence at different cost.
  • Roughly in order of increasing cost and fidelity: design checklists, thought experiments and back-of-the-envelope estimates, analytic models, simulations, and prototypes or experiments.
  • Models (queueing for latency, schedulability analysis for deadlines) need parameters. Early in the life cycle those parameters are guesses, so a cheap checklist or estimate is often the honest tool. Later, measurements can feed a model or a prototype.
  • Checklists are the seven design-decision categories applied to one quality. They find omissions. They do not produce a latency number.
  • Choose the technique to match the risk and the life-cycle stage. An ATAM (Chapter 21) is a facilitated way to apply questioning and scenario analysis; it is not a substitute for a queueing model when you need a number.
Exam deep dive

Analysis ladder

  1. Checklists — systematic questions; cheap; good for design reviews.
  2. Thought experiments and back-of-the-envelope analysis — order-of-magnitude estimates with explicit assumptions.
  3. Analytic models — queueing, schedulability, and similar mathematics when the assumptions hold.
  4. Simulation — an executable model of the architecture’s timing or resource behavior.
  5. Prototype or experiment — real code on the risky path; highest fidelity, highest cost.

Early life cycle: scenarios, checklists, estimates. Mid life cycle: models and focused prototypes on sensitivity points. Late life cycle: measurement on the built system, which reconstruction and test can feed.

Practice prompts

You have a two-week spike and a worry that a shared database cannot absorb peak writes. Which rung of the analysis ladder do you climb, and what assumption will you write down?

Why is a checklist the wrong tool to answer “is p95 latency under 200 ms,” and why is a prototype the wrong first tool on day one of design?

A model says the system meets its deadline. Name two reasons the running system might still miss it.

Part III — Architecture in the life cycle

Chapters 15–22 move from vocabulary to work: how much architecture, how requirements become ASRs, how to design, document, implement, check conformance, evaluate, and govern.

Chapter 15

Architecture in Agile Projects

Study notes

  • The question is not “architecture or agile.” It is how much architecture to decide before coding, given the cost of rework if you guess wrong.
  • Up-front architecture effort pays off when the system is large, the domain is unfamiliar, quality attributes are stringent, the team is distributed, or a wrong structure would be expensive to undo. It pays less when the system is small, the team has built this shape before, and change is cheap.
  • Agile architecture still has ASRs, still uses tactics, and still leaves a trail of decisions. It avoids documentation that nobody will read, and it designs the next risky slice rather than the entire future.
  • Guidelines: work on the architecturally significant items first, evaluate early and often, keep documentation proportional to stakeholders, and let the architecture emerge in increments without pretending there is no architecture.
  • Connects back to Chapter 1 (decisions are not all early) and forward to Chapters 16–18 (just enough scenarios, just enough design, just enough views).
Exam deep dive

Key terms

How much architecture
The amount of design that minimizes total cost: cost of architecture work plus cost of rework from architectural mistakes.
Sweet spot
Shifts right (more up front) as size, complexity, requirements volatility you cannot absorb, and quality-attribute risk grow. Shifts left when the team already knows the pattern.
Agile architect
Designs incrementally, stays with the team, treats scenarios as backlog items, and documents decisions that others must follow.
Practice prompts

Two projects use Scrum. One is a brochure site; one is a national payment switch. Argue for a different amount of up-front architecture in each, using rework cost.

Which artifacts from Chapters 4 and 18 would you still keep on a two-team agile project, and which would you thin?

“The architecture will emerge” is sometimes true and sometimes a way to skip hard quality attributes. How can a team tell the difference?

Chapter 16

Architecture and Requirements

Study notes

  • Architecturally significant requirements are the few requirements that shape structures. They come from quality attributes, from high-value or high-risk functions, and from constraints. Collecting every shall-statement is not the architect’s job.
  • Three sources: existing requirements documents (mine them for scenarios and constraints), stakeholder interviews, and business goals. The facilitated interview method in this chapter is the Quality Attribute Workshop. The business-goal method is PALM.
  • A utility tree turns raw concerns into a prioritized ASR list. Root is “utility.” Children are quality attributes, then refinements, then concrete scenarios. Each leaf is rated on business value and on architectural impact (high, medium, low).
  • The methods combine: PALM finds goals and gives existing drivers a pedigree; QAW elicits and prioritizes scenarios from a room of stakeholders; the utility tree is the backlog those scenarios land in. Documents are a starting inventory, not the workshop.
  • Prioritize (H,H) first in design. Do not ignore (H,M) and (M,H): high business value with medium architectural impact, and the reverse, both hide risk.
Exam deep dive

Quality Attribute Workshop

  1. Presentation and introductions.
  2. Business or mission presentation.
  3. Architectural plan presentation (even if the plan is only a sketch).
  4. Identification of architectural drivers.
  5. Scenario brainstorming.
  6. Scenario consolidation.
  7. Scenario prioritization (stakeholders vote; a common rule is about 30 percent of the scenario count in votes each).
  8. Scenario refinement of the winners into six-part form.

PALM (Pedigreed Attribute eLicitation Method)

  1. Overview of the method.
  2. Business drivers presentation.
  3. Architecture drivers presentation.
  4. Business-goal elicitation, expressed as scenarios, then prioritized.
  5. Identification of quality attributes that would serve those goals — including missing requirements.
  6. Assignment of pedigree: which goal each existing driver serves, and why the number in the response measure is that number.
  7. Conclusion, next steps, feedback.

Utility tree

Utility → quality attribute → refinement → scenario, each leaf tagged (business value, architectural impact). It is both a prioritization tool and a completeness check: a business goal with no scenario is a gap.

Practice prompts

Build a four-leaf utility tree for a campus course-registration system. Mark each leaf (H/M/L, H/M/L) and say which leaf you would design first.

A stakeholder says “the system must be secure.” What does a QAW facilitator do before that sentence is allowed into the utility tree?

PALM step 6 asks why a latency limit is 40 ms and not 80. Why is that question architectural rather than pedantic?

Chapter 17

Designing an Architecture

Study notes

  • Design here is a deliberate decomposition driven by ASRs, not a tour of every requirement. The strategy is generate-and-test: propose a fragment of design, see which ASRs it satisfies, and repeat.
  • Attribute-Driven Design (ADD) is the method. You always design one element at a time, starting with the whole system on a green-field project. The output of a round is a set of children, their responsibilities, and their interactions — plus new ASRs allocated downward.
  • Patterns and tactics are the generation tools. You pick a pattern because its known strengths match the ASRs of this element, then you add tactics for the qualities the pattern does not cover, and you record the tradeoffs.
  • Stop when the ASRs are satisfied to the depth the team can implement. Not every module needs the same depth in round one.
  • Inputs are ASRs (a utility tree is ideal because it is already prioritized), plus constraints. Outputs are sketches of structures that Chapter 18 will turn into views.
Exam deep dive

ADD steps

  1. Choose an element of the system to design. First time through, that element is the whole system. Later, it is a child that still has unsatisfied ASRs.
  2. Identify the ASRs for the chosen element. Rank them. Constraints come along.
  3. Generate a design solution: choose a pattern, apply tactics, allocate responsibilities to children, define interactions, and check the design against the ASRs.
  4. Inventory what remains and pick the inputs for the next iteration (the next element, or the same element at finer grain).
  5. Repeat until the ASRs you intended to satisfy are satisfied.

In step 3, verify each important ASR explicitly. If a tactic hurts another ASR, that conflict is a result, not a failure of the method — it becomes a tradeoff to carry into evaluation.

Practice prompts

You are on ADD iteration 1 for a ride-sharing backend. The top ASRs are “match a rider in 300 ms at peak” and “add a new city without rewriting the matcher.” Sketch the pattern you would try and one tactic you would add.

Why does ADD tell you to design one element rather than all modules in a single drawing?

After iteration 1 you have three subsystems. How do you decide which child is the element in iteration 2?

Chapter 18

Documenting Software Architectures

Study notes

  • Documentation is written for uses: education of new people, communication among stakeholders, analysis, and construction. If a section serves none of those, it should not be written.
  • Notations range from informal boxes-and-lines, through semi-formal UML, to formal architecture description languages. Precision should match the analysis you need to do. An informal diagram that names elements and relations is already useful; an ambiguous diagram is not.
  • Choose views by listing stakeholders and the structures they need. Combine views when one audience always reads two structures together, but do not merge so far that the relations become muddled.
  • A view package typically holds a primary presentation, an element catalog, a context diagram, a variability guide, and rationale. Around the views sit a documentation roadmap, a system overview, a mapping between views, and a glossary.
  • Behavior is documented when structure alone cannot answer a quality question: traces, sequence sketches, or state models tied to scenarios.
  • When the architecture moves faster than the document, capture decisions as they are made and prefer a living short description over a stale novel. Agile projects still owe stakeholders the views they use to build and to review.
Exam deep dive

Key terms

View
A representation of one structure. Chosen from module, C&C, and allocation families, plus any quality-specific view (security, exception, communication) the stakeholders need.
Primary presentation
The picture or table that shows elements and relations.
Element catalog
What each element is, its properties, and its interfaces.
Variability guide
How the view may legally vary. Essential for product lines (Chapter 25).
Rationale
Why this design, including rejected alternatives. This is what evaluation and later architects need.

Choosing views

Make a table of stakeholders against candidate views. A view earns its place if at least one stakeholder needs it for a real task. Start from the structures ADD actually produced, not from a generic checklist of every view in the catalog.

Practice prompts

A new developer, a security reviewer, and an operator join the project. Which view would you hand each of them first, and what section of that view must not be missing?

When is combining the deployment view and the C&C view helpful, and when does the combination hide a problem?

Your architecture changes weekly. What would you still write down the same day a decision is made, and what would you postpone?

Chapter 19

Architecture, Implementation, and Testing

Study notes

  • Implementation does not automatically follow the architecture. Someone must embed the structures in the code: module boundaries, allowed dependencies, threading, deployment units, and error policy.
  • Practical carriers of the architecture include frameworks that already implement the patterns, code templates, libraries that hide platform tactics, and checks (reviews, dependency rules) that fail the build when a forbidden dependency appears.
  • Testing has two architecture-related jobs. One is ordinary functional and integration testing organized along the decomposition and uses structures, so increments are testable. The other is testing quality-attribute scenarios: the response measures from Chapters 5–11 become test oracles.
  • Incremental implementation should follow the architecture (Chapter 1’s process advice). If the uses structure says A needs a real B, the integration order should respect that.
  • When code and architecture diverge, you either change the code or change the documented architecture. Chapter 20 is how you discover the divergence if you no longer trust the document.
Exam deep dive

Key terms

Architecture carrier
A mechanism that makes the design hard to violate: framework, template, allowed-dependency rule, code generator.
Conformance
The implementation’s structures match the documented ones. Reviews and reconstruction both produce evidence.
Scenario-based test
A concrete quality-attribute scenario used as a test: stimulus, environment, and a checkable response measure.
Practice prompts

You chose a layered pattern. Name two implementation mechanisms that keep a developer from calling upward, and one test that would catch a violation.

Which of your availability scenarios can be turned into an automated test, and which can only be reviewed?

Why does the uses structure suggest an integration order?

Chapter 20

Architecture Reconstruction and Conformance

Study notes

  • Reconstruction recovers the as-built architecture from artifacts (code, builds, traces, deployment descriptors) when the documentation is missing, stale, or untrusted. The goal is a view you can analyze, not a picture of every class.
  • The pipeline has four iterative phases: extract raw views, load them into a database, fuse those views into architecturally meaningful ones, and analyze the result for violations of rules you care about.
  • Tools extract facts; they do not decide which facts are architectural. You need a question first (layer violations, unwanted coupling, deployment surprises) or the database fills with noise.
  • View fusion combines extracted facts — static calls plus dynamic traces, for example — into a hypothesis about a view. Experts, if you still have them, confirm or correct the hypothesis.
  • Analysis compares the reconstructed view to a rule or to the intended architecture. A violation is evidence for conformance work, for a documentation update, or for both.
Exam deep dive

Reconstruction pipeline

  1. Raw view extraction — parsers, profilers, build scripts, and similar tools emit facts (calls, includes, deployments).
  2. Database construction — store and clean the facts so later queries are possible. Collapse noise; drop what the goal does not need.
  3. View fusion — query and combine facts into a candidate architectural view.
  4. Architecture analysis — test the view against intended rules and report violations.

Guidelines worth remembering: start from an explicit goal, expect iteration, do not trust a tool to reconstruct an architecture unattended, and prune before you fuse.

Practice prompts

You suspect the UI layer calls the database directly. Which phase of reconstruction answers that, and what raw fact do you need?

Why is “run a reverse-engineering tool and print the class diagram” not yet architecture reconstruction?

The experts who built the system have left. Which phases get harder, and what can you still conclude?

Chapter 21

Architecture Evaluation

Study notes

  • Evaluation asks whether the architecture is fit for the ASRs you claim to care about, early enough that change is still cheap. It is a risk-discovery activity, not a pass/fail certificate and not a proof.
  • The Architecture Tradeoff Analysis Method (ATAM) brings stakeholders and the architecture team together around business drivers, a utility tree, and scenario-based probing of architectural approaches.
  • Outputs to memorize: risks, nonrisks, sensitivity points, tradeoff points, and risk themes. A risk is a decision that may fail an ASR. A nonrisk is a decision judged safe against an ASR. A sensitivity point is a property that the response depends on. A tradeoff point is a sensitivity point for more than one quality.
  • ATAM is phased: preparation, evaluation with the architecture team, evaluation with a broader stakeholder group, and follow-up reporting. The nine steps below are the evaluation steps.
  • Lightweight evaluation keeps the spirit (utility tree, scenarios, risks) with a smaller cast and less ceremony when a full ATAM is more process than the project can use.
Exam deep dive

ATAM evaluation steps

  1. Present the ATAM.
  2. Present the business drivers.
  3. Present the architecture.
  4. Identify architectural approaches (patterns and tactics in use).
  5. Generate the quality-attribute utility tree.
  6. Analyze architectural approaches against the high-priority scenarios.
  7. Brainstorm and prioritize scenarios with the larger stakeholder group.
  8. Analyze architectural approaches again, now against the new high-priority scenarios.
  9. Present results: risks, nonrisks, sensitivity and tradeoff points, risk themes.

Phases

  • Phase 0 — partnership and preparation.
  • Phase 1 — evaluation with the decision makers and architects (through step 6).
  • Phase 2 — evaluation with a broader set of stakeholders (steps 1–9, with emphasis on 7–9).
  • Phase 3 — follow-up: write and deliver the results.

Step 6 and step 8 are the same kind of analysis on two scenario sets: the team’s utility tree, then the stakeholders’ brainstorm. Disagreement between those sets is itself a finding.

Practice prompts

During analysis, replication is found to cut failover time and to complicate consistency. Classify that finding as risk, nonrisk, sensitivity point, or tradeoff point — more than one label can apply if you justify it.

Why does ATAM analyze scenarios twice (steps 6 and 8)? What would you miss with only the utility tree?

When would you choose a lightweight evaluation instead of a full ATAM? What outputs do you refuse to drop even in the light version?

Chapter 22

Management and Governance

Study notes

  • Architecture work needs ordinary management: a plan (what architecture tasks exist and when), an organization (who the architect is relative to teams), implementation tracking, and measurement of whether the architecture effort is paying off.
  • Team structure tends to mirror the decomposition (Conway’s observation in practical form). Coordination cost follows the interfaces. Putting the architecture team on the other side of every question creates a bottleneck; putting nobody there creates drift.
  • Governance is the set of rules about who may make and change architectural decisions, how compliance is checked, and what happens on a violation. A review board, a decision record, and automated conformance checks are governance mechanisms, not substitutes for a design.
  • Measurement should tie back to stakeholder value: defect rates at integration, time to make a class of change, failed evaluations, stakeholder satisfaction. Activity metrics (“number of views”) are weak.
  • This chapter is the management face of Chapters 19–21. Evaluation without governance does not change the next release; governance without evaluation becomes bureaucracy.
Exam deep dive

Four management activities plus governance

  • Planning — schedule architecture design, evaluation, and documentation as project tasks with inputs and outputs.
  • Organizing — assign architectural responsibility; align teams with modules and with the coordination the architecture demands.
  • Implementing — track decisions into code; keep communication paths that match the dependency structure.
  • Measuring — observe cost and benefit of architecture activities, not only their occurrence.
  • Governance — decision rights, mandatory checkpoints, and compliance mechanisms.
Practice prompts

A company forms an architecture review board that meets monthly and has no written decision rights. Is that governance? What is missing?

Your module structure and your team structure disagree. What symptoms would you expect in schedule and in quality?

Propose one measure that would tell a manager the architecture work is reducing integration risk.

Part IV — Architecture and business

Chapters 23–25 connect design choices to money, to the skills of architects and organizations, and to reuse across a product family.

Chapter 23

Economic Analysis of Architectures

Study notes

  • ATAM can tell you that strategy A helps availability and hurts cost of change. It does not tell you whether A is worth funding. The Cost Benefit Analysis Method (CBAM) adds stakeholder utility and implementation cost so strategies can be ranked.
  • Utility is how much stakeholders value a particular quality-attribute response, usually scored on a small scale from worst acceptable to best imaginable. Benefit of a strategy is the gain in utility it is expected to produce, weighted by scenario importance.
  • CBAM is typically used when an existing system needs an upgrade and several architectural strategies compete for a limited budget. It can also compare options on a new system.
  • The output is an ordered list of strategies by benefit and by benefit relative to cost, plus the side effect that stakeholders see each other’s priorities. The NASA ECS case in the chapter is the worked example of that ranking, not a template to memorize numerically.
  • Inputs are imprecise on purpose. The method’s claim is that a shared, explicit estimate beats an unexamined preference, as long as people then check the ranking against intuition.
Exam deep dive

CBAM steps

  1. Collate the scenarios (often the high-priority ATAM scenarios).
  2. Refine them so the response levels are clear.
  3. Prioritize scenarios (votes become weights).
  4. Assign utility to the current response and to desired response levels.
  5. Develop architectural strategies and map them onto scenarios, including side effects on other scenarios.
  6. Determine the expected utility of each strategy’s quality-attribute levels.
  7. Calculate total benefit from the utility gains and the scenario weights.
  8. Choose strategies using benefit and cost (benefit/cost is the usual ranking key) within the budget.
  9. Confirm the ranking with the group’s intuition and revisit outliers.

Remember the chain: scenario weight × utility gain = contribution to benefit; benefit compared with cost ranks the strategy. A strategy that helps one scenario and hurts another must include the negative utility.

Practice prompts

Two strategies have the same benefit. One costs twice as much. What does CBAM tell you to do, and when would you override that ranking?

A strategy raises availability utility and lowers modifiability utility. Where in the nine steps does that show up?

Why is CBAM a poor fit if you have not yet agreed on scenarios?

Chapter 24

Architecture Competence

Study notes

  • Competence is treated at two levels: the individual architect, and the organization that employs architects. A brilliant architect in an organization with no governance or learning loop still fails to repeat success.
  • Individuals are described with duties, skills, and knowledge, both technical and nontechnical. Duties include creating an architecture and evaluating one. Skills include communication, leadership under uncertainty, and strategic thinking. Knowledge includes patterns, tactics, the domain, and the organization’s business.
  • Organizational competence is assessed with several lenses, not a single maturity number. The chapter uses the duties-skills-knowledge practices of the organization, a human-performance lens (do you know what architecture effort costs and what value it returns?), and an organizational-learning lens (is architectural knowledge captured and reused?).
  • An assessment interviews both producers of architectures and consumers (developers, managers). Findings are a profile across practice areas, closer to a vector than to a grade.
  • Connects to Chapter 22 (governance is an organizational practice) and Chapter 28 (how an individual starts those practices without waiting for permission).
Exam deep dive

Key terms

DSK
Duties, skills, and knowledge — the individual competence model, technical and nontechnical.
Human performance lens
Questions about the cost of architecture work and the value stakeholders actually receive.
Organizational learning lens
Whether architectural knowledge is retained: documentation, communities, “who knows what,” and reuse on the next system.
Assessment result
A set of findings by practice area, used to pick improvements, not a single score.

Chapter 25

Architecture and Software Product Lines

Study notes

  • A software product line is a set of products that share a managed set of features, built from a common set of core assets, in a planned way. The architecture is the core asset that makes the others composable.
  • Clone-and-own (copy a product and edit) works once or twice and then collapses under divergent copies. A product line invests in variation points so the differences are explicit.
  • Scope is the boundary of the family. Too narrow and the reuse savings are trivial. Too wide and the core assets become a compromise that fits nobody. Products outside the scope are a business decision, not a surprise for the architect.
  • Variability is the quality attribute of the product line: a request to support a difference in hardware, features, technology, UI, or quality, at a stated binding time, with a cost measure. The architecture’s variation mechanisms must match those binding times.
  • Mechanisms differ in who can exercise them and what they cost to build: inheritance, component substitution, plug-ins, templates, parameters, generators, aspects, runtime conditionals, configurators. Building the mechanism is often expensive; exercising it should be cheap.
  • Evaluate a product-line architecture for the qualities of each product and for the ability to instantiate products inside the scope. Document a variability guide: what may vary, how, when, and which combinations are illegal.
Exam deep dive

What makes it work

  • Core assets beyond code: requirements, architecture, test plans, schedules, and people who already know the domain.
  • A defined scope and the discipline to send out-of-scope requests through a business decision.
  • Variation mechanisms chosen for the stakeholder who will exercise them (developer vs. installer vs. end user) and for the binding time in the variability scenario.

Failure patterns worth naming

No sustained champion, middle managers who will not give up per-project control, unclear business goals, quitting at the first overrun, untrained staff, undisciplined variation points, scope set far too wide or too narrow, and no tooling to exercise the variations.

Practice prompts

A company ships three mobile banking apps by copying a repository. At what point does clone-and-own become more expensive than a variation point, and which mechanism would you pick for a per-bank color and logo?

Write a variability scenario whose binding time is runtime, and one whose binding time is development time. Which mechanisms fit each?

The product-line scope is “all vehicles.” Why is that a dangerous architecture input?

Part V — The brave new world

Chapters 26–28 apply the same ideas to cloud platforms and to ecosystems whose users also build the product, then close with advice for practicing in an organization that is not ready.

Chapter 26

Architecture in the Cloud

Study notes

  • Cloud computing is a way of delivering pooled, elastic computing resources, often with self-service provisioning and measured billing. The architectural shift is that hardware, and sometimes the platform or the application, is someone else’s service with a contract.
  • Service models: Infrastructure as a Service (you manage OS and application; you rent machines, storage, and networks), Platform as a Service (you deploy applications onto a provided stack), Software as a Service (you use a finished application, often multi-tenant). Deployment models: private, community, public, and hybrid, distinguished by who owns and operates the cloud.
  • The economic bet is higher utilization and elasticity: you stop buying peak capacity that sits idle, and you trade capital expense for operating expense. Uncertainty remains — you must still understand the provider’s failure modes and the bill.
  • Base mechanisms the chapter walks through include virtualization (hypervisor, an extra level of address translation, a scheduler), virtualized storage with replication (the HDFS-style story of name nodes and data nodes is the example), and network indirection (addresses and headers that can be rewritten so tenants share a physical network).
  • Architecting for a cloud environment means designing for multi-tenancy, failure of instances, stateless or quickly recoverable compute, and explicit control of where state lives. Quality-attribute scenarios do not go away; the tactics are partly supplied by the provider and partly still yours.
Exam deep dive

Key terms

IaaS / PaaS / SaaS
How much of the stack the consumer controls, from virtual machines up to a finished application.
Multi-tenancy
One running application serves many customers. Upgrades happen once for everyone; isolation between tenants becomes an architectural requirement.
Hypervisor
The layer that creates and schedules virtual machines and adds a translation between guest addresses and host resources.
Elasticity
The ability to add or remove capacity. It is a performance and cost tactic only if the architecture can actually use a new instance.

Exam habit: take an availability or performance scenario from Part II and say which part the cloud provider’s mechanism covers and which part remains the application architect’s problem.

Practice prompts

Your service stores session state in memory on one virtual machine. Autoscaling adds three more VMs at peak. Why is latency still bad for many users? Which tactic from Chapter 8 or 5 fixes the mismatch?

Contrast IaaS and SaaS for a university that wants email. What does the architect stop deciding in the SaaS case?

Multi-tenancy pushes upgrade pain from customers onto the provider. Which new quality-attribute risk does the provider accept?

Chapter 27

Architectures for the Edge

Study notes

  • Edge-dominant systems (large open-source platforms, social and content platforms, app ecosystems) are built by communities, not only by a hired team. The architecture influence cycle is extreme: the architecture determines who is allowed to contribute.
  • The Metropolis model is a picture of communities, not a component diagram. Stakeholders include customers and end users, developers, and prosumers (people who both consume and produce). Realms: an outer mass of end users, a periphery of developers and prosumers, and a core platform reached through APIs.
  • Permeability differs. In many open-source systems a contributor can move from user to developer to core committer. In open-content systems, contributing content does not make you a core developer. That social rule should be an explicit architectural and governance choice.
  • Classic life cycles assume known requirements, a finite team, and managed releases. At the edge, requirements arrive continuously from the periphery, contributors come and go, and versions coexist. The core has to tolerate old, partial, and multiple clients.
  • Implications: invest in the core’s APIs and stability, expect indifference to a single project phase, treat the periphery as the source of requirements, and evaluate the core as the fabric that holds incompatible extensions together.
Exam deep dive

Key terms

Metropolis structure
Core, periphery, and masses — communities and the platform that joins them.
Core
The software kernel and its APIs (a kernel, a wiki engine, a phone platform). This is what the organization must architect with care.
Periphery
Developers and prosumers who build on the core. Their work is not fully planned by the core team.
Prosumer
A participant who both uses the system and produces content or extensions.

What changes in the life cycle

  • Requirements are asserted by use at the edge more than they are elicited up front.
  • Management does not control the periphery’s effort.
  • Delivery must tolerate many versions at once.
  • Architecture effort concentrates on the core and on the rules of extension.

Chapter 28

Epilogue

Study notes

  • The epilogue is about adoption. Knowing the methods does not mean a project will let you run an ATAM, hire a lead architect, or fill out a full view package. The advice is how to insert architectural practice anyway.
  • Speak in ends, not means. Decision makers buy products, risk reduction, and strategy. Project managers buy credible schedules and fewer late surprises. Architecture is justifiable in those terms: it is a risk reducer and a basis for estimates.
  • Get into the requirements conversation early so quality attributes are shaped while they are still movable. Talk to marketing about variations the current architecture could support — that is product-line thinking in miniature.
  • Argue with rough economics. A spreadsheet with honest assumptions beats a plea for “best practice.” Small, regular communities of practice (a reading group, a shared scenario list, an offer to review another team’s design) spread competence faster than a mandate.
  • Take small wins. The book’s promise is cumulative: each evaluated decision, each written-down view, each conformance check leaves the organization slightly more able to do the next one. Chapter 24’s competence model is the long-term target; this chapter is how you start.
Exam deep dive

Six moves

  1. Translate architecture into business outcomes the decision makers already want.
  2. Translate it again into project-manager concerns: risk, schedule, and budget.
  3. Join requirements work instead of receiving a document over a wall.
  4. Make the economic case, even with back-of-the-envelope numbers.
  5. Start a small, regular architecture community with a concrete product (a template, a pattern set, a review offer).
  6. Treat each adopted practice as a win; do not wait to reform the whole company.
