Every heavy-reporting option — and what each one actually buys you

السيناريو: Odoo/POS يكتب على account.move.line (~200M صف)، و50+ مستخدم × 20+ فرع بيطلبوا تقارير تقيلة. الـ Indexing و SQL Optimization خلاص اتعملوا. السؤال بقى: إيه الطبقات اللي تفصل الـ Writes عن الـ Reads، وإيه اللي يصغّر البيانات المقروءة؟

Scenario: Odoo/POS writes to account.move.line (~200M rows) while 50+ users across 20+ branches run heavy reports. Indexing and SQL tuning are already done. The real question: what isolates writes from reads, and what shrinks what reports read? 

Odoo / POS

      Heavy Reads
         ↓
      50+ users
      20+ branches
قاعدة ذهبية: مش كل حل Performance Magic.
Replica = عزل شغل · Aggregation = تصغير بيانات · Async = راحة UX · CQRS = فصل مسؤوليات.
ومش لازم تستخدم الـ 22 حل كلهم — بعضهم بدائل، وبعضهم طبقات فوق بعض.
Golden rule: not every solution is performance magic.
Replica = workload isolation · Aggregation = data reduction · Async = UX relief · CQRS = separation of concerns.
You don’t need all 22 — some are alternatives, some are layers.

What each level buys you

عزل الشغل (Isolation)

Workload isolation

Replica / سيرفر منفصل / حدود اتصالات — يوقف التقارير عن خنق الـ POS. مش بيخلّي scan على 200M رخيص.

Replica / separate host / connection caps — stops reports from choking POS. Does not make a 200M scan cheap.

تصغير البيانات (Reduction)

Data reduction

Pre-agg / MatView / Read Model / Archive / Warehouse — ده اللي يخلّي 200M تحس إنها آلاف.

Pre-agg / MatView / Read Model / Archive / Warehouse — this is what makes 200M feel like thousands.

راحة المستخدم (UX)

UX relief

Async + Workers + Cache — المستخدم مش هيستنى HTTP. تكلفة الـ query ممكن تفضل زي ما هي.

Async + Workers + Cache — users stop waiting on HTTP. Query cost may stay the same.

الهندسة (Architecture)

Architecture

CQRS / Events — طبقة تمكين عشان العزل + التصغير يفضلوا قابلين للصيانة. مش سحر لوحدهم.

CQRS / Events — enablement so isolation + reduction stay maintainable. Not magic alone.

PostgreSQL Partitioning

account_move_line

الميزة

Benefit

  • يقلل كمية البيانات اللي الـ query محتاجة تقرأها (range queries).
  • Cuts rows touched for date-range queries via partition pruning.

العيب / الحذر

Risk

  • account.move.line أساسي في Odoo — FK, ORM, Constraints, Upgrades, Modules.
  • Core Odoo table — FKs, ORM, constraints, upgrades, modules need careful study.

مش أول Lever بعد الـ indexes. ادخّله متأخراً وبعد دراسة.

Not the first lever after indexes — late / special only.

يعزل Write/Readisolates W/R لسه 200Mstill 200M 
Primary DB  ──replication──►  Read Replica

الميزة

Benefit

  • نعزل workload التقارير عن الـ writes / POS.

خد بالك

Caveat

  • الـ Replica لسه فيه 200M صف. التقرير السيئ يفضل تقيل.
  • Replica still has 200M rows. A bad query stays expensive.

Read Replica = Workload Isolation — مش بالضرورة Query Optimization.

Read Replica = Workload Isolation — not necessarily query optimization.

تجميع مسبق · Pre-Aggregation

Pre-Aggregation

Highest ROI for 200M
⭐⭐⭐ أكبر مكسب أداءbiggest perf win 
200M raw rows
      ↓ Aggregation (nightly / incremental)
Daily Summary (thousands–millions)
      ↓
Reports read summary — not AML

ليه مهم عندك؟

Why it matters here

  • بدل كل report يعمل SUM/GROUP BY على AML كل مرة.
  • Stops every report from re-SUM/GROUP BY-ing AML.
  • هنا فعلاً ممكن تشوف قفزة أداء كبيرة.
  • This is where you can see a large performance jump.

القيد

Constraint

  • للـ Analytical/Management — مش للتقارير النظامية Exact بدون إثبات تطابق.
  • For Analytical/Management — not Exact statutory without proven parity.

المفتاح في Odoo/Accounting: مسارين

The Odoo/Accounting key: two lanes

خلط المسارين = إما تأخير خطر على التقارير النظامية، أو تكلفة زايدة على تقارير الإدارة.

Mixing lanes forces either unsafe lag on statutory reports or unnecessary cost on management reports.

Exact Accounting

ميزان مراجعة، GL، دفتر شركاء، ضريبة/ZATCA، إقفال.

Trial balance, GL, partner ledger, tax/ZATCA, statutory close.

  • لازم يطابق دفتر Odoo (near real-time أو as-of مضبوط).
  • Must match Odoo ledger (near real-time or controlled as-of).
  • مسموح: Replica · Async · Connection limits.
  • Allowed: Replica · Async · Connection limits.

Analytical / Management

KPIs فروع، مبيعات يومية، Dashboards، اتجاهات، P&L عبر الفروع.

Branch KPIs, daily sales, dashboards, trends, cross-branch P&L.

  • Eventual consistency OK (دقائق–ساعات) مع as of.
  • Eventual consistency OK (minutes–hours) with as-of.
  • مسموح: Pre-agg · MatView · Read Model · Reporting DB · Events · CQRS · Warehouse.
  • Allowed: Pre-agg · MatView · Read Model · Reporting DB · Events · CQRS · Warehouse.

ترتيب التنفيذ للسيناريو بتاعك

Recommended order for your scenario

مش هبدأ بـ «اعمل CQRS». هفكر كده:

Don’t start with “just do CQRS”. Think like this:

200M account.move.line
        │
        ▼
هل المشكلة في query نفسها؟  → غالباً NO (indexes done)
        │
        ▼
هل Reads بتنافس Writes؟ → YES
        │
        ├─ Read Replica + Async + Caps     (Phase 1)
        │
        └─ Pre-Aggregation / Read Model    (Phase 2)
                │
                ▼
           Reporting DB                    (Phase 3)
                │
                ▼
           Event-Driven refresh            (Phase 4)
                │
                ▼
           CQRS shape formalized           (Phase 5)
                │
                ▼
           Warehouse / OLAP if needed      (Phase 6)
  1. صنّف التقارير Exact vs Analytical.
  2. Classify reports Exact vs Analytical.
  3. اعزل Replica + Reporting host + Async + Limits.
  4. Isolate Replica + reporting host + Async + limits.
  5. صغّر Pre-Aggregation للـ Analytical فقط.
  6. Shrink Pre-aggregation for Analytical only.
  7. بعدين Reporting DB → Events → CQRS → Warehouse.
  8. Then Reporting DB → Events → CQRS → Warehouse.
