Kubernetes: المفاهيم الأساسية، الـ Architecture، والنشر العملي

دليل تتعلم بيه ليه المنصة موجودة، إزاي الـ cluster بيوصل للحالة اللي أنت طالبها، وإزاي تكتب YAML وتتحكم في الـ cluster من Python من غير ما تحفظ أوامر من غير معنى.

المستوى: Intermediate زمن الدراسة: تقدير 14–18 ساعة مركزة الإطار: Kubernetes 1.30+ الكود: YAML و Python client

هتخرج من الدليل ده قادر تعمل إيه

  • تشرح مشكلة الـ orchestration وتفرّق بينها وبين مجرد تشغيل container.
  • ترسم الـ control plane وتقول مين بيتكلم مع etcd ومين لأ.
  • تختار بين Deployment و StatefulSet و DaemonSet و Job لسبب واضح.
  • تصمم Service و probes و requests بشكل ما يكسّرش التحديث ولا يخبي العطل.
  • تشخّص Pending و CrashLoopBackOff و rollout واقف من الأحداث مش من التخمين.
  • تكتب client بـ Python بصلاحيات ضيقة، وتفرّق بين kubeconfig و in-cluster config.
  • تجاوب أسئلة مقابلة بمستوى متوسط لمتقدم، ومعاك الـ trade-off مش شعار واحد.

افتراضات الدليل، متعملهاش حقيقة زيادة. التركيز هنا على الـ architecture الأساسية والـ objects اللي هتقابلها في أغلب الـ clusters. التحكم البرمجي معروض بالـ official Python client، واسم الحزمة على PyPI هو kubernetes. الأمثلة بتشرح سلوك 1.30 وطالع، وأي فرق متعلق بإصدار متعلم عليه صراحة.

مش هنغطي بناء control plane على EKS أو GKE أو AKS، ولا service mesh، ولا GitOps tool، ولا كتابة operator كامل. أدوات زي Helm و Kustomize و Gateway API هتظهر بس كنقطة قرار، مش كمنهج.

مراجعة حقائق الإصدارات اتعملت في 14 أكتوبر 2026 من صفحة Kubernetes Releases الرسمية. وقتها الخطوط المدعومة كانت 1.35 و 1.36 و 1.37، وآخر patch مذكور لـ 1.37 كان 1.37.1 بتاريخ 15 سبتمبر 2026. كان فيه patch 1.37.2 مستهدف 13 أكتوبر 2026. قبل أي upgrade، راجع الرقم الحالي بنفسك.

من غير JavaScript هتقدر تقرأ كل الشرح وتفتح الإجابات من عناصر details. التصحيح التلقائي للاختيارات وحفظ التقدم محتاجين JavaScript.

نظرة تنفيذية

الفكرة في جملة: أنت بتكتب الحالة اللي عايزها، وKubernetes يفضل يقارنها بالحالة الحقيقية ويحرّك الـ cluster لحد ما الاتنين يتقابلوا، أو لحد ما يفشل ويوريك ليه.

المشكلة

الـ container بيحل تغليف التطبيق. لما يبقى عندك نسخ كتير على آلات كتير، محتاج حد يجدول، يعيد التشغيل، يحدّث بالتدريج، ويقدم عنوان ثابت رغم إن عناوين الـ Pods بتتغير.

المكوّنات المهمة

kube-apiserver هو الباب. etcd هو المخزن. الـ controllers بتصلح الفرق. الـ scheduler بيختار Node. على كل Node، kubelet بيشغّل الـ Pods عن طريق container runtime.

فين بتستخدمه

منصات تشغيل خدمات، وظائف batch، أنظمة ليها حالة زي قواعد البيانات لما الفريق قادر يشغلها، وأدوات داخلية بتتكلم مع الـ API. مش كل تطبيق صغير محتاج cluster.

اللي يفضل في دماغك: الـ Pod هو وحدة التشغيل. الـ controller هو اللي بيملك عدد النسخ والهوية. الـ Service هو العنوان الثابت. الـ API server هو الوسيط الوحيد تقريبًا لكل قرار. أي أداة، بما فيها Python client، ما بتعدلش الـ containers مباشرة؛ بتكتب object في الـ API.

خريطة المفاهيم

الخلط الشائع إن الناس بتحط design pattern وشكل تطبيق وشكل cluster في كيس واحد. في Kubernetes المستويات دي مختلفة، وكل مستوى ليه أسئلة مختلفة.

تشغيل عمليةcontainer، image، process، cgroupإزاي التطبيق يشتغل معزول على آلة؟
وحدة جدولةPod، volume، probeإيه اللي بيتجدول مع بعض وبيتشاركَ الشبكة؟

الـ Deployment مش architecture للنظام كله. هو controller جوه طبقة الـ workloads. الـ Ingress controller تطبيق بيتنشر غالبًا جوه الـ cluster، مش جزء من ثنائيات الـ control plane الأساسية. الـ CNI والـ CSI واجهات لإضافات الشبكة والتخزين؛ من غيرهم الـ Pods ممكن مايبقاش ليها شبكة أو أقراص، لكنهم مش بديل عن الـ scheduler.

علاقة المستويات: الصورة بتتنفَّذ جوه container، والـ container جوه Pod، والـ Pod بيتجدول على Node، والـ controller بيقرر عدد الـ Pods، والـ Service بيختار الـ Pods الجاهزة، والـ API server بيسجل كل ده في etcd. لو غيّرت مستوى وأنت بتشخّص، هتدور في المكان الغلط.

1. ليه Kubernetes موجود

قبل المنصة، الفريق كان بيبني النسخ والتحديث وإعادة التشغيل بنفسه: سكربتات، مدير آلات، أو منصة داخلية. Google كانت عندها Borg، وبعدين المشروع اتفتح. Kubernetes بقى مكان الاتفاق على objects وAPI، مش مجرد أداة تشغيل containers.

المشكلة قبل الحل

container واحد على سيرفر واحد مفهوم. عشرات النسخ على آلات بتقع، مع تحديث من غير ما تقطع الخدمة، وعنوان ثابت، وإعداد منفصل عن الصورة، وصلاحيات مختلفة لكل تطبيق: دي مشكلة تشغيل موزعة. من غير orchestrator، كل فريق بيعيد بناء نسخة ناقصة من نفس الحلقات: راقب، قارن، صلح.

النموذج الذهني

تخيّل thermostat: أنت بتظبط درجة الحرارة، والجهاز يفضل يقارن القراءة بالهدف. التشبيه ده بيلمّس فكرة الـ reconciliation، بس التنفيذ الحقيقي أوسع. فيه حلقات كتير، وفيه تعارض متفائل عن طريق resourceVersion، وفيه باب واحد تقريبًا للتعديل وهو الـ API server. الثرموستات ما عندوش etcd ولا صلاحيات RBAC.

إيه اللي مش هيعمله

  • مش بيكتب تطبيقك، ومش بيخلي كود بطيء سريع.
  • مش بيأمّن الشبكة لو ما فيش CNI بيطبق NetworkPolicy، ولو ما كتبتيش السياسات.
  • مش بياخد نسخة احتياطية من قاعدة البيانات لمجرد إنك حاططها في StatefulSet.
  • مش مطلوب لخدمة واحدة على آلة واحدة لو مفيش حاجة من قدراته هتتستخدم.

مفاهيم لازم تبقى مألوفة قبل المكمل

  • process، exit code، وإشارات زي SIGTERM.
  • container image، registry، والفرق بين الصورة والـ container الشغال.
  • IP وDNS وHTTP، لإن الـ Service والـ probes مبنيين عليهم.
  • YAML: مسافات، خرائط، قوائم. تاب غلط يغيّر المعنى.
  • فكرة client/server وREST، لإن كل العملاء بيتكلموا HTTP مع الـ API.

ملخص الفصل: Kubernetes نظام الحفاظ على حالة مطلوبة لتشغيل containers على آلات كتير. قيمته في الـ API والحلقات اللي بتصلح الفرق، مش في إنه "يشغّل Docker بس بشكل أكبر".

تحقق سريع. ليه ما نكتفيش بـ container runtime؟

الإجابة والسبب

الإجابة الصحيحة هي الثانية. من 1.24 اتشال dockershim، والـ kubelet بيتكلم مع runtime متوافق مع CRI زي containerd أو CRI-O. الخيار الثالث غلط لإن الحاوية تقدر تشغّل سيرفر شبكة عادي.

2. Architecture الـ cluster

الـ cluster مجموعة آلات ليها مخ واحد للحالة. الآلات اللي بتشغّل الـ control plane بتمسك القرار. الـ Nodes بتشغّل الشغل. الفصل ده مهم لإن سقوط جزء مش زي سقوط جزء تاني.

كل مكوّن بيعمل إيه

نموذج السقوط: الـ Pods عمليات على الـ Nodes. الـ control plane مش في مسار كل packet بين العميل والتطبيق في التصميم الشائع. عشان كده عطل الـ API مش معناه فورًا إن كل الطلبات على التطبيقات وقعت. معناه إن التجديد والإصلاح والجدولة وقراءة الحالة متوقفين. بعد فترة، عقود الـ Nodes وتجديد الشهادات وسياسات تانية بتبان آثارها.

إضافات بتبان أساسية وهي مش جوه الثنائي

الـ CNI بيدي الـ Pod عنوان وشبكة. من غيره الـ Pod ممكن يفضل في ContainerCreating. الـ CSI بيدي أقراص. CoreDNS بيحوّل orders.shop.svc.cluster.local لعنوان Service. الـ metrics-server بيقدم أرقام الـ CPU والذاكرة اللي الـ HorizontalPodAutoscaler الافتراضي بيعتمد عليها. دول قرارات نشر، وغيابهم يفسر أعطال كتير الناس بتلوم فيها الـ Deployment.

ملخص الفصل: احفظ الباب، المخزن، حلقة الإصلاح، ووكيل الـ Node. أي عميل محترم بيتكلم مع الـ API server. تشخيص "الـ cluster واقع" يبدأ بسؤال: الواقع هو الـ API، ولا Node، ولا شبكة الـ Pods، ولا تطبيق جوه Pod؟

تحقق سريع. مين المفروض يكتب حالة الـ cluster في etcd؟

الإجابة والسبب

الثالثة. عزل etcd ورا الـ API server هو سبب إن RBAC والتحقق موجودين في مكان واحد.

3. الـ API، والحالة المطلوبة، والـ reconciliation

Kubernetes قاعدة objects. كل object ليه apiVersion وkind وmetadata، وغالبًا spec وstatus. الـ spec هو طلبك. الـ status هو اللي النظام شافه. الفرق بينهم هو شغل الـ controllers.

مسار طلب التعديل

توثيق التحكم في الوصول بيرتب المسار كده: اتصال TLS، ثم authentication، ثم authorization، ثم admission، ثم تحقق الـ object، ثم الكتابة في المخزن. طلبات القراءة ما بتعديش على admission controllers. جوه الـ admission فيه طور تعديل وبعدين طور تحقق. لو أي controller في الـ admission رفض، الطلب يقف.

  1. المصادقة تجاوب على "مين ده؟". الفشل 401.
  2. التفويض يجاوب على "يقدر يعمل الفعل ده على المورد ده؟". الفشل 403. وحدات التفويض بتتمشى بالترتيب المضبوط على الـ API server. أول allow أو deny بيحسم. لو الكل رجع من غير رأي، الطلب يترفض. RBAC قوائم سماح، ومفيهوش قاعدة Deny.
  3. الـ mutating admission يقدر يغيّر الـ object، زي حقن ServiceAccount. بعدين الـ validating admission يقدر يرفض.
  4. التحقق من شكل الـ object، وبعدين الحفظ في etcd.

ValidatingAdmissionPolicy مستقرة من 1.30، وبتخليك تكتب جزء من التحقق بـ CEL جوه الـ API server بدل webhook خارجي. MutatingAdmissionPolicy أحدث؛ كانت beta في 1.34. راجع نضجها في إصدار الـ cluster قبل ما تبني عليها. الـ webhooks لسه أداة شائعة للتعديل.

التعارض المتفائل

كل نسخة متخزنة ليها metadata.resourceVersion. لو قريت object وعدّلته، وحد تاني كتبه قبل كتابتك، التحديث يرجع 409. الصح تعيد القراءة وتدمج تاني. ده مش عطل شبكة عشوائي. الـ controllers بتتعامل معاه كمسار طبيعي.

الملكية والحذف

ownerReferences بتربط الـ Pod بالـ ReplicaSet والـ ReplicaSet بالـ Deployment. لما الأب يتمسح، جامع القمامة يمسح الأبناء حسب سياسة الحذف: Background أو Foreground أو Orphan. الـ finalizer اسم في metadata.finalizers بيمنع الحذف النهائي لحد ما المالك يشيل الاسم بعد ما يظبط المورد الخارجي. Pod واقف على Terminating ساعات كتير بيبقى وراه finalizer، مش حاوية بس رافضة تقفل.

Labels و annotations

الـ label هوية قابلة للاختيار: الـ Service والـ ReplicaSet بيختاروا بيها. الـ annotation بيانات مش للاختيار، زي مرجع أداة أو وقت إعادة تشغيل. ما تحطش مفتاح اختيار في annotation وتتوقع الـ Service يلاقيه.

ملخص الفصل: اكتب spec، وسيب status للنظام. اقرأ التعارض 409 كدعوة لإعادة المحاولة الذكية. افهم إن الحذف ممكن يتأخر بسبب finalizer، وإن الاختيار بيتم بالـ labels.

4. الـ Pod: أصغر حاجة تتجدول

الـ Pod مش container باسم تاني. هو غلاف لحاوية أو أكتر بيتشاركوا شبكة الـ Node namespace الخاصة بالـ Pod، وبيقدروا يشاركوا volumes. ليهم عنوان IP واحد جوه شبكة الـ cluster، ومنافذ الحاويات لازم ما تتعارضش على نفس البروتوكول.

دورة الحياة

مرحلة الـ Pod بتبقى Pending أو Running أو Succeeded أو Failed أو Unknown. الحاوية ليها حالة Waiting أو Running أو Terminated. CrashLoopBackOff وImagePullBackOff أسباب انتظار، مش مراحل رسمية للـ Pod. الـ Pod الناجح في Job بيخلص بـ Succeeded لما حاوياته تخرج بصفر حسب سياسة الإعادة.

إمتى تحط حاويتين في Pod واحد

لما لازم يتشاركوا localhost ودورة حياة واحدة، زي مساعد سجلات لازم يشوف ملفات التطبيق على volume مشترك. لو خدمتين مجرد إنهم بيتكلموا HTTP، يبقى كل واحدة Pods مستقلة وService بينهم. جمعهم في Pod واحد بيعني إنهم بيتجدولوا مع بعض وبيقعوا مع بعض.

الـ sidecars الأصلية

من 1.29 لـ 1.32 ميزة SidecarContainers كانت beta وشغالة افتراضيًا إلا لو حد قفل الـ feature gate. من 1.33 بقت GA. الشكل الرسمي: init container مع restartPolicy: Always. بتبدأ قبل حاويات التطبيق، وبتفضل شغالة طول عمر الـ Pod، وبتتقفل بعد ما حاويات التطبيق تخلص. الحاوية العادية جنب التطبيق لسه ممكنة، لكنها ما بتاخدش ترتيب البدء والإيقاف ده.

الحذف الهادئ

  1. الـ API يسجل deletionTimestamp ويبدأ يحسب terminationGracePeriodSeconds. الافتراضي 30 ثانية.
  2. عنوان الـ Pod يتشال من عناوين الـ Service الجاهزة عشان traffic جديد ما يروحش له.
  3. لو فيه preStop، الـ kubelet يشغّله جوه الحاوية.
  4. الـ kubelet يبعت SIGTERM للعملية.
  5. لو المهلة خلصت والعملية لسه موجودة، SIGKILL. الخروج 137 غالبًا معناه إشارة قتل، ومن أسبابه كمان نفاد الذاكرة.

تطبيق يتجاهل SIGTERM، أو قفل اتصالاته بياخد أطول من المهلة، هيتقتل في نص الطلبات. زود المهلة بوعي، وخلي التطبيق يقفل المستمع ويخلّص الشغل الحالي. الـ preStop مش بديل عن معالجة الإشارة؛ هو مكان تنظيف إضافي قبل الإشارة.

ملخص الفصل: جدولة الـ Pod ذرية. الحاويات جواه مش خدمات مستقلة من ناحية الشبكة. إعادة تشغيل الحاوية شيء، وإعادة جدولة الـ Pod على Node تانية شيء تاني.

5. مين بيملك الـ Pods

ما تنشرش تطبيق إنتاج كـ Pod لوحده. الـ Pod لوحده ما يتعوضش لو اتمسح أو الـ Node وقعت. الـ controller هو المالك.

ملخص الفصل: ابدأ من سؤال الهوية والتخزين ونهاية الشغل. Deployment هو الافتراضي للخدمات المتطابقة. ملكية الـ ReplicaSet المباشرة بتتعمل وأنت بتشخّص rollout، مش وأنت بتنشر تطبيق.

Ingress و Gateway API

الـ Ingress قاعدة توجيه HTTP على اسم نطاق ومسار، ومحتاج Ingress controller؛ المنصة الأساسية ما بتشحنش controller واحد جاهز في كل التوزيعات. Gateway API مشروع أغنى لنفس عائلة المشاكل، وناضج في موارد كتير، لكنه مش "استبدال اتعلن إن Ingress اتشال". للاستخدام البسيط، Ingress مفهوم وكافي. للسياسات المعقدة والملكية بين الفرق، ادرس Gateway API كقرار منصة.

NetworkPolicy

من غير سياسات، الاتصال مسموح على قد ما شبكة الـ cluster تسمح. أول سياسة تختار Pod في اتجاه معيّن بتعزل الاتجاه ده: المسموح هو اللي السياسات بتقوله، والسياسات بتتضاف. كتابة السياسة مش كافية؛ إضافة الشبكة لازم تنفّذ NetworkPolicy. Flannel لوحده ما ينفّذهاش. وقفل الخروج كله من غير سماح لـ DNS بيكسر حل الأسماء.

ملخص الفصل: Service اختيار وثبوت. EndpointSlice واقع الجاهزية. Ingress طبقة HTTP اختيارية ومحتاجة controller. السياسة الشبكية مسؤولية CNI وتنفيذ، مش مجرد YAML متخزن.

7. الإعداد، الأسرار، والأقراص

الصورة تفضل قابلة لإعادة الاستخدام لما الإعداد اللي بيتغير يعيش برهها. ConfigMap للإعداد غير السري. Secret للبيانات الحساسة. الاتنين مش بيئة سحرية جوه الصورة.

الـ Secret افتراضيًا بيتخزن كبيانات الـ API، والقيمة في YAML بتظهر base64. التشفير ده ترميز، مش حماية. الحماية بتيجي من RBAC، ومن تشفير etcd at rest لو متظبط، ومن عدم ظهور القيمة في أوامر وسجلات وصور. ما تحطش كلمة سر في ConfigMap عشان "مش Secret ومش هتتراجع".

المتغير اللي داخل من env بيتقفل لقطة وقت إنشاء الحاوية. تحديث الـ ConfigMap ما يغيّرش المتغيرات دي إلا بإعادة تشغيل. الملف اللي جاى من volume بيتحدثه الـ kubelet على دورة مزامنة، مش في نفس اللحظة، والتطبيق لازم يعيد قراءة الملف. لو التطبيق ما بيعيدش القراءة، غيّر annotation في قالب الـ Pod عشان تعمل rollout.

immutable: true على ConfigMap أو Secret بيمنع التعديل وبيسمح للـ kubelet يتوقف عن متابعتهم. مناسب للإعداد اللي تغييره أصلاً بيتم بنسخة جديدة.

الأقراص

emptyDir مساحة فاضية بعمر الـ Pod، كويسة لملفات مؤقتة. hostPath ملف على الـ Node، خطر ومربوط بآلة معينة. بيانات التطبيق المهمة تعدي من PVC. الـ PV هو القرص. الـ PVC هو الطلب. الـ StorageClass مع CSI بيعمل توفير ديناميكي: تعمل PVC، والمزوّد يعمل القرص ويربطه.

وضع الوصول ReadWriteOnce معناه إن القرص يتوصل للكتابة من Node واحدة في الوقت نفسه، مش "من Pod واحد" بالضرورة. نسختين على Node واحدة ممكن يتشاركوا قرص RWO حسب المزوّد، ونسختين على آلتين لأ. ReadWriteMany مش متاح في كل أنظمة التخزين. افترض إن قاعدة البيانات محتاجة قرص لكل نسخة، وتحقق من الـ storage class.

ملخص الفصل: افصل الصورة عن الإعداد. افصل السر عن الترميز. افصل قرص الـ Pod المؤقت عن القرص اللي له عمر أطول من الـ Pod. وفي الإنتاج، سر من غير تشفير at rest ومن غير RBAC لسه سر ظاهر للي يقدر يقرأ الـ API.

8. الجدولة، الطلبات، والحدود

الـ scheduler ما بيشغّلش الحاوية. هو بيكتب binding. قبل كده بيعمل فلترة: الموارد، الـ taints، والقيود الصلبة. بعدين بيحسب نقاط: التوزيع، والتفضيلات. أول ما الـ binding يتسجل، الـ kubelet على الـ Node المختارة ياخد الشغل.

Requests و limits و QoS

الـ request هو اللي المجدول بيحجزه، وأساس نسبة استهلاك المعالج في الـ HPA. الـ limit سقف. المعالج قابل للضغط: الـ limit بيخنق عن طريق حصة CFS حتى لو الآلة فاضية. الذاكرة مش قابلة للضغط: تعدي الـ limit يخلّي الحاوية تتقتل بـ OOMKilled، وغالبًا الخروج 137.

الفئةالشرط المبسطأثر عملي

قرار إنتاج، مش قاعدة مطلقة: حد الذاكرة غالبًا لازم يتظبط لإن القتل واضح أحسن من إن عملية تاكل ذاكرة الـ Node. حد المعالج قرار زمن استجابة. فرق كتير بتظبط requests صادقة وبتسيب حد المعالج فاضي أو واسع عشان تقلل الخنق، وفرق تانية بتفرض الحد عشان العزل. اعرف أثر الاتنين على الشغل بتاعك.

Taints و affinity

الـ taint على الـ Node طرد. الـ toleration على الـ Pod تصريح بالوجود رغم الطرد. الأثر NoSchedule يمنع الجديد، وPreferNoSchedule تفضيل، وNoExecute يقدر يطلّع الموجود. عقد التحكم عادة عليها taint عشان تطبيقات الناس ما تنزلش عليها. الـ Pods بتاخد tolerations افتراضية لـ not-ready وunreachable لمدة 300 ثانية، وبعدين ممكن تتشال لو العقدة لسه مش سليمة.

nodeSelector مطابقة بسيطة. affinity قواعد أغنى، ومنها تفضيل أو إجبار القرب أو البعد عن Pods تانية. topologySpreadConstraints طريقة مباشرة لتوزيع النسخ على zones أو Nodes. anti-affinity الصلبة مع عدد نسخ أكبر من عدد الـ zones بيخلّي النسخ الزيادة Pending. دي غلطة تصميم شائعة.

ملخص الفصل: المجدول بيحجز بالـ requests وبيحترم الطرد والقيود. الـ limit سياسة قتل أو خنق وقت التشغيل، ومش رقم بيستخدمه المجدول عشان يلاقي مكان. اقرأ حدث المجدول قبل ما تزود نسخ.

9. الـ probes، الإصلاح، والتحديث التدريجي

ثلاث فحوصات، وثلاث نتائج مختلفة. الخلط بينهم هو سبب أشهر أعطال "التطبيق بيعيد التشغيل لوحده" و"الخدمة من غير عناوين".

ما تعملش liveness على "قاعدة البيانات بعيدة" أو على مسار بيعمل شغل تقيل. لحظة عطل في الاعتماد هتعيد تشغيل كل النسخ وتكبّر العطل. الجاهزية هي اللي تقول "ما تبعتليش طلبات". الحياة بس للعملية اللي مش هترجع إلا بالقتل. مسار الحياة يبقى رخيص ومحلي.

تسلسل الـ rollout

  1. تغيير القالب يرفع generation ويعمل ReplicaSet جديد.
  2. maxSurge يحدد كام Pod زيادة عن العدد المطلوب مسموح. maxUnavailable يحدد كام من العدد المطلوب يقدر يغيب.
  3. الاتنين صفر مع بعض إعداد مرفوض عمليًا لإن مفيش طريقة تحرك. maxUnavailable: 0 مع maxSurge: 1 بيحافظ على الطاقة القديمة لحد ما الجديدة تبقى جاهزة، وبيحتاج مكان لنسخة زيادة.
  4. النسخة الجديدة ما بتتحسبش جاهزة إلا بعد نجاح الجاهزية، وبعد minReadySeconds لو متظبط.
  5. لو مفيش تقدم خلال progressDeadlineSeconds، والافتراضي 600 ثانية، حالة الـ Deployment تبقى ProgressDeadlineExceeded.

إعادة التشغيل من غير تغيير صورة بتتم بتغيير annotation على القالب، وkubectl rollout restart بيعمل كده. الرجوع kubectl rollout undo بيرجع لـ ReplicaSet قديم لسه محفوظ.

HPA و PDB

الـ HorizontalPodAutoscaler في autoscaling/v2 بيغيّر replicas. نسبة المعالج بتتحسب من الـ request. من غير request، المقياس ده ما لوش أساس. محتاج مصدر مقاييس؛ الـ metrics-server يكفي للمعالج والذاكرة. التوسع الرأسي VPA مشروع تاني، ومش نفس الكائن.

الـ PodDisruptionBudget بيحد الإخراج الطوعي، زي تفريغ Node، مش بيمنع سقوط آلة. minAvailable أو maxUnavailable، واحد بس. ميزانية بتطلب كل النسخ تفضل موجودة مع تفريغ عقد هتخلّي التفريغ يقف. دي حماية صحة، وممكن تبقى عطل تشغيل لو الرقم مستحيل.

ملخص الفصل: الجاهزية بوابة traffic. الحياة ملاذ أخير للعملية المعلقة. الـ rollout حركة نسختين من ReplicaSet جوه حدود surge وunavailable. الميزانية بتحمي من الإخراج الطوعي، ومش من الفيزياء.

10. الهوية، RBAC، وسياسة الـ Pod

كل طلب ليه هوية: مستخدم بشري من kubeconfig، أو ServiceAccount جوه Pod، أو نظام تاني مظبوط على الـ API. بعد الهوية، RBAC بيقرر الأفعال. بعدين سياسات الـ Pod بتقيّد شكل الشغل اللي ينفع يتعمل.

الكائنالنطاقبيعمل إيه

كل namespace فيه ServiceAccount اسمه default، ورمزه بيتوصل للـ Pods إلا لو قفلت automountServiceAccountToken: false. الحساب ده من غير bindings زيادة ما يقدرش يعمل حاجة مفيدة، لكن وجود الرمز عادة توسعة غير مقصودة. تطبيق ما بيناديش الـ API: اقفل التركيب. تطبيق بينادي الـ API: اعمل حساب خاص وRole على الموارد والأفعال المطلوبة بس، ومنها subresources زي deployments/scale.

PodSecurityPolicy اتشالت في 1.25. البديل المدمج هو Pod Security Admission بمعايير privileged وbaseline وrestricted، وأوضاع enforce وaudit وwarn عن طريق labels على الـ namespace. معيار restricted أضيقهم: من غير root، ومن غير صلاحيات زيادة، ومع seccomp، ومن غير namespaces بتاعة المضيف. في 1.34 المعيار ده كمان بيرفض probes وlifecycle handlers بتحدد host بعيد. القائمة الكاملة للشروط مكانها توثيق Pod Security Standards، لإن نقلها من الذاكرة هنا هينقص قاعدة.

سياق الأمان اللي يستاهل يبقى عادة في التطبيقات العادية: runAsNonRoot، allowPrivilegeEscalation: false، readOnlyRootFilesystem مع volume للكتابة المؤقتة، وcapabilities.drop: ["ALL"]، وseccompProfile.type: RuntimeDefault. الصورة اللي عملية التشغيل فيها root هتقع لو فرضت القيود دي قبل ما تظبط الصورة. القيود جزء من تصميم الصورة، مش ملصق آخر خطوة.

ملخص الفصل: 401 هوية، 403 تفويض، والرفض من admission شكل أو سياسة. أصغر Role يؤدي الشغل. معيار الـ Pod بيتقفل على الـ namespace اللي يقدر يستقبل شغل الناس، مش بس على كائن واحد وأنت بتكتب المثال.

استثناءات هتشوفها

  • ApiException.status == 401: الهوية أو الرمز.
  • 403: الـ Role ناقص فعل أو مورد أو subresource.
  • 409: الكائن موجود وأنت بتعمل create، أو resourceVersion قديم وأنت بتحدّث.
  • 422: الجسم عدى HTTP لكن الـ API رافض المعنى، زي selector مش مطابق أو حقل ممنوع.
  • 410 على watch: نسخة المورد اللي بتتابع منها خلصت. اعمل list من جديد وخد resourceVersion الحالي وابدأ المشاهدة تاني.

في عميل Python، حجة تنفيذ أمر جوه فحص exec غالبًا اسمها _exec مش exec، لإن exec كلمة محجوزة. لو الكونستركتور رفض الاسم، راجع نسخة المكتبة قبل ما تغيّر تصميم الفحص.

kubernetes.utils.create_from_yaml مناسبة لسكربت إنشاء أولي. هي مسار create، ولو المورد موجود بتفشل. التحديث المتكرر للبشر والـ GitOps مكانه kubectl apply وتطبيق من جهة الخادم. في Python، التحديث الجزئي عن طريق patch_*، ونوع المحتوى الافتراضي في دوال patch الشائعة strategic merge. لو بعت JSON patch، شكل الجسم يبقى قائمة عمليات مش خريطة.

ملخص الفصل: المكتبة عميل API. اختَر التكوين حسب مكان العملية. عامل 409 و403 كجزء من التصميم. ما تديش عملية الأتمتة cluster-admin عشان المثال يخلّص.

Python · عميل رسمي

from kubernetes import client, config
from kubernetes.client.exceptions import ApiException

NAMESPACE = "shop"
NAME = "learn-nginx"


def load_config() -> None:
    """داخل Pod استخدم حساب الخدمة. على جهازك استخدم kubeconfig."""
    try:
        config.load_incluster_config()
    except config.ConfigException:
        config.load_kube_config()


def deployment_body(image: str, replicas: int) -> client.V1Deployment:
    labels = {"app": NAME}
    container = client.V1Container(
        name="nginx",
        image=image,
        image_pull_policy="IfNotPresent",
        ports=[client.V1ContainerPort(name="http", container_port=80)],
        readiness_probe=client.V1Probe(
            http_get=client.V1HTTPGetAction(path="/", port="http"),
            period_seconds=5,
            failure_threshold=2,
        ),
        resources=client.V1ResourceRequirements(
            requests={"cpu": "50m", "memory": "64Mi"},
            limits={"cpu": "200m", "memory": "128Mi"},
        ),
    )
    template = client.V1PodTemplateSpec(
        metadata=client.V1ObjectMeta(labels=labels),
        spec=client.V1PodSpec(
            service_account_name=NAME,
            automount_service_account_token=False,
            containers=[container],
        ),
    )
    return client.V1Deployment(
        api_version="apps/v1",
        kind="Deployment",
        metadata=client.V1ObjectMeta(name=NAME, labels=labels),
        spec=client.V1DeploymentSpec(
            replicas=replicas,
            selector=client.V1LabelSelector(match_labels=labels),
            template=template,
        ),
    )


def ensure_deployment(image: str, replicas: int) -> None:
    apps = client.AppsV1Api()
    try:
        created = apps.create_namespaced_deployment(
            namespace=NAMESPACE,
            body=deployment_body(image, replicas),
            dry_run="All",
        )
        print("dry-run ok:", created.metadata.name)
    except ApiException as exc:
        raise SystemExit(f"rejected before create: {exc.status} {exc.reason}") from exc

    try:
        apps.create_namespaced_deployment(
            namespace=NAMESPACE,
            body=deployment_body(image, replicas),
        )
        print("created")
    except ApiException as exc:
        if exc.status == 409:
            print("already exists; leaving it unchanged")
        else:
            raise


def main() -> None:
    load_config()
    ensure_deployment("nginx:1.27-alpine", 2)


if __name__ == "__main__":
    main()

تتبع التنفيذ

  1. على اللابتوب، load_incluster_config ترمي ConfigException لإن مفيش ملفات رمز الخدمة. الاستثناء يتتمسك، وload_kube_config يقرأ السياق الحالي.
  2. dry_run="All" يمرّر الجسم على التحقق من غير حفظ. لو الـ selector فاضي أو النوع غلط، هتشوف الرفض هنا.
  3. create_namespaced_deployment طلب POST على /apis/apps/v1/namespaces/shop/deployments. النجاح يرجع الكائن ومعاه uid وresourceVersion.
  4. لو الاسم موجود، 409. السكربت ما يحاولش يرقّع بصمت.
  5. بعدها، في أداة حقيقية، تقرأ status.ready_replicas لحد ما تساوي spec.replicas، أو المهلة تخلص. الحلقة دي كويسة لأمر قصير. الـ controller الطويل يستخدم watch وقائمة شغل، ويعيد list لما ياخد 410.

import time
from kubernetes import client
from kubernetes.client.exceptions import ApiException


def wait_ready(timeout: int = 120) -> None:
    apps = client.AppsV1Api()
    deadline = time.monotonic() + timeout
    while time.monotonic() < deadline:
        dep = apps.read_namespaced_deployment(NAME, NAMESPACE)
        desired = dep.spec.replicas or 0
        ready = dep.status.ready_replicas or 0
        print(f"ready {ready}/{desired}")
        if desired and ready >= desired:
            return
        time.sleep(2)
    raise TimeoutError(f"{NAME} was not ready within {timeout}s")


def print_pods() -> None:
    core = client.CoreV1Api()
    pods = core.list_namespaced_pod(NAMESPACE, label_selector=f"app={NAME}")
    for pod in pods.items:
        print(pod.metadata.name, pod.status.phase, pod.status.pod_ip)


def scale_to(replicas: int) -> None:
    apps = client.AppsV1Api()
    apps.patch_namespaced_deployment(
        name=NAME,
        namespace=NAMESPACE,
        body={"spec": {"replicas": replicas}},
    )


def explain_forbidden(exc: ApiException) -> None:
    if exc.status == 403:
        print("RBAC refused the call. Check verb, resource, and namespace.")
        print(exc.body)
    else:
        raise exc

مفاهيم بتتقلب

  • فشل الحياة ما بيعملش جدولة على Node جديدة لمجرد الفشل. بيعيد الحاوية.
  • فشل الجاهزية ما بيقتلش الحاوية. بيوقف traffic.
  • وجود NetworkPolicy في etcd مش معناه إنها بتتطبق.
  • Secret مش تشفير. base64 مش سرية.
  • حد المعالج مش رقم الجدولة. الـ request هو رقم الجدولة.
  • Service من غير selector ما بيعملش اختيار سحري. يا إما تكتب selector، يا إما تمتلك الـ EndpointSlices بنفسك، ودي حالة متقدمة.

سؤال 1 · أساسيات

Kubernetes بيحل إيه بالظبط؟

بيختبر: إنك مش حافظ تعريف تسويقي، وإنك فاهم المشكلة.

الإجابة النموذجية

إجابة قصيرة تتقال

Kubernetes keeps a desired state for containerized workloads. I declare Pods, replicas, and updates. Controllers schedule work onto nodes, replace failures, and roll changes. A Service gives clients one address while Pod IPs change.

الشرح

المنصة مش runtime. الـ runtime بيشغّل الحاوية. Kubernetes بيوزعها ويحافظ على العدد والتحديث والاكتشاف. من غيرها الفريق يبني الحلقات دي بنفسه.

إجابة ضعيفة

"أداة Docker بتاع Google." دي بتخلط التاريخ بالوظيفة وبتجاهل CRI.

متابعة

  • امتى ترفض تدخل Kubernetes؟
  • إيه اللي بيفضل شغال لو الـ API وقع؟

لمسة senior

تكلفة التشغيل والمراقبة والنسخ الاحتياطي لـ etcd. للخدمة الواحدة على آلة واحدة، المنصة ممكن تبقى حمل أكبر من الفايدة.

سؤال 2 · أساسيات

الفرق بين Pod و container؟

بيختبر: نموذج الجدولة والشبكة.

الإجابة النموذجية

إجابة قصيرة تتقال

A container is the process. A Pod is the scheduling unit around one or more containers. They share the Pod network namespace, so they use localhost with each other, and they share volumes. The Pod has one IP.

الشرح

إعادة تشغيل الحاوية بتحصل جوه نفس الـ Pod. الـ sandbox بيمسك الشبكة. عشان كده المساعد والتطبيق يتكلموا على localhost، لكن خدمتين مستقلين ما ينحطوش في Pod واحد بلا سبب.

إجابة ضعيفة

"الـ Pod هو container بس في Kubernetes." بتضيّع المشاركة والجدولة الذرية.

متابعة

  • إيه اللي يحصل لعنوان الـ Pod لو الحاوية وقعت؟
  • امتى sidecar يبقى مبرر؟

لمسة senior

من 1.33 الـ sidecar الأصلي init container بسياسة restartPolicy: Always، وترتيب الإيقاف بتاعه مختلف عن حاوية عادية جنب التطبيق.

حدود الدليل والمراجعة

  • الأمثلة ما اتنفّذتش على cluster وقت كتابة الملف. الناتج المذكور شكل متوقع، مش سجل جلسة.
